# 重要设计取舍追溯

此表区分产品要求与技术效果。无论设计是否已确认，行为测试均尚未运行。完整说明见DESIGN.md。

| 取舍 | 依据 | 目标落点 | 待验证风险 |
|---|---|---|---|
| 轻量方法库，不保留强制runtime | 用户明确要求参考Matt，以目标、规则、边界和任务为核心 | 全体技能与工程组织 | 不能误称保留全部旧后端/迁移恢复保障 |
| 一句话组合入口 | 用户明确要求简短组合而非重复方法 | grill与grill-docs | 依赖未加载时不能凭名称模拟 |
| 知识是观察视角而非问卷 | 多轮已确认游戏提问设计 | grilling及各领域参考 | 不引入无关系统、不反复问已知事实 |
| GDD与spec分开且自动协作 | 用户明确要求在问答中由Agent判定归属并调用 | gdd/spec/domain/grilling | 精度丢失、循环写入、部分成功和错误定稿 |
| 标签沿用，人机责任写入验收 | 用户关心Agent能否识别自己与人的边界 | setup/tasks/implement/review | 不因ready-for-agent就提前关单 |
| 原型默认为浏览器小游戏 | 用户明确要求真实玩法、SVG美术、互动和反馈 | prototype | 交互网页冒充游戏、桌面结果冒充目标设备 |
| Research有不同深度，无pplx依赖 | 用户确认研究深度，随后取消专项收费API | research/wayfinder | 工具兜底被当成降低证据要求 |
| Docs用于所有正式工作资料与子代理指令 | 用户最新明确范围；Matt参考方法广泛适用 | Docs及所有实际产出点 | 当前源码未接入，跨上下文不能假设继承 |
| Codebase/Merge/Docs加入整合范围 | 用户点名三项进行设计；最终细节未笼统标为全通过 | 最近三项草案 | 过度抽象、资源误合并、文档改写丢失责任 |
| 不搬完Matt其他六项 | 用户要求取舍，不追求覆盖数量 | 候选发布范围 | 被暂缓能力不能悄悄声称已由其他技能完整替代 |
