# MyGameStudio 改版：游戏专业产出与证据合同候选

研究日期：2026-09-15。读取的本地 HEAD：`268e2fa6fd535482c3567c8b58f124aa09d93f94`。性质：支持改版决策的研究与建议，未采纳、未实施，也不是任何游戏的验收报告。

## 结论

建议把游戏专业性放在按项目条件选择的产出与验证合同中，接入既有规划、任务和评审流程；不要为每项专业要求重造一套管理系统。研究仅核实五类问题：可玩验证、目标设备性能、资源导入集成、持久状态、发行准备。以下合同是由本地现状及官方资料推导的设计建议，不是引擎或平台要求所有项目采用的统一制度。

## 已有能力必须保留

- [Game-Design] 已覆盖游戏设计九类模块规格、数值单位与取整、玩家流程与失败恢复、跨模块矛盾、主观体验验证方法和阶段阻断。已开发或已发布的变更会核对存档、玩家进度与迁移影响。因此不应声称“当前没有游戏专业设计或存档意识”。
- [Game-Art] 和 [Game-Audio] 已要求真实资源、来源或生成依据、规格检查、预览或播放入口、接入信息与集成责任，并保留人工审美/听感待验收。资源交付与集成已有分工，新增项应明确“接下来如何证实集成成功”。
- [Game-Build] 已要求实际构建、源版本对应、启动入口、真实运行记录、待试玩与外部发布权限分离。[Game-Playtest] 已要求明确版本、实际执行、逐场景证据、人工反馈来源、版本指纹与相关复测。
- [技术设计模板] 已有性能、存档、兼容和平台约束占位；[模板说明] 明确专有字段按需添加，不强迫所有游戏填全。当前提升空间是把这些提示落实为可选择的专业检查内容，而不是说它们完全不存在。

## 七项值得决策的合同候选

### 1. 当前可玩增量对应玩家行为与规则

**建议通常适用，实施时按变更风险缩放。** 每个玩家可见增量说明：玩家起始状态、实际操作、反馈/状态变化、完成或失败结果、涉及的当前规则。跨系统工作优先交付能走通的薄切片；纯资源任务可交付资源，但其集成验收另有明确归属。

最小证据是适用构建、运行入口、关键步骤和实际观察，失败与退出路径按实际风险选择。延用现有 [Game-Design] 的玩家旅程与 [Game-Playtest] 记录，不要求每个小修复都重新全流程试玩。此项主要是本地已有合同的组合建议；官方资料不能证明某种固定里程碑命名或切片粒度适合所有游戏。

**需要决定：** 哪些类型的完成声明必须附实际可玩证据，哪些变更只需局部行为/资源检查。

### 2. 体验问题、行为正确性与人的反馈分别结论

**体验判断被声明或将决定投入时触发。** 每次试玩先写需要回答的体验问题，例如新玩家是否理解下一步、失败反馈是否足够清楚、操作是否有预期节奏。记录参与者情况、步骤、实际反馈和限制；做过一次试玩只能支持那次观察，不能自动证明市场效果。

[Steam Playtest 官方资料](https://partner.steamgames.com/doc/features/playtest) 的“Gathering Feedback From Players”说明反馈收集由开发者负责，并建议告诉玩家需要什么反馈和去哪里反馈。页面并未规定统一样本量、通过率或研究方法；本研究不据此发明强制样本阈值。

现有 [Game-Playtest] 已分离 Agent 观察与人工反馈，并规定操作和回传要求。补强点是把反馈对应到待作的设计决定，以及“继续投入、局部调整、暂停验证”的项目选择；不是再加一套真假反馈纪律。

**需要决定：** 何时必须由目标玩家参与，何时开发者自身试玩足以支持当前阶段；无反馈是否阻断由哪个具体体验风险决定。

### 3. 目标设备与场景明确的性能预算

**需要承诺运行体验或优化效果时触发，数值由项目决定。** 最小合同包含目标设备/最低档、构建与画质设置、代表性场景、帧时间与卡顿证据、约定预算和实测限制。内存、加载时间、发热等仅在平台或场景需要时添加。

[Unity 官方性能指南](https://unity.com/how-to/best-practices-for-profiling-game-performance) 建议设置帧时间预算、确定硬件档位或最低配置，并在目标设备的构建上分析；编辑器观测不足以代替实际目标设备，深度分析还会引入额外开销。由此推导：不能用开发机平均 FPS 或静态代码审查声称低端设备达标。

[技术设计模板] 已提示性能约束；候选增量是明确预算、采样条件和结果证据。不要全局写死 60 FPS、某个百分位、某种工具或大型设备实验室。

**需要决定：** 项目何时选择性能目标，首个可玩版本需要覆盖哪些设备和场景，以及无法取得设备时如何标识未验证。

### 4. 资源从制作、导入到导出运行的完整接入

**使用外部资源或引擎导入流程时触发。** 资源文件的尺寸、声道或格式检查通过之后，还需明确导入配置、引擎引用方式、集成责任及游戏内验证；替换源资源后检查重导入是否保留约定效果。2D/3D、材质、碰撞、动画、声音循环等字段按类型选择，不强迫所有项目配置全部内容。

[Godot 官方导入文档](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/import_process.html) 说明源资源会转成内部资源，导入参数写入伴随文件，源资源变化会重导入；还给出“编辑器里可以、导出后会坏”的具体边界：已导入资源应通过 ResourceLoader 访问，FileAccess 直读可能在导出后失效。相应文件管理方式属于 Godot，不能照搬到所有引擎。

[Game-Art]、[Game-Audio] 已有来源和接入责任，[Game-Build] 已有入口和引用检查；候选新增是把“引擎内效果与导出后实际加载”明确交给集成验收，引用已有资源结果，避免资源制作完成后无人检查游戏内结果。

**需要决定：** 资源任务与集成任务何时可以是同一张任务，何时分开；如何记录“文件合格、已接入、导出运行通过”三个不同事实而不引入重复状态系统。

### 5. 持久状态、恢复与既有存档的适用场景

**有跨会话状态时触发；存在旧存档且变更触及格式或规则时才增加兼容决策。** 先确定哪些对象与状态必须保存、何时写入、何时恢复、缺失或无效数据的玩家可见处理。正常保存→退出→恢复应使用真实产物验证。已有玩家或历史存档时，再选择保留读取、迁移或明确重置策略，并准备代表性旧数据验证。

[Godot 官方存档教程](https://docs.godotengine.org/en/stable/tutorials/io/saving_games.html) 要求先识别需要持久化的对象与信息，并指出加载前的状态重置、嵌套对象顺序和引用恢复需要按项目定制。它只是教程，没有提供通用生产级兼容或灾难恢复保证。版本识别、损坏数据处理与旧存档测试是基于这些边界和项目风险的建议，不能冒称官方统一要求。

[Game-Design] 已有阶段、存档与迁移影响分析。增量是让决定能够落成实现验收场景；没有存档的短体验、已核实没有旧用户数据的项目，不机械增加迁移和补偿流程。

**需要决定：** 首次存档实现的最低恢复保证，以及已发布变更需保留哪些旧状态、哪些情况必须由开发者选择。

### 6. 测试构建、目标平台与测试结论一一对应

**声明某版本可运行时通常适用；范围等于实际承诺的平台。** 保留现有源版本与产物身份，补充引擎/工具版本、目标平台、关键构建配置、安装/启动方式及平台覆盖表。测试对象应为交付构建；编辑器、桩环境、真实客户端证据分别表述。不存在通用要求必须为每个产物找到单个一一对应的源文件：构建清单应表达真实输入、配置与输出关系。

[Steam 构建审核规则](https://partner.steamgames.com/doc/store/review_process?l=english) 要求产品在商店页面声明的所有支持操作系统上正常启动。[Godot 导入文档](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/import_process.html) 则给出编辑器与导出结果不同的实际原因。因此建议在已有 [Game-Build]、[Game-Playtest] 的版本指纹机制上增加“哪个平台上的哪个构建支持了这项结论”。

**需要决定：** 是否以一个统一构建清单承接资源、运行和试玩证据；不能访问的平台保留未测，不降低声明范围后假称通过。

### 7. 发行承诺和当前构建相符的准备清单

**确定外部发行平台并进入发行准备时触发。** 清单包括实际发行范围、平台要求的当前来源、商店内容/支持功能与实际构建的对应、提交审核所需材料、未完成项与明确责任。准备完成、平台审核通过、实际发布分别记录；不为概念和本地原型提前强制一套商店手续。

[Steam 官方审核流程](https://partner.steamgames.com/doc/store/review_process?l=english) 将商店页面和构建审核分开，要求商店所称支持功能在当前构建中实现，截图展示游戏内容，未来内容说明真实状态。这是 Steam 适用要求，不代表所有平台规定相同；本研究没有检查任何实际商店后台或提交状态。

现有 [Game-Build] 明确普通构建不自动上传或发布。候选补充是“准备哪些材料才能请求发布”，不用构建技能顺带执行平台操作，也不新增所有项目必经的常设发行角色。

**需要决定：** 发行准备作为按需专业合同，还是独立入口；其完成是否由哪些平台事实阻断，如何保持实际发布授权独立。

## 接入改版地图的建议

最先适合讨论的一个决定是：**哪些游戏专业证据属于所有项目的最低完成条件，哪些由项目类型、阶段和风险触发？** 它会约束后续技能拆分、模板和流程复杂度。上述七项是该决定的候选素材，不应自动变成七套入口或七张实施工单。

通常保留：当前规则能定位、结果对应版本、可运行/资源真实性有实际证据、人的体验结论有真实来源。条件增强：性能目标、引擎资源导入、持久状态、旧存档、目标平台矩阵、商店与发行要求。先选合同及触发条件，再决定挂到规划、实现、评审或试玩的哪个现有位置。

优先补强建议为性能证据、资源导出集成、状态恢复和发行准备四块；设计完整性、资源真实性和人工反馈纪律现状较明确，应提炼保留，避免改版时遗失。这里“较明确”只指文档要求的明确程度，不代表实际用户项目中已验证执行效果。

## 证据范围与限制

- 本地阅读覆盖 Game-Design、Art、Audio、Build、Playtest 及相关模板；并按专业关键词核查合同、Prototype、Implement 和模板。没有运行整个插件，也没有验收实际游戏。不能用本文判定插件或任何游戏已达到质量门槛。
- 外部采用五类官方文档。Unity 来源是官方性能方法指南，不是对某个已安装 Unity 版本 API 的验证；Godot `stable` 页面会随版本移动，最终引擎适配应固定项目版本重新核对；Steam 规则也应在真实发行准备时重查。
- 不引用搜索结果中的论坛和二手文章。不复制统一阈值、不宣称固定试玩人数能证明好玩、不将 Steam 条款泛化成跨平台法律或发行要求。
- 本次没有研究多人联网、反作弊、经济平衡、付费、长期运营或完整无障碍标准；这些是否必要依赖具体支持范围，应由地图另行澄清，而非据本研究默认加入所有项目。
- 本文只支持“应讨论什么专业合同”的规划决定；最终门槛、技能边界、是否阻断以及平台选择均尚未由用户采纳。
