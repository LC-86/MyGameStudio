# MyGameStudio 全插件分阶段架构重构

Design basis: 用户已确认的分阶段总方案与原子任务读取设计
Code baseline: `49f3b1e7323c02a5fd39f3d9c847df023c4f2459`
Branch: `codex/architecture-optimization`

本规格发布到项目本地 Markdown 工单系统，作为后续拆票依据。分流状态表示规格可交给 Agent 继续处理，不代表已实施或已验收，也不授予提交、推送、安装和发布权限。

## Problem Statement

独立开发者希望持续完善 MyGameStudio，但现有实现存在长文件、重复代码、跨 module 的规则依赖和重复读取。理解与修改一个行为往往需要同时检查任务读取、后端、运行保障及验收脚本，增加维护成本和回归风险。

已核对的代码基线包含 4,526 行生产 Python，以及 29,825 行测试与验收代码。18 份验收客户端合计 4,605 行，存在重复实现和实际行为差异。最大测试文件为 4,024 行，其中一个测试函数有 1,499 行。单纯删行或分文件不足以改善维护体验，需要让完整职责集中、验证更直接。

任务读取还有可复现的行为问题：一次可开工查询读取 CONFIG 六次、任务集合两次；两次任务内容不同，会将不同读取时点的信息混合成一个结论。验收客户端的合成回放也显示，1,000 条固定事件经过十次轮询被 JSON 解码 21,000 次。

用户已经确认：保持现有使用方式、记录格式和已验收行为，允许内部重构；需要修正的行为逐项列明。优化应减少维护负担和无必要操作，同时保留权限、恢复与证据语义。

## Solution

在独立分支按可验收成果逐阶段重构：先固定可复跑的行为基线，再统一原子任务读取；随后整理验收判据与测试、合并验收客户端、集中工作结果发布恢复、整理受控写入，最后精简业务 Skill 的共同说明。

开发者继续使用现有十四个业务入口、命令行和受控工具。已有项目与任务不需要因第一阶段重构迁移数据。可开工查询减少重复读取，同一次判断使用同一份已取得任务集合；下一次调用重新读取，反映之后的修改。

module 的 depth 通过完整行为和较小 interface 体现；locality 通过同一规则集中维护体现；leverage 通过多个真实调用复用实现体现。性能以实际读取、请求、解码次数和实测耗时评价，代码量以相同范围的净增减评价。

## User Stories

### 使用兼容与全程维护

1. 作为独立开发者，我希望继续使用现有业务 Skill 调用方式，以便升级后的内部重构不打断日常工作。
2. 作为独立开发者，我希望已有任务、协作配置和工作记录保持可读，以便不需要为内部代码整理迁移项目数据。
3. 作为制作统筹，我希望原子任务身份、分流、进度、核心基线与成果验收的含义保持，以便能继续正确安排工作。
4. 作为插件维护者，我希望每个阶段交付可运行、可检查的完整行为，以便逐步推进并及时发现回归。
5. 作为插件维护者，我希望新增及整理后的文件有明确职责和长度约束，以便快速定位要修改的规则。
6. 作为插件维护者，我希望代码净减量包含新增共享实现和适配代码的成本，以便知道实际减少了多少重复。
7. 作为独立审查者，我希望行为修正与纯结构调整分别登记，以便判断变化是否符合已确认范围。
8. 作为独立开发者，我希望每阶段保留可说明的回退方式，以便发现问题时能恢复匹配的代码与交付包。

### 原子任务读取

9. 作为制作统筹，我希望一次可开工查询只获取一份任务集合，以便依赖和任务状态不会混用两次读取结果。
10. 作为制作统筹，我希望一次查询的配置字段与执行条件来自同一份 CONFIG 原文，以便判断不会使用相互不一致的配置。
11. 作为制作统筹，我希望下一次查询重新读取任务和配置，以便能看到用户刚刚修改的安排。
12. 作为专业角色，我希望可开工集合继续说明它不是执行授权，以便不会把记录层面的就绪误当成允许写入。
13. 作为本地任务使用者，我希望列举任务继续按现有目录顺序输出，以便已有任务选择与安排方式保持。
14. 作为 GitHub 任务使用者，我希望 list 与 ready、deps 各自保留原有顺序，以便内部共享读取不会改变现有选择结果。
15. 作为本地任务使用者，我希望 show 继续按指定任务目录读取，以便目录与正文身份不一致时仍能定位并检查原记录。
16. 作为本地任务使用者，我希望读取一个任务时不扫描无关任务，以便保持当前单任务读取的范围和成本。
17. 作为 GitHub 任务使用者，我希望 show 继续读取所需的 Issue 详情与评论，以便任务结果不会被列表中的概略信息替代。
18. 作为制作统筹，我希望远端不可用时仍能辨认缓存来源与时间，以便不会把旧数据当成刚确认的远端状态。
19. 作为制作统筹，我希望远端不可用且没有缓存时明确失败，以便不会静默使用另一个本地任务来源。
20. 作为命令行调用者，我希望 list 仍返回原有 JSON 数组和字段，以便已有消费程序继续工作。
21. 作为命令行调用者，我希望其他读取命令的参数、返回字段、错误和退出码保持，以便已有脚本不需要改用新协议。
22. 作为插件调用方，我希望脚本运行和 Python 导入使用同一错误类型，以便既有错误处理能继续捕获后端失败。
23. 作为双后端使用者，我希望相同任务正文的共同字段只按一套规则解析，以便本地与 GitHub 不会因重复实现产生偏差。
24. 作为 GitHub 任务使用者，我希望标签优先级、分流冲突和关闭原因继续被保留，以便存储特有事实不因共享解析而丢失。
25. 作为独立审查者，我希望畸形任务仍能进入核验，以便缺身份、空字段或不一致记录不会被提前过滤而隐藏。
26. 作为制作统筹，我希望基线的格式修正、实质变化及原版本完成事实继续分别表达，以便不会错误作废已有成果。
27. 作为项目操作者，我希望后端迁移计划和交接读取保持原语义，以便整理依赖关系不改变任务映射与资料引用。

### 验收判据与测试

28. 作为独立审查者，我希望验收判据与运行脚本使用同一可调用 interface，以便测试验证的是实际参与验收的规则。
29. 作为独立审查者，我希望判据仍核对真实事件、具体资源、动作与命令归属，以便报告措辞或示例文本不能冒充行为证据。
30. 作为插件维护者，我希望通过离线事件回放检查判据，以便常规回归不必启动真实模型或真实远端操作。
31. 作为插件维护者，我希望测试按行为主题组织，以便失败能定位到具体职责而不是一个巨型测试函数。
32. 作为独立审查者，我希望所有已固化的正向对照、历史反例和已接受限制有对应关系，以便重构不会通过删测试制造通过结果。
33. 作为插件维护者，我希望测试不再正则截取 Shell 源码，以便合法的内部写法变化不会破坏测试入口。
34. 作为独立审查者，我希望保留实际运行脚本的接入检查，以便独立判据通过时还能确认现场调用链没有漏接。

### 验收客户端

35. 作为插件维护者，我希望十八个验收场景共用通信与等待实现，以便一次修复覆盖所有相关场景。
36. 作为验收执行者，我希望各场景保留自身身份与必要选项，以便客户端共享不会抹平五种现有行为差异。
37. 作为验收执行者，我希望事件增量消费、每条输入只解码一次，以便轮询成本不随旧事件反复累积。
38. 作为验收执行者，我希望普通完成、失败、超时及事件筛选保持原结果，以便已有证据与报告仍可比较。
39. 作为验收执行者，我希望绝对中断阈值与相对中断阈值分别保留，以便不同恢复场景仍能模拟预定中断时点。
40. 作为验收执行者，我希望退出码与子进程生命周期保持，以便中断测试能准确结束本次进程并留下真实证据。
41. 作为插件维护者，我希望重复的 GitHub 替身共用实现，以便故障注入与回读行为不会在多个副本中分叉。

### 工作结果发布恢复

42. 作为专业角色，我希望工作结果的未发布、结果未知、已发布待补索引和完成状态继续被区分，以便知道实际进度和恢复条件。
43. 作为专业角色，我希望超时或结果不确定时先回读远端，以便避免重复创建已经存在的成果记录。
44. 作为专业角色，我希望结果已发布但索引未完成时重试只补齐剩余工作，以便不会再次发布同一结果。
45. 作为插件维护者，我希望恢复登记核对完整请求归属，以便短标识碰撞的两个请求不会互相覆盖或冒认。
46. 作为项目操作者，我希望损坏登记继续明确披露并保留必要信息，以便能核对远端事实后恢复。
47. 作为已有项目使用者，我希望旧恢复登记布局继续按原约定读取和迁移，以便升级不会遗失已发布结果的身份。
48. 作为项目操作者，我希望清除恢复登记只影响属于当前请求的记录，以便不会删除另一请求的恢复依据。
49. 作为插件维护者，我希望在线执行和草稿重放复用相同恢复事实，以便同一状态不会在不同调用处被解释成不同结果。

### 受控写入

50. 作为独立开发者，我希望角色、原子任务、用途和实际授权继续共同约束写入，以便内部重构不放宽专业角色的权限。
51. 作为独立开发者，我希望撤销完成后的旧请求仍被拒绝，以便运行中的执行实例不能利用旧配置继续写入。
52. 作为独立开发者，我希望路径身份、换链和资源占用检查保持，以便别名、竞态或并发不能绕过受控写入。
53. 作为独立开发者，我希望本地写入在审计或登记失败时继续按原语义回滚，以便失败不会留下被误报的文件结果。
54. 作为项目操作者，我希望远端已经发生的结果在审计失败时仍如实披露，以便不会被误认为尚未执行并再次写入。
55. 作为插件维护者，我希望完整受控操作封装在同一职责中，以便调用方不需要自行拼接授权、持锁、执行和审计顺序。

### 业务说明与交付

56. 作为专业角色，我希望入口说明保留选择条件、输入输出和专业差异，以便更短的说明仍足以指导正确工作。
57. 作为插件维护者，我希望共同执行规则、写入协议与结果字段各有唯一维护位置，以便同一规则无需多处同步修改。
58. 作为独立开发者，我希望十四个业务入口继续仅显式触发，以便精简说明不会改变何时调用专业工作。
59. 作为插件维护者，我希望来源、许可证、固定上游方法和引用闭包保持完整，以便代码与说明整理后仍可追溯和交付。
60. 作为独立开发者，我希望每阶段报告实际检查、未验证项及匹配的交付包，以便能据真实证据决定后续安装和发布。

## Implementation Decisions

### 已确认的范围与顺序

1. 采用保持外部用法的内部重构。现有 Skill、命令行、MCP、公开 Python 调用和记录格式兼容；功能性修正分别登记。当前已批准纳入的首项修正是 R1：可开工查询混用两次任务读取。
2. 阶段依次为：0 固定基线；1 原子任务读取统一；2 验收判据与测试组织；3 验收客户端去重；4 工作结果发布恢复；5 受控写入内部整理；6 业务 Skill 与包内说明。
3. 阶段 2、3 的调查可提前；共享文件实施保持单一修改者。阶段 4、5 依赖可复跑基线和稳定判据。每个成果通过相应检查后再继续相关下游，失败先处理本阶段回归。
4. 第一阶段已细化到职责和验收。其余阶段按本规格的行为目标与退出条件继续细化内部实现，不预造通用框架；新增外部行为或新的实际取舍另行明确，不视作已确认内容。

### 第一阶段的 module 与 interface

5. 查询 module 组织本次配置加载、adapter 选择、任务集合与来源信息，以及依赖、可开工集合和基线判断。共同规则不反向依赖查询或命令行。
6. 首轮用两个有实质内容的共享 module 承接共同类型、正文及纯记录核验，以及协作配置、本地读取和文档位置检查。逻辑职责不要求一对一拆成文件；查询与命令行是否进一步拆开，以实际长度和职责混杂程度决定。
7. 本地 Markdown 与 GitHub 是两个真实 adapter。前者保留目录定位与文件结果，后者保留 Issue、标签、评论及恢复语义。迁移和交接读取直接依赖配置、共同规则与本地 adapter，消除对查询入口的反向调用。
8. 共同错误类型保留单一身份，GitHub 记录错误继续继承它。现有公开导入与脚本入口保持；仓库自身对私有实现的依赖随职责迁移调整。兼容导出不应变成永久公开所有内部函数的理由。
9. 每次顶层读取调用按需取得 CONFIG 原文一次，由同一原文解析配置与执行条件；需要任务集合时获取一次，依赖和可开工判断使用该集合。内部载体只在本次调用中存在，不新增公共参数或返回对象。
10. 下一次顶层调用重新读取。用于本次判断的核心文档按实际路径复用已读文本，逻辑版本和指纹从对应文本推导；不引入跨调用缓存或后台同步。
11. 本次任务集合保留来源顺序。需要排序或附加调用特有标记的结果使用独立投影，避免原地修改影响其他判断。本地按目录排序；GitHub list 按身份排序，ready、deps 保留原后端返回顺序。
12. 本地 show 继续按目录定位且不扫描无关任务。GitHub show 保留集合定位、详情与评论读取；verify 保留标签、评论或本地结果文件核验。一次任务集合获取不等于所有命令只允许一个网络请求。
13. 同调用复用只保证不隐式重取集合后混合计算，不承诺多个文件、远端详情、评论与基线处于同一时刻的事务一致状态。

### 对外结果与 R1

14. config 保留现有配置字典；list 的 Python 返回继续为任务列表，命令行继续为原有字段投影的 JSON 数组。show 保留单任务结构；deps 保留依赖边、未解析引用、循环及整体结果；ready 保留可开工、阻塞原因与既有读取元信息。
15. baseline 保留双指纹口径和受影响任务含义；verify 保留检查名称、顺序、结果及后端特有信息。公开函数和后端构造入口的现有参数、默认值及错误含义保持。
16. 离线列表、详情和 ready 分别保留各自已有缓存标识、来源、时间与说明。远端无缓存时按现有方式失败，不回退本地。没有读取元信息的现有返回不在本阶段改为新的统一外层对象。
17. 命令行继续输出原有 JSON。既有捕获的记录错误和文件错误退出码为 2；依赖、核验、基线与交接的判定失败保留 1；成功保留 0。ready 含阻塞任务不自动变成命令失败。模块调用原本抛出的错误不统一吞掉或替换为空集合。
18. 正文头部、小节、字段分隔、空值及未知内容按原规则处理；本地与 GitHub 的共同字段和核心核验共享实现。GitHub 标签覆盖、分流冲突、关闭原因和 PR 排除规则保留；缺身份与畸形任务继续可被核验发现。
19. R1 的旧输入为两次任务响应对同一任务给出不同依赖，旧结果会混用它们。新结果只使用本次唯一获取的任务集合；第二个预备响应不被本次消费。下一次顶层调用必须能读取变化后的依赖并更新最终分类。
20. 第一阶段不改变用户数据或持久化格式。本地 adapter 继续只读；GitHub 抓取保留现有缓存写入约定。写入前的权限和 CONFIG 重读独立保留，读取结果不充当授权凭证。

### 后续阶段的职责调整

21. 验收判据 module 接收实际事件并判断资源、动作、执行命令和结果归属。Shell adapter 和 Python 测试使用同一 seam；保留现有判定结果与支持范围，移除正则截取源码和每例拼接 Shell 的测试专有复杂度。
22. 测试按行为主题组织，重复准备代码改为具名案例数据；原案例、反例身份、正向对照和已接受限制有逐项映射。保留少量实际脚本接入检查，避免只验证孤立判据。
23. 验收客户端 module 共用通信、请求响应归属、等待与进程生命周期。十八个场景的身份、参数、事件筛选和中断差异保留；五个现有行为族通过回放验证，不强制统一成同一种策略。
24. 客户端增量处理新事件，同一输入记录解码一次后供消费者使用；普通完成、失败、超时、绝对和相对中断阈值、退出码及子进程结束语义保持。重复的 GitHub 替身共用实现。
25. 工作结果发布恢复 module 集中发布事实、回读收养、待补索引、请求归属和草稿恢复。在线调用与重放继续使用同一恢复事实，保留未发布、结果未知、部分成功与完成的区别。
26. 完整请求身份、损坏登记披露、旧布局兼容迁移与逐请求清除语义保留。不同远端动作的可重复执行条件保持区别，不建立覆盖所有写操作的通用自动重试框架。
27. 受控写入内部整理策略解释、执行登记、本地字节事务和远端结果表达，但完整操作仍封装在现有 interface 后。最终身份与权限重读、持锁、执行及审计顺序保持。
28. 锁前预检和锁内重新校验具有不同用途，不能为了减少读取删除后者。网络期间锁的语义、路径保护、占用、回滚和已发生远端结果的披露不在本次重构中放宽。
29. 业务 Skill 保留显式选择、输入输出和专业差异；共同执行规则、受控写入协议和结果字段各有权威维护位置。精简产品元数据中的实现历程，但不删除来源、许可证或固定上游内容。

### 量化与交付约束

30. 新整理生产文件通常为 200–400 行；超过 500 行复查职责，超过 600 行须记录完整不变量无法合理拆分的理由及验证方式。函数通常为 20–60 行，超过 80 行复查职责，完整事务允许有明确理由的例外。
31. 测试按主题组织，单文件尽量不超过 500 行；顶层验收运行脚本目标不超过 300 行。旧大文件随所属阶段处理，第一阶段不为全仓达标修改无关内容。
32. 行数以相同范围的物理行统计，包含空行和注释；拆文件不算净减量。禁止以压缩排版、转移到数据文件或删除必要兼容与验证逻辑伪造收益。生产代码不设未经论证的总量下降百分比。
33. 第一阶段合成正常 ready 的目标是 CONFIG 原文 6→1 次、任务集合 2→1 次。客户端共享化净减约 3,000–3,500 行是规划估计，须扣除新增共享实现与适配后实测；事件一次解码是可验收目标，不预报端到端加速倍数。
34. 沿用当前依赖工具链；每个成果记录行为验证、结构变化、行数和操作量。产品内容变化后核对来源指纹、交付清单与可复现构建；回退使用前一阶段匹配的代码和包，第一阶段不要求用户数据迁移。

## Testing Decisions

### 测试 seam 与判断标准

测试 seam 沿用已共同确认的总方案和第一阶段设计，本次规格整理没有增加新的使用取舍。

| 被测 module | 优先经过的最高可用 seam | 替身或补充检查 | 既有测试先例 |
| --- | --- | --- | --- |
| 原子任务查询 | 现有公开读取函数；少量命令行真入口检查 | 临时本地项目、注入的 GitHub transport；计数实际读取与请求 | 本地记录检查、GitHub 后端检查、双后端畸形任务一致性、离线元信息与命令行检查 |
| 验收判据 | 运行脚本和测试共同调用的证据判定 interface | 已保存或合成的事件回放；保留实际 Shell 接入检查 | 工具拒绝与 curl 直连判据的历史正反例、留存事件流回放 |
| 验收客户端 | 场景使用的客户端操作 interface | 受控进程或事件回放 adapter；验证输入、输出、退出与生命周期 | 普通执行、受控中断、相对阈值和场景事件筛选 |
| 工作结果发布恢复 | 现有结果追加 interface，必要时经受控远端操作验证整条调用 | 故障注入 transport、临时恢复登记；检查实际写入次数和最终状态 | 超时收养、partial 重试、碰撞共存、损坏披露、旧布局迁移与清除归属 |
| 受控写入 | 现有完整受控操作 interface | 隔离文件树、并发执行和故障注入 | 实例及 CONFIG 在途撤销、路径竞态、资源占用、审计失败和回滚 |
| 业务 Skill 与交付包 | 显式入口、实际专业结果及包加载入口 | 引用与来源校验；后续按权限进行真实入口对照 | 显式触发检查、专业成果核验、包完整性和字节可复现检查 |

测试优先判断调用方能观察到的结果、错误、来源信息、文件字节、远端操作次数和进程状态。操作量是本次效率合同的一部分，可以计数底层实际读取，但不能只断言某个私有助手调用一次而忽略最终行为。

使用相同输入比较稳定字段；时间戳等非确定字段核验格式、来源和对应关系，不要求两个运行逐字节相同。用可识别的反例和正向对照证明检查能发现目标回归；必要的因果变异在隔离副本中运行。

结构验收补充核对依赖方向、实际代码量和文件职责，行为测试不绑定源码中的特定函数声明或 Shell 排版。减少测试代码时保留被验证行为和案例身份；测试通过不自动证明真实宿主、远端或人工体验已验收。

### 第一阶段验收矩阵

| ID | 场景 | 必须观察到 |
| --- | --- | --- |
| READ-01 | 多份本地任务和依赖的正常 ready | CONFIG 原文一次、每份任务正文一次；静态输入下最终分类保持 |
| READ-02 | GitHub 正常 ready | 全量任务集合一次；依赖与任务判断使用同一集合 |
| READ-03 | 预备的第二响应改变依赖 | 本次调用不消费第二响应；最终结果没有两个时点混合 |
| READ-04 | 两次顶层调用之间改变配置、任务或基线 | 第二次读到新内容；不存在跨调用复用旧状态 |
| READ-05 | 远端不可用，有缓存、无缓存及在线转离线 | 来源、时间与缓存标识保持；无缓存明确失败；不回退本地 |
| READ-06 | 本地目录与正文身份的顺序相反，远端返回非身份顺序 | 各入口原排序分别保持；排序副本或离线标记不污染其他结果 |
| READ-07 | 本地目录名与正文身份不一致，以及任务缺失 | show 仍按目录定位且不扫描无关任务；错误和退出码保持 |
| READ-08 | 同正文经双后端读取，包含空字段、未知小节、畸形任务 | 共通字段与核心核验一致；后端专有信息及标签覆盖规则保留 |
| READ-09 | 各读取命令的成功、阻塞和失败 | JSON 类型、字段、原因和退出码兼容；实际脚本入口可用 |
| READ-10 | 两种导入顺序及脚本运行触发 GitHub 记录错误 | 单一错误继承关系；现有捕获分支有效；无新增未捕获 traceback |
| READ-11 | GitHub show、verify 与本地结果核验 | 必要的详情、评论、标签或结果文件读取实际发生；失败和未核对表达保持 |
| READ-12 | CONFIG 在途撤销、实例撤销和审计故障 | 受控写入的锁内重读、拒绝和原故障处理保持 |
| READ-13 | 后端迁移计划和交接读取 | 源任务、映射、引用与权限要求保持；替身验证不产生真实远端写入 |
| READ-14 | 内部 module 重组后的完整入口与交付 | 脚本、MCP 引用、公开导入、来源指纹和匹配交付包检查通过；无开发机位置依赖 |

先保留现有后端行为基线，再沿单次 ready 读取闭环、共同规则归属、其他读取入口接入逐步验证。错误身份兼容通过后，才移除现有依赖循环所需的临时身份补偿。R1 必须同时验证本次正确结果、一次获取及下一次调用刷新。

### 后续阶段的必要验收

| 阶段 | 检查集合 | 通过条件 |
| --- | --- | --- |
| 2 判据与测试 | 真实事件与示例文本区分；资源身份和动作匹配；命令归属；保守拒绝范围；历史反例和真对照；实际 Shell 接入 | 原判据结论与已接受限制逐项保持；同一 interface 可从运行与测试使用；不再提取源码 |
| 3 客户端 | 五族行为；普通完成、失败与超时；事件筛选；绝对及相对中断；退出码；子进程结束；增量消费与共享替身 | 场景结果兼容；同一输入一次解码；十八个入口实际引用共享实现；净增减计数可复查 |
| 4 发布恢复 | 读前回查；超时收养；已发布待补索引；碰撞双请求；损坏登记；旧布局迁移；清除归属；在线与重放结果一致 | 发布次数和返回事实符合原恢复合同；无重复发布或他人登记误删；必要兼容分支保留 |
| 5 受控写入 | 完整授权交集；实例及配置在途撤销；路径和换链；同资源竞争；审计故障；本地回滚；远端已发生结果 | 原锁内检查和实际写入语义保持；调用方不需拼装授权与提交步骤 |
| 6 Skill 与交付 | 共同规则的直接可达引用；专业输入输出；显式触发；来源与许可证；完整包加载及重建 | 文本减量不丢规则；固定方法与模板依赖完整；实际执行与包检查有证据，未验证项明确列出 |

上述检查复用现有五套后端、运行保障和包检查的相关行为；整理测试入口后要能追溯原覆盖。修改范围涉及的检查通过后，只有新改动、失败或未解决的具体疑点才扩大或重复验证。

确定性验证使用项目专用临时目录、隔离副本和注入替身。生产内容变化时，在隔离副本核对来源指纹、交付清单与字节可复现性；直接使用旧包不能证明新代码可交付。

真实模型轮、真实远端写入、日常安装替换和人工体验分别保留对应的运行条件与授权要求。应运行的真实检查未完成时记录实际限制，不将离线回放、文案检查或历史通过结果当作本次完整验收。

## Out of Scope

- 新业务能力、新任务后端、新用户命令、统一改变所有公开 JSON 结构，或改变十四个业务入口的职责与调用方式。
- 用户任务、协作配置、缓存和恢复登记的新持久化格式，以及为内部重构而要求用户迁移数据。
- 跨调用常驻缓存、后台同步、严格跨文件或远端事务快照，以及新增分页或并发能力。
- 放宽授权交集、移除锁内重读、改变网络期间持锁语义或弱化路径、占用、审计和撤销保障。
- 删除旧恢复兼容、损坏哨兵、原始证据、固定上游方法或许可证来降低代码量。
- 以改写产品核心基线、取消验收要求或缩减历史反例掩盖回归。
- 尚未测得的整体提速倍数、强制生产代码下降比例，以及把规划估计当作验收事实。
- 本次规格发布不执行产品或测试实现，不创建实施子工单，不进行 Git 提交、推送、标签、真实远端写入、安装或发布。
