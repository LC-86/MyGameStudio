## 阶段安排

| 阶段 | 用户可见结果 | 核心调整 | 退出条件 |
| --- | --- | --- | --- |
| 0 固定基线 | 后续能说明什么变好、什么保持 | 固定行为案例、现有输出与操作计数；区分运行时、测试、验收与交付材料 | 基线可复跑，已知限制与行为修正有明确登记 |
| 1 原子任务读取统一 | 一次查询不再混合两次任务读取，现有调用照常使用 | 同调用复用配置与任务；共享正文与核验规则；消除读取相关双向依赖 | [第一阶段验收设计](task-reading.md)成立；两后端、CLI、来源信息与兼容调用有结果 |
| 2 验收判据与测试组织 | 判据可离线验证，失败能定位到具体规则 | 事件判据从 Shell heredoc 移入独立 module；按行为拆测试，保留具名反例 | 全部既有正反例映射保留；真实脚本接入同一判据；测试无需正则抽取源码 |
| 3 验收客户端去重 | 修改一次客户端能覆盖所有场景，轮询不反复解析旧事件 | 18 份客户端共享 implementation，保留五族真实差异；共用 GitHub 替身 | 五族回放一致；中断、事件选择、退出码与子进程生命周期保留；净行数和解码次数复测 |
| 4 工作结果发布恢复 | 重试、部分成功与恢复状态继续可靠，修改集中 | 收拢评论发布、回读收养、pending-index 归属与草稿恢复；缩小 GitHub 大文件 | 身份碰撞、损坏登记、旧布局迁移、已发布待补索引与重复调用的完整生命周期通过 |
| 5 受控写入内部整理 | 权限拒绝与实际写入行为保持，故障更容易定位 | 策略、执行登记、本地事务及远端结果各有明确职责；完整受控操作保持封装 | 锁内撤销、换链、占用、审计失败和回滚语义保持；不得以减少重读替代撤销保障 |
| 6 业务 Skill 与包内说明 | 共同规则只维护一处，专业入口更简洁 | 共同约定、受控写入协议与结果模板各有权威位置；专业入口保留差异 | 引用闭包、来源指纹、显式调用及专业结果语义通过；实际执行效果有对照 |

顺序理由：阶段 1 有可复现的正确性与操作量收益；阶段 2、3 改善后续重构的验证与维护成本；阶段 4、5 涉及恢复和权限，后置；阶段 6 涉及模型执行语义，不能只靠文本缩短判断完成。

阶段 2、3 的调查可提前进行。实施时一次处理一个可验收成果；阶段 4、5 依赖阶段 0 的行为基线与阶段 2 的判据稳定性。共享文件改动保持单一修改者。每阶段通过后再继续相关下游，失败先修复本阶段回归。

当前只把阶段 1 细化到职责和验收层面。后续阶段进入实施准备时，再补充其内部设计与行为对应关系，不提前造通用框架或一次性展开全部实现细节。

## 衡量方式

| 维度 | 已观察基线 | 完成判断 |
| --- | --- | --- |
| 生产代码量 | 5 个 Python 文件共 4,526 物理行；最大 1,848 行 | 以相同范围比较净增减；单纯拆文件不算净减量；不强制以删除必要行为换总量下降 |
| 生产文件长度 | 1,848 / 1,119 / 1,109 / 261 / 189 行 | 新整理文件通常 200–400 行；超过 500 行复查职责；超过 600 行需写明无法拆开的完整不变量及验证方式 |
| 函数长度 | 现有 CLI 223 行、结果追加 185 行、远端操作 180 行 | 通常 20–60 行；超过 80 行复查职责；完整事务可有明确理由的例外 |
| 测试与验收 | 测试 9,086 行、验收代码 20,739 行；最大测试函数 1,499 行 | 测试按行为主题组织，文件尽量不超过 500 行；案例与反例不丢失；顶层运行脚本目标不超过 300 行 |
| 可复制代码减量 | 客户端 18 份共 4,605 行，归一化名称后为五个行为族 | 共享化净减 3,000–3,500 行为估计，最终扣除新增 module 与入口适配后复算 |
| 任务读取效率 | 合成 ready：CONFIG 6 次，任务读取 2 次 | 同调用 CONFIG 内容一次、任务集合获取一次；下一调用重新读取；额外标签/评论核验按原用途保留 |
| 客户端解析效率 | 1,000 条固定事件、10 次轮询产生 21,000 次 JSON 解析 | 共享客户端的消费链每条输入记录一次解码；超时与中断结果兼容；测操作量与耗时，不预报端到端倍数 |
| locality 与 depth | 规则分散、源码形状测试、跨文件私有调用 | 调用方通过较小 interface 驱动完整职责；维护同一规则时不需同步修改多份 implementation |

行数统计含空行和注释，不用压缩排版、一行巨型表达式或移动到数据文件伪造减量。既有大文件随对应阶段逐步消化；第一阶段不为全仓达标去拆无关文件。

## 全程保持的行为

- 原子任务身份、分流与进度、基线引用、结果及证据之间的含义保持；可开工集合不是写入授权。
- 本地 Markdown 与 GitHub 是两个真实 adapter；shared module 只吸收共同行为，各自的结果读取、排序及离线语义保留。
- 受控写入的最终身份与权限检查留在同一锁内；撤销完成后的旧请求不得继续写入。
- 远端结果不确定时先回读；部分成功与未发布区分；旧恢复登记和碰撞归属检查保留。
- 原始证据、许可证、固定上游方法、历史记录与当前产品代码分开看待；不把历史材料体积当成运行效率问题。
- 本轮不增加后端、持久化存储、跨调用缓存、并发写入策略或新的用户命令。发现相关需求时另列范围，不混入纯重构。

## 验证与回退设计

每个实施成果先用现有可观察 interface 固定行为，再用最小改动通过反例和正向检查；结构迁移不能以“旧测试依赖源码”作为删除行为覆盖的理由。少量真实入口检查保留，用来证明调用链实际接入新 module。

确定性检查在项目专用临时目录或隔离副本运行；保留与本次改动有关的五套现有检查覆盖和精确输出。需要更改 `plugin/` 时，在隔离副本核对 provenance、打包清单和可复现构建，避免旧交付物与新代码混用。

真实模型轮、真实远端写入、日常客户端替换与发布是单独的验收或交付动作，实施准备时列出目标、成本、影响和具体内容。当前设计不替代这些动作的授权和结果。

阶段 1 不迁移用户数据。回退时恢复该阶段之前的代码及匹配交付包；其他阶段沿同样原则先说明是否触及持久化格式。每票的提交、推送和发布继续按各自明确授权执行。
