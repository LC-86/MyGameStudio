# 06：把功能想法形成当前可执行规格

**What to build:** Game-Design 组织当前问题的讨论，Game-Spec 将真实采纳的决定更新为本轮产品规格；制作人员能找到规则、边界、验收标准与依据版本。

**Blocked by:** [04：初始化一个使用本地任务记录的新项目](04-initialize-local-project.md)

**Status:** ready-for-agent

## 验收标准

- [ ] 用一个局部功能和一个多项未决问题的样例分别验证质询及决策地图分支；内部方法按问题需要加载，不额外暴露公共通用入口。
- [ ] 区分研究事实、助手建议、候选方案与用户实际决定；独立事实调查结果可追溯，未决项说明对当前工作的影响。
- [ ] 已采纳内容形成当前行为规则、边界情况、系统关系、范围与完成标准，引用项目目标、必要技术约定和验证材料；不强制完整游戏长文档。
- [ ] 只有对应设计实例修改产品基线；涉及目标或范围变化时输出明确的统筹同步交接，不能静默修改项目目标。
- [ ] 基线实质变化具有可识别版本及采纳依据，候选和被替代内容保留过程记录；格式修改不会被当作新产品要求。
- [ ] 交付的规格与交接能由未参与讨论的执行者读取，未实现内容不被报告为实际功能；本票可用明确的历史决定样例验收，不模拟人作决定。

## 实施依据

开始时读取[实施范围与验收约定](../spec.md)，再按本票分支读取[设计技能合同](../../mygamestudio-framework/contracts/design.md)、[业务 Skill 共同合同](../../mygamestudio-framework/contracts/common.md)、[工作记录与任务后端合同](../../mygamestudio-framework/contracts/records.md)。具体工程位置在实施时从当前项目读取。
