# 项目接入与初始化流程

状态：接入策略、清单确认、恢复与重复运行规则已由用户在 Q32–Q34 确认。

## 入口与依据

用户显式调用 Game-Init，或由已显式调用的 Game-Producer 按明确的接入请求委派。先明确目标项目及当前请求，按新项目或已有项目选择路径。文档组织读取[项目目录模板](project-layout.md)，能力与运行保障读取[能力衔接决定](../issues/05-capability-adaptation.md)。

制作统筹组织接入，专业文档由相应角色维护。文档写入使用 writing-for-agents。

## 项目协作配置

读取已有 tracker、标签与领域文档约定；按[协作配置合同](../contracts/project-configuration.md)确定实际任务后端及位置、五类标签映射、当前文档和术语/ADR 的权威位置。这承接 setup-matt-pocock-skills 对应的初始化能力，保持同一个 Game-Init 入口。

首版任务后端为本地 Markdown 与 GitHub Issues，已有有效选择优先沿用；新个人项目无既定方式时建议本地 Markdown。核心设计文档默认 Markdown，其位置独立于任务后端。配置选择、拟写草稿及外部动作纳入下方具体清单；完成条件是后续 Skill 能从同一配置找到当前资料和任务。

## 新项目

依据已明确的目标、规模、投入与技术条件，形成协作配置和当前所需资料的具体清单，确认后按角色建立；有内容时再创建相应文档。尚未选择的引擎、平台或未确定的设计保持待定。

完成条件：当前项目目标和资料入口可定位，已有决定有出处，后续工作能从当前状态开始。

## 已有项目

### 1. 分析现状

对原项目只读，覆盖项目结构、主要功能和资源、现有文档、工程配置、已有验证与进度记录。对照已实现行为、文档要求与开发者当前目标，定位有效资料、缺失内容、矛盾及未验证部分。分析报告及拟议变更先作为本次任务产物保存，应用后归档到项目。

完成条件：每项拟复用或补齐的关键内容有依据，原项目保持未修改；不能查明的事实和需要开发者决定的事项明确列出。

### 2. 形成接入清单

先复用有效资料，通过 INDEX.md 等入口记录实际路径和维护责任。按模板补齐缺失内容，针对冲突、过时或职责混杂的资料提出必要的整理方案。

清单列出目标位置、复用项、拟新增或修改项及理由。涉及运行保障的客户端配置、权限或 hooks 信任时，单独说明具体动作和授权范围。

完成条件：用户能够判断哪些内容会改变、哪些资料将作为当前依据，以及仍有哪些未决问题，并确认本次具体写入清单。同一范围内无需逐文件重复确认。

### 3. 应用与核对

在当前授权范围内组织对应角色写入，保留已有资料及其可追溯关系。核对入口、引用、模板内容与实际项目是否一致；代码观察不能直接变成未经确认的产品目标。

完成条件：已执行事项与清单一致，完成项有实际结果，未完成项和能力缺口可定位。文档接入完成与运行保障已经启用分别记录。

## 中断与重复运行

保留已经完成的有效结果和剩余事项。恢复时核对实际文件、原清单和用户后来的修改，按仍适用的范围补齐；影响写入的新变化重新列出受影响清单。

再次接入无缺口时报告无需改动。模板升级先提出对应变更建议，确认后应用，保留已有项目内容。

完成条件：已做与待做事项可区分；恢复依据当前事实；重复执行不会制造重复资料或覆盖用户后续修改。
