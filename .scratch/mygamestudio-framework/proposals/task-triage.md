## 五类分流状态

| 状态 | 游戏项目中的用途 |
| --- | --- |
| needs-triage | 新想法、问题或受目标变更影响的旧任务，等待核对当前目标并决定如何处理 |
| needs-info | 当前输入不足以确定下一步；列出已知事实和具体缺失信息，能从项目查明的部分先自行调查 |
| ready-for-agent | 已有明确工作说明，可以交给 Agent 承接；实际开工还需核对基线、依赖、能力和授权 |
| ready-for-human | 下一步工作确实需要人参与，例如试玩判断、设计取舍或 Agent 无法代做的操作；提供明确请求与回传要求 |
| wontfix | 本请求不再安排执行，保留原因和相关决定；也可用于已有成果已覆盖、无需重复实现的请求 |

保留上述标签名称。每项经过分流的请求使用一个当前分流状态，具体标签字符串可由实际 tracker 映射。

## 与执行、验收和进度的关系

五类标签回答当前请求如何分流。任务记录还需明确执行责任、验收方式、实际进度和依赖；这些是任务字段或记录，不必都扩展成标签。

例如 Agent 制作战斗原型、开发者判断手感：制作工作可以由 Agent 开始；产物交付后记录待人工验收。分流调整不能抹掉已经由 Agent 执行的事实，也不能把需要人工判断误写成 Agent 无法开展制作。

需要人参与时，要指出具体是哪一步以及需要回传什么。只有缺乏信息时使用 needs-info；依赖尚未完成和本轮暂缓分别在依赖、计划或进度中表达。wontfix 不替代这些状态，也不作为本轮工作已完成的证明。

## 维护责任与变化

统筹组织分流，按当前授权与决定权维护管理记录；专业执行者提供分析和工作事实。重要方向、范围和投入取舍由开发者决定。

已有任务因目标变化而失去执行依据时，受影响任务回到 needs-triage，完成影响核对后再分流。新信息补齐后，也先核对是否足以继续。保留历史状态与对应依据，不改写旧版本下的执行事实。

实际开工仍以当前基线、依赖、输入、能力和授权为依据，ready 标签本身不授予额外操作权限。

## 适配原始 triage 流程

保留先调查、再分流、补充可执行说明和保存已决问题的做法。原流程面向工单和外部 PR 的默认评论、关闭及拒绝知识库写入，应映射到本项目已定的目录与授权。

小项目按必要性收集信息和验证。清楚的日常任务按已有授权推进；尚未决定的实质取舍交给开发者，不为每次标签变化增加固定审批仪式。
