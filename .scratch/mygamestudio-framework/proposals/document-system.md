# 项目文档体系

状态：文档组织、模板策略、基线版本、任务分流、人机责任及并行修改原则已确认。具体字段与运行设计已在合同中补齐。

用途：供[项目记录、角色交接与跨会话恢复](../issues/04-project-handoffs.md)讨论。适用对象是未来使用 MyGameStudio 的游戏项目，不是要求当前插件仓库立即按此重组。

## 术语假设

本草案暂把 GRD 理解为游戏需求文档，把 TDD 理解为技术设计文档。用户尚未给出缩写全称；不把这一解释写入正式术语表，也不混同测试驱动开发。

## 核心思路

核心基线指当前已采纳、仍适用、用于指导工作和判断结果的目标、需求、设计与技术约束。基线可以改变，但改变后要更新受影响的执行依据。文档很长、文件名带 design、修改时间最新，都不能单独证明它是当前基线。

专业工作先形成可讨论方案，必要时用原型或研究验证；得到当前授权和决定支持的内容成为执行依据。执行计划由这些依据推导；实际制作和验证产生结果与证据，再用于判断下一轮是否调整基线。这个过程按当前小目标反复进行，不要求全项目所有文档一次性完稿。

## 文档用途与维护归属

| 内容 | 用途与地位 | 维护责任 |
| --- | --- | --- |
| 项目目标、范围、投入约束 | 当前项目管理基线；说明正在实现的总体目标及边界 | 制作统筹 |
| GRD / 游戏需求 | 当前产品要求；明确玩家目标、能力需求、优先事项及不做的内容 | 方案设计；引用项目管理基线，避免重复维护全局范围 |
| 游戏设计 / 功能设计 | 当前体验与规则的具体约定；已确认的功能规格也是其作用范围内的基线 | 方案设计 |
| 技术架构 / TDD | 当前实现约束、系统结构、数据与接口约定、关键技术取舍 | 制作实现（用户已确认） |
| 迭代计划 / 原子任务 | 如何推进当前目标的可变安排，引用相关需求与设计依据；不独立改写需求 | 制作统筹维护整体安排；专业执行者提供技术拆解和本任务执行事实 |
| 调研、讨论、候选方案、原型说明 | 决策的过程材料；未经采纳的想法不自动成为实现要求 | 开展该专业工作的角色 |
| 决策记录 / ADR | 解释为什么选某方案及替代关系；已接受且仍适用的决定对对应基线形成约束 | 对应专业角色；统筹记录涉及目标、范围和项目管理的决定 |
| 试玩、测试、Review、交付记录 | 对指定成果或版本的观察与判断证据；不替代需求，也不自动证明更新后的版本仍满足要求 | 相应执行者或独立审查者 |

## 小项目如何保持轻量

建议初始按“项目约定、游戏需求与设计、技术设计”三类长期信息维护当前依据，另外维护当前任务。它们可以很短，按实际需要创建和扩展；不预建空文档，也不要求完整商业测算。

用户已确认：小项目默认合并 GRD 与游戏设计、技术架构与 TDD，必要时再拆分。合并后仍区分其中的不同用途。

建议每项信息只在一个位置维护原文，其他文档引用，避免多个文件各保存一份“当前需求”。

这里的合并只针对职责和更新方式相容的内容。不能为减少文件数让制作统筹接管专业设计，也不能让技术设计自行改写产品目标。

用户已认可原子任务围绕可交付、可检查的小成果组织，当前及近期目标细化为任务。原子计划引用需求或设计；执行步骤可调整，需求变化回到对应基线处理。Matt 方法如何组合为游戏闭环，见[游戏开发小闭环提案](game-work-loop.md)。

## 维护与恢复

用户已确认：核心文档展示当前采用的方案，讨论稿、候选方案、修改原因和被替代内容另行留存。原子计划引用核心设计；“设计已采纳”与“功能已实现”分开记录。维护方式如下。

1. 建立一个轻量入口，指向当前项目约定、适用设计、当前任务与必要记录；入口负责定位，不复制各文档正文。
2. 区分草案、当前采用和已被替代的内容，记录必要的采纳依据与替代关系。有效要求实质变化时记录新基线版本；逻辑版本与内容指纹按[记录合同](../contracts/records.md)维护。
3. 请求和结果注明所用基线版本；开始、恢复或交接工作时核对适用性，按实际影响调整相关任务和验收要求。历史结果保留原版本下的事实。
4. 专业角色维护自己的专业依据和工作记录。重要目标、范围、体验或投入取舍仍由用户决定；当前授权内的普通技术调整不要求增加一轮统一人工签字。
5. 目标变化时，统筹先检查影响并更新项目管理内容，组织相应角色更新专业基线；受影响任务标记待复核或调整。保留旧成果与已完成事实，不自动删除，也不把“按旧要求完成”直接算作“按新要求完成”。
6. 独立评审获取适用基线及实际成果，不仅依赖作者总结；证据能否沿用按改动影响判断，不全量作废或重复验证。

## 后续接口

- 开始、交接、恢复或协调并行工作时，按[交接与恢复决定](../issues/04-project-handoffs.md)核对当前依据、实际成果及修改范围。
- 技能专用字段见[业务合同](../contracts/common.md)，创建资料使用[文档模板](../templates/README.md)，版本与后端映射使用[记录合同](../contracts/records.md)；分流信息见[任务分流设计](task-triage.md)，默认布局见[项目目录模板](project-layout.md)。

默认文件名与目录见[项目目录模板](project-layout.md)。已有项目的复用与映射另由初始化流程确定。本文件记录框架设计，运行时实现与验证留给后续实施。

## 有限的一手依据

- Unity 教程从简短设计说明发展到 GDD，并通过原型、试玩和反馈修订设计：[Game Design](https://learn.unity.com/tutorial/game-design?version=6.3)。这支持渐进形成设计资料，不是统一行业文档标准。
- Microsoft 分别讨论更新当前设计文档与用 ADR 保存决定背景、结论和后果：[Design Decision Log](https://microsoft.github.io/code-with-engineering-playbook/design/design-reviews/decision-log/)。
- Microsoft 建议待办持续细化并具备验收标准：[Backlog Management](https://microsoft.github.io/code-with-engineering-playbook/agile-development/backlog-management/)。此处借鉴信息职责，不引入团队会议或固定 Sprint 制度。

完整来源范围与限制见[一手资料核对结果](../research/documentation-evidence.md)。上述来源不证明本草案是唯一或已验证最优的文档体系。
