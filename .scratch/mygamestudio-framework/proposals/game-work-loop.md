# 游戏开发小闭环

状态：小闭环已在 Q26 采用，五类分流及独立的执行、验收和进度信息已在 Q27 调研后采用。Game-* 名称已纳入确认的十四个入口，合同已补齐；技能尚未实现。

## 适用范围与依据

用户显式调用制作统筹后，由统筹在授权范围内组织本轮工作。直接调用专业 Skill 时只运行需要的环节。已有目标、设计或计划足够清楚时，从适用环节接入。

写入文档时使用 writing-for-agents。权限、直接调用后的同步和目标变化规则分别见[角色分工](../issues/02-role-responsibilities.md)与[工作流决定](../issues/03-workflow-gates.md)。需要判断原始技能能否直接调用时，读取[复用边界核对](../research/matt-workflow-fit.md)。

## 推进步骤

### 1. 明确本轮目标

统筹核对当前目标、现状和请求范围，选择需要的专业角色。局部想法用 grill-with-docs；跨多个会话的未决问题用 wayfinder 建决策地图。需要检验设计时，由方案设计制作验证原型。

完成条件：当前要解决的问题、预期成果和范围清楚；影响本轮开工的未决事项已解决，或明确交给开发者决定。未来问题可保持粗粒度。

### 2. 形成当前可执行约定（Game-Spec）

方案设计整理本轮规则、体验要求与完成标准，将已采纳内容更新到对应游戏设计。制作实现提供必要的技术可行性判断和技术设计，统筹记录项目管理方面的决定。引用当前基线版本及原型证据。

完成条件：准备执行的范围有适用设计与可检查的完成标准，候选方案和已采纳要求可区分。规格的详略服从本轮成果，不要求长篇用户故事；已有规格足够时直接引用。

### 3. 拆分与分工（Game-Plan）

相应专业角色给出任务拆解与依赖建议，统筹组织当前及近期工作。以可验证的小成果拆单；完整功能尽量形成可试玩的窄路径，资源、调研等工作以可独立核验的专业产物拆分。

每项任务分别记录执行者、验收者、依赖、基线版本、输入和完成标准。任务依赖应来自实际开工条件。计划中的重要取舍沿既定授权规则处理，当前授权内的日常拆解由统筹组织。

完成条件：每项准备开工的任务都有明确成果、执行分工、验收方式和真实依赖；尚需信息、能力或授权的任务与可执行任务区分。

### 4. 制作与验证（Game-Implement）

执行者接手时核对基线与输入。Agent 任务按类型调用实现、素材或工具技能；Human 任务提供明确输入、操作目标和回传要求，依据人实际提供的结果继续。

制作实现按任务选择验证方式：适合自动化的逻辑检查、实际运行与交互、资源导入与规格检查等。验证原型仍由方案设计在隔离位置维护。

完成条件：实际成果可定位或运行，约定检查有记录，未完成与未验证内容明确。实现失败时按原因修复或返回设计讨论；Git 提交、推送、外部工单写入及发布沿用单独授权边界。

### 5. 独立审查与人工验收（Game-Review、Game-Playtest）

按任务产物选择相应专业的独立子代理。代码保留 Standards 与 Spec 两轴审查；设计和资源采用适用专业标准与需求符合性检查。输入包含实际成果、当前要求及版本，审查范围应覆盖本次真实改动。

代码审查需覆盖本轮未提交或新建内容，具体变更捕获机制在技术设计中确定。原版 code-review 在固定 Git 比较范围确实覆盖目标时可使用；其差异审查结果不能替代运行验证和玩家体验判断。

完成条件：所有本任务要求的审查均有结果；需返修的问题已处理并复核；约定需人工验收时取得实际反馈。轻微任务的检查力度沿用已定规则。

### 6. 收束当前任务并选择下一步

专业执行者提交工作结果与证据引用。统筹核对成果和要求的匹配情况，更新任务状态与项目安排。实际发生的设计或技术约定变化，由对应角色同步基线；普通任务完成不必改写未变化的核心文档。

完成条件：状态与验证、审查及人工验收事实一致；遗留问题有明确去向；下一步依据当前目标。直接调用专业技能时，整体进度仍由统筹下一次显式介入同步。

目标或范围在任何步骤变化时，先进入已确认的影响检查与同步流程，再继续受影响工作。

## 原始技能的使用建议

| 原始技能 | 建议 |
| --- | --- |
| wayfinder | 复用决策地图方法及能力，用于有多个未决问题的较大工作；采用项目实际 tracker 与授权范围 |
| grill-with-docs | 复用质询和领域术语澄清能力；由有权维护对应专业文档的角色执行，接入实际文档落点 |
| to-spec | 为 Game-Spec 重写游戏任务的规格结构；保留归纳已有决定、范围和验证标准，按任务提供体验规则、原型证据及基线引用 |
| to-tickets | 为 Game-Plan 适配成果类型、Agent / Human 分工和项目目录；保留小成果、独立验证与真实依赖 |
| implement | 为 Game-Implement 重写多产物执行与验证协议；移除自动提交等越过已定授权的默认步骤 |
| code-review | 在代码审查分支条件满足时复用；Game-Review 另处理设计、素材、实际运行证据与人工验收，确保包含真实待审改动 |

上表区分能力复用与完整技能协议照用。复用时需满足当前角色写入范围、文档落点、工具条件和调用规则；不直接复制原始技能的全部副作用。

## 执行者与验收者

选择分流标签或设计任务字段时，先读取[任务分流设计](task-triage.md)及其一手依据；以下示例说明两类责任的区别。

分别记录谁执行、谁验收，并另记任务状态：

- Agent 执行、Agent 验收：可用明确检查与独立审查核验的技术或资源工作。
- Agent 执行、Human 验收：Agent 实现或制作成果，由开发者判断体验、手感或审美是否达到约定。
- Human 执行：确需人的试玩、判断或工具操作；验收方式按任务目的明确。

本仓库词表简写为人执行；完整 Matt triage 还涵盖设计判断、手工测试等需要人参与的工作。分流、执行与验收的具体语义以已采用的任务分流设计为准。Agent 可执行的任务先完成制作，再等待需要的人工判断。
