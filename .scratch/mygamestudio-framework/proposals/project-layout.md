# 项目目录模板

状态：默认布局已由用户在 Q22 确认采用，基线版本关联已在 Q23 确认。已有项目映射、协作配置与记录合同已补齐，用于未来游戏项目。

## 默认布局

```text
游戏项目/
└── docs/
    └── mygamestudio/
        ├── INDEX.md          # 当前资料和任务的定位入口
        ├── CONFIG.md         # 协作配置；已有配置可直接映射复用
        ├── PROJECT.md        # 当前目标、范围与投入约束
        ├── GAME_DESIGN.md    # 游戏需求与设计
        ├── TECH_DESIGN.md    # 技术架构与技术设计
        ├── CONTEXT.md        # 按需维护术语；已有术语表优先复用
        ├── work/            # 本地任务后端的请求和结果；远端模式仅按需存草稿/证据引用
        ├── records/         # 调研、讨论、决策及被替代方案的记录
        └── evidence/        # 试玩、测试、Review 等验证材料或引用
```

各类资料首次有内容时建立。内容增长后，在对应区域拆分文件或子目录。

## 入口与维护责任

INDEX.md 以带读取条件的引用定位当前资料和任务。各项内容只在其维护位置保存正文。

| 读取情形 | 资料位置 | 维护责任 |
| --- | --- | --- |
| 查任务后端、标签、领域资料和文档位置 | CONFIG.md 或已有配置入口 | 制作统筹维护配置与映射 |
| 接入、恢复工作或检查目标与范围变化 | PROJECT.md | 制作统筹维护当前项目约定 |
| 确定玩法、体验规则或功能验收要求 | GAME_DESIGN.md | 方案设计维护游戏需求与设计 |
| 制定技术方案、实现功能或分析工程限制 | TECH_DESIGN.md | 制作实现维护架构与技术设计 |
| 接手任务、记录交付或同步进度 | work/ | 统筹维护整体安排；专业执行者记录工作事实 |
| 追溯决定原因或比较候选方案 | records/ | 对应角色保存调研、讨论、决定和历史 |
| 核对试玩、测试或独立审查结果 | evidence/ | 执行者或审查者保存证据或引用 |
| 统一项目术语或追溯技术取舍 | CONTEXT.md、records/ 或已有领域文档位置 | 对应专业角色维护术语与决定 |

核心文档保存已采纳的当前内容；records/ 保留决策背景和替代关系。work/ 引用适用基线，并使用工作请求、工作结果模板。evidence/ 关联对应任务和成果；已有大型资源与构建使用引用。

拆出的功能或系统设计沿用原维护角色。work/ 中请求和结果的维护责任按[记录合同](../contracts/records.md)执行；混合职责文档通过[运行保障](../contracts/runtime.md)中的受控修改或拆分处理。

## 与代码、资源及已有项目的关系

源代码、游戏资源、构建产物和验证原型继续按实际引擎或工具约定组织；这份通用模板只规定管理资料的逻辑位置，并通过引用连接专业产物。

已有项目的资料先分析后接入，按[项目接入、深度分析与初始化](../issues/08-project-onboarding.md)复用有效路径并建立映射，缺口及必要整理进入具体清单。目录模板不强制移动或覆盖已有文件。

模板资产由插件提供，实例化后的项目资料由项目维护；模板升级按[初始化流程](project-onboarding.md)先列出具体变更，再按确认范围应用。

## 具体合同与模板

- 选择本地 Markdown 或 GitHub Issues、复用既有配置时读取[协作配置](../contracts/project-configuration.md)。核心文档的位置与任务后端分别确定。
- 读写任务、结果、版本和历史时读取[记录合同](../contracts/records.md)。
- 创建或补齐实际文档时从[模板入口](../templates/README.md)选择当前需要的文件。
