# 第一版业务 Skill 清单

状态：十四个业务入口及拆分已由用户确认，具体合同已补齐；本文件不表示已创建可安装技能。

## 使用方式

日常从 Game-Producer 显式进入，也可直接调用任一业务 Skill。所有入口按当前请求与授权执行；已有资料通过版本引用传递。

下面按默认职责分组，不增加常设角色。共同能力可以在允许范围内复用，调用 Skill 本身不改变角色的写入权限。例如验证原型中的编码仍受方案设计的原型范围约束。

## 业务入口

| 默认职责 | 业务入口 | 处理的工作 | 核心交付 |
| --- | --- | --- | --- |
| 制作统筹 | Game-Producer | 接收需求，校准当前目标，组织角色与技能，处理目标变化和反馈 | 当前工作安排、决策事项、结果汇总与管理记录 |
| 制作统筹 | Game-Init | 配置任务后端、标签和文档位置；新项目接入、已有项目分析与补齐 | 协作配置、现状分析、接入清单、资料入口与初始化结果 |
| 制作统筹 | Game-Plan | 将当前可执行约定拆成小任务，分流并明确依赖与人机责任 | 关联基线版本的任务及安排 |
| 制作统筹 | Game-Status | 检查实际进度、阻塞与待人事项，恢复上下文，按授权同步管理记录 | 当前状态、缺口和接续位置 |
| 方案设计 | Game-Design | 讨论玩法、规则、系统、数值、关卡、叙事、交互与视听方向；按需处理市场、发行及运营方案 | 候选方案、取舍与需要验证的问题 |
| 方案设计 | Game-Spec | 将已讨论并采纳的产品决定整理为当前设计和本轮可执行规格 | 游戏设计更新、明确规则、完成标准和依据引用 |
| 方案设计 | Game-Prototype | 为明确设计问题制作隔离原型并检验 | 原型、运行或查看方式、验证结论及未决事项 |
| 制作实现 | Game-Implement | 组织当前制作任务的专业工作、集成和必要验证；不接管整个项目计划 | 可交付成果、技术设计变化与验证记录 |
| 制作实现 | Game-Code | 当前任务所需的技术方案、代码实现与代码级验证 | 技术设计、代码及检查结果 |
| 制作实现 | Game-Art | 当前目标所需的视觉资源，例如图像、模型、动画和特效 | 符合本轮要求的资源及使用、验证信息 |
| 制作实现 | Game-Audio | 当前目标所需的音乐、音效或语音制作、编辑及资源准备 | 音频资源、接入信息及验证记录 |
| 制作实现 | Game-Build | 按项目实际工具构建、运行、导出或准备发布成果 | 构建或导出结果、运行入口、检查结果与缺口 |
| 相应专业角色的执行实例 | Game-Review | 按产物类型独立检查规范与需求符合性，核对实际待审范围 | 独立审查结果、问题与证据、覆盖范围 |
| 相应专业角色的执行实例 | Game-Playtest | 制定并执行可用的试玩检查，组织需要人的试玩与反馈 | 针对具体版本和场景的操作、观察、证据及反馈 |

## 边界

- Game-Producer 控制项目目标和整体安排；Game-Implement 组织已分配制作任务的内部工作。小任务可以直接调用专业 Skill。
- Game-Design 处理尚需讨论或验证的方案；Game-Spec 整理已采纳的决定，技术设计由制作实现维护并被引用。
- Game-Review 检查成果是否符合约定；Game-Playtest 获取实际运行和试玩证据。两者按任务需要组合，人工体验判断仍依据实际反馈。
- Game-Status 的检查可以只读；管理记录写入按当前请求及授权执行。Game-Build 不因构建完成自动取得上传或发布授权。
- 专业能力按项目条件执行。缺少生成、编辑或验证工具时，说明缺口并提供可接手的材料；只有实际产出的成果才记为完成。

## 通用能力与内部复用

按[依赖分发方案](dependency-policy.md)提供基本工作流所需的固定版本及资源。基础内部方法及配套引用已由[依赖闭包研究](../research/bundled-dependency-closure.md)核对；最终分发按[包合同](../contracts/package.md)记录实际采用版本、改写和许可。

to-spec、to-tickets、implement 的游戏侧协议已决定重新设计；code-review 的双轴方法用于 Game-Review 的代码分支，并确保实际改动范围被覆盖。原始源文件与本项目改动保留可追溯记录。

通用能力作为固定版本的内部依赖，由业务流程明确加载；对外主要提供上方十四个业务入口，不额外注册一套同名通用入口。此方式已由用户在 Q36 确认。
