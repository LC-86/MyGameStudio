## Question

新建游戏项目与接手已有项目分别如何接入 MyGameStudio？已有项目的深度分析需要覆盖哪些内容、怎样形成可信的现状与缺口判断？如何根据文档和目录模板建立或补齐项目结构，识别可复用资料、矛盾内容和待确认事项，并明确初始化的角色分工、修改范围、验证及重复运行行为？

## Comments

### 2026-09-07 — 用户明确要求

用户要求插件提供各种项目文档模板和目录结构模板，并具备新建项目或接手项目时的初始化能力；已有项目须先深度分析，再进行初始化和文档、目录补齐。

模板内容及目标目录结构由[项目记录、角色交接与跨会话恢复](04-project-handoffs.md)确定，本票决定如何将它们应用于真实项目。沿用既定的显式调用与三角色职责，不因打开一个项目就自动触发初始化，也不因有初始化技能而默认新增角色。

### 待讨论的执行原则（助手建议，尚未确认）

- 新项目结合已明确的目标、规模、投入和技术条件选择适用模板，只建立当前需要的结构与内容。
- 已有项目先检查代码、资源、现有文档、工程与运行依据、当前进度及明显不一致，形成现状和缺口分析；资料中实际实现、历史意图和用户已认可的当前需求需要区分。
- 优先复用已有有效资料，讨论是保留现有结构并建立映射，还是确需整理；不能把已有项目视为空目录套用模板。
- 初始化形成清楚的补齐范围、保留或映射关系及结果记录；补写只依据可追溯资料，不把推测当作已确认需求。具体修改确认、回退和验收方式仍需决定。
- 本票当前只设计接入流程，不执行实际项目初始化，不迁移或覆盖用户现有项目。

### 下一轮：已有项目的结构接入（助手建议，待用户确认）

建议已有项目先深度分析，再优先复用有效文档和现有目录，通过管理入口记录实际位置；缺失内容按模板补齐。只有现有资料相互冲突、已过时或职责混杂，无法清楚维护时，才提出必要的整理方案。

例如已有 docs/GDD.md 是有效游戏设计，入口可直接指向它，避免再创建一份内容相同的 GAME_DESIGN.md。统一的是文档用途、维护责任和读取方式，已有项目不必先搬到新项目默认布局才能接入。

需用户确认这一默认策略。后续再明确分析报告、具体变更计划、写入确认及再次初始化的行为；本轮仍不对真实游戏项目做初始化。

### 2026-09-07 — 已有项目优先复用与映射（用户已确认）

用户对 Q32 回答“认可”：新项目采用默认目录，已有项目先深度分析，优先保留有效文档和原有结构，通过入口登记实际位置及维护责任；缺失内容按模板补齐。冲突、过时或职责混杂的资料，在分析后提出必要的整理方案。

### 下一轮：已有项目写入前的确认（助手建议，待用户确认）

建议分析阶段保持对原项目只读，先形成具体初始化清单：目标位置、复用资料、拟新增或修改内容，以及需要开发者决定的冲突。开发者确认一次后，按清单组织相应角色完成写入和核对；同一范围内无需逐文件重复确认。

分析报告区分已观察的实现、已有文档中的要求与需要用户确认的目标。运行验证的结果按实际执行情况记录；缺少运行条件时明确未验证，不据此补写已通过的结论。

具体流程草案见[项目接入与初始化流程](../proposals/project-onboarding.md)。首版运行保障所需的配置如果涉及客户端或权限设置，应在清单中独立说明具体修改和授权范围。

### 2026-09-07 — 已有项目初始化清单确认（用户已确认）

用户对 Q33 回答“认可”：先对原项目只读分析，再列出复用、新增、修改和待决冲突的具体清单，用户确认一次后按范围统一执行并核对；同一范围内不逐文件重复询问。涉及客户端配置或权限设置的动作在清单中独立说明。

### 下一轮：中断与再次初始化（助手建议，待用户确认）

建议保留已经完成的有效结果，记录执行到哪里及剩余事项；恢复时读取当前实际文件并与原清单核对，只处理仍需完成的内容。用户后来的修改优先保留，出现影响写入内容或范围的新变化时，重新给出受影响部分的清单。

同一目标再次初始化且没有缺口时，报告无需改动；不会重建文档或用空模板覆盖内容。新版模板涉及已有资料变化时，先提出升级或补齐建议，由用户确认对应改动后应用。

### 2026-09-07 — 恢复与重复运行（用户已确认）

用户对 Q34 回答“认可”：保留已完成的有效内容，恢复时核对实际文件与当前变化，仅补剩余缺口；用户后来的修改保留。没有缺口时报告无需改动，冲突和模板升级涉及的变化先列明，再按对应确认范围处理。

## Answer

接入与初始化采用[项目接入与初始化流程](../proposals/project-onboarding.md)，详细步骤和完成条件由该文件维护。

### 新建与接手

- 用户显式启动接入，先明确目标项目与本次范围。新项目依据已明确内容建立当前需要的资料；默认布局见[项目目录模板](../proposals/project-layout.md)。
- 已有项目先只读分析代码、资源、文档、工程配置及已有结果，区分实现现状、有效要求、缺失与冲突、尚未验证和需要用户决定的事项。
- 有效文档与原有目录优先复用，通过入口记录实际位置及维护责任。缺失资料按模板补齐；冲突、过时或职责混杂的内容提出必要整理方案。观察到的代码行为不能直接转成未经采纳的产品目标。

### 写入与完成

- 原项目分析阶段保持未修改。初始化清单列出目标位置、复用项、拟新增或修改项及理由；用户确认一次后，在对应范围内组织角色写入和核对。
- 客户端配置、权限或 hooks 信任等动作在清单中独立说明具体操作与授权范围；同一范围内不逐文件重复询问。
- 制作统筹组织工作，专业文档由相应角色维护，写入使用 writing-for-agents。核对入口、引用、资料内容与实际项目的一致性，记录实际完成项和缺口。
- 文档接入完成与运行保障已经启用分别记录；不得用结构已建立代替能力已验证。

### 中断、再次运行与升级

- 保留已经完成的有效结果，记录执行位置及剩余事项。恢复时检查实际文件、原清单及用户后续修改，按仍适用的范围继续。
- 无缺口时报告无需改动。出现影响写入的新变化时，列出受影响部分再处理，保留用户内容与历史事实。
- 新版模板涉及已有资料变化时，先提出升级或补齐建议，经对应确认后应用。

具体运行接口、版本标识和模板字段在[Skill 划分、Agent 分工与完整设计验收](06-skill-contracts.md)中细化；本票不执行真实项目初始化。

### 2026-09-07 — 协作配置补充（用户明确要求）

用户指出需要类似 setup-matt-pocock-skills 的项目初始化和接手能力，包括任务使用 GitHub Issues 或本地 Markdown 等配置。本补充纳入 Game-Init，不改变已确认的十四个业务入口。

Game-Init 同时承担协作配置与资料接入：识别已有任务后端、五类标签映射、文档位置及领域资料布局；在缺失或需要切换时形成选择和具体配置清单。首版提供本地 Markdown 与 GitHub Issues 后端合同；具体项目在初始化时确定，当前插件设计 tracker 保持原有本地 Markdown。

配置及后端合同见[项目协作配置](../contracts/project-configuration.md)与[工作记录合同](../contracts/records.md)。此处参考原 setup 的探查、确认和映射方法，实际写入继续遵守已定目录、角色和授权规则，不执行原 setup 对当前客户端文件的修改。
