# 显式调用与制作统筹的协作边界

## Question

所有 Skill 必须显式调用时，调用必须由开发者逐次发起，还是允许开发者调用制作统筹后，由统筹明确调用下游 Skill？如何界定一次调用内的工作范围、执行中的追问和恢复，以及何时必须等待下一次显式调用？

## Comments

### 2026-09-07 — 用户明确的调用方式与职责边界

- 制作统筹类似游戏制作人，可以发起对所有 Skill 的调用；开发者仍可单独显式调用任一 Skill。
- 开发者可以显式调用制作统筹并提出新功能想法；统筹判断需要一个或多个 Skill，组织完成需求并向开发者反馈。
- 制作统筹自身只可修改和记录项目管理类文档，不能直接修改设计文档、代码等专业产物。
- 此澄清替代助手此前“只有开发者能逐次发起每个 Skill”的建议；该建议未被用户采纳。
- 统筹可以选择下游 Skill，不代表普通对话可自动触发插件技能。

### 2026-09-07 — 用户确认连续调度边界

用户对以下建议回答“可以”：明确授权“按这个方案实现”后，统筹可以在这次授权范围内连续组织设计、开发和验证，不要求用户逐次调用；遇到需要用户决定的玩法取舍、范围变化或约定的阶段检查点时暂停，其余工作持续组织完成。

## Answer

本票通过用户对调用主体、自身写入职责及连续调度边界的明确回答解决。

1. 开发者显式调用制作统筹或任一专业 Skill；普通对话内容不能自动触发 Skill。
2. 制作统筹被调用后，可明确选择并组合所有 Skill，在当前需求范围内组织工作并汇总反馈，无需开发者逐个手动调用。
3. 统筹自身只能修改、记录项目管理文档，不能直接修改设计文档、代码等专业产物。专业产物由对应专业执行者在授权范围内处理；调度能力不扩大统筹自身的写入职责。
4. 用户要求讨论时，统筹组织讨论和评估；不能据此自行转入实现。用户明确授权实施后，可连续组织设计、开发和验证。
5. 遇到需要用户决定的玩法取舍、范围变化或约定检查点时，暂停相关步骤并取得决定；其余已授权且不依赖该决定的工作可以继续。必要追问不要求用户重新逐个调用 Skill；若需求范围或授权改变，不能自行假定同意。
6. 可覆盖暂停与恢复的原则是保留原需求和授权边界；具体跨会话恢复、授权记录与失效情况由[项目记录、角色交接与跨会话恢复](04-project-handoffs.md)细化。

后续细化：项目管理文档与专业产物的具体归属由[专业角色的职责、产出与决定权](02-role-responsibilities.md)及交接设计确定。Codex 中如何承载和落实职责隔离仍需核实，本票确定的是产品规则，不表示技术权限隔离已经实现。
