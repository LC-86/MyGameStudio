## Question

从游戏想法到发布和上线迭代，通用工作流如何划分阶段？每个阶段解决什么问题、需要什么输入、产生什么可检查的结果；什么证据支持继续、返工、缩减范围或停止？如何接入已有项目，避免机械地从头重走？明确流程与证据要求，并结合角色职责确定责任归属。

同时明确不同项目规模、已有进度和游戏类型下的流程裁剪原则：哪些工作可合并，哪些证据可沿用，哪些检查不能因为裁剪而遗漏。

## Comments

### 2026-09-07 — 通用流程起点（助手建议，待用户确认）

以六个阶段作为流程参照：方向与范围、核心玩法验证、完整体验验证、正式生产、发布准备与发布、上线迭代。阶段围绕需要回答的问题和验证证据组织，不预设引擎、平台或美术类型。

建议允许按项目规模合并阶段、在依赖允许时并行工作，已有项目从核实后的现状接入。合并阶段仍需回答相关关键验证问题；可以沿用经核实仍适用的已有证据，不能将阶段名称或文档数量视为通过依据。具体阶段通过标准、裁剪方式及责任还需进一步讨论。

本次讨论仅设计发布流程，不执行或授权发布。

### 2026-09-07 — 轻量流程与人主导判断（用户已确认并补充）

- 用户认可六阶段作为参照、根据项目规模和现状裁剪流程。
- 框架面向个人独立开发，不采用大团队、大公司式的统一重流程。许多验证与判断由开发者本人推进，不应因缺少完整市场调研、投入预估或测试模型而将个人项目一直卡在立项评审。
- 个人项目可以通过简要收集信息，由开发者作出方向判断；更重视尽快得到可玩的完整体验，用户以垂直切片表达这一目标。
- 不同开发体量、投入和难度的项目需要不同工作流。用户以“羊了个羊”与“王者荣耀”作规模差异的例子，不表示选定任一项目、引擎、平台或商业模式。
- 因此，六阶段仅作为全生命周期的覆盖参照，不能实现为每个项目都必须顺次完成、达到统一标准才放行的流程。具体工作量与判断方式须服从当前项目需要。

### 后续设计约束

将此前“阶段通过条件”的讨论转为项目适用的检查与人工决定：明确当前要做出的成果、关键不确定性及需要开发者判断的事项。记录应区分已验证、未验证和开发者选择继续的内容；选择继续不应被写成已有验证证据。后续细化规则时不得重新引入用户已经排除的企业式立项门槛。

### 下一轮：围绕小目标交替设计与实现（助手建议，待用户确认）

建议只要求开始当前工作所需的最小设计清楚，不等待整个游戏的设计文档定稿。围绕一个小的体验目标，方案设计形成足够执行的方案，制作实现完成可试玩结果，开发者试玩反馈后再调整后续设计与任务；关键不确定性大时先制作验证原型。允许连续小循环形成垂直切片及后续版本。

需要确认这一推进粒度；各轮最少输入、输出和验收记录的具体内容由本票的阶段责任与后续交接设计共同展开，不将“轻量”解释为无需明确当前目标、授权或结果。

### 2026-09-07 — 小步迭代与整体把控（用户已确认并补充）

用户认可围绕小目标交替开展设计与实现，称之为“小步快跑”。用户强调这种模式尤其需要把控整个项目，否则容易失控；明确举出的失败场景是目标已经调整，却仍然按照最初目标管理项目。

因此，整体目标与当前任务、设计要求、验收判断保持一致，属于本框架必须处理的问题，不能仅记录单次工作进度而忽略目标变化。

### 下一轮：目标变更后的同步检查（助手建议，待用户确认）

建议制作统筹维护简短、明确的当前项目目标、范围和下一份可试玩成果。目标或范围变化后，先识别受影响的计划、设计、正在进行的工作及验收要求；统筹更新项目管理记录，组织相应专业角色修订专业产物，对过时或待复核内容作出标记。历史产物保留，不因目标变化自动删除；未受影响且仍在授权内的工作可以继续。

仅完成普通任务时，可沿用已确认的“专业角色记录事实、统筹下次介入同步进度”规则。若发生目标或范围变更，则建议受影响的工作先完成轻量同步再继续，避免按旧目标推进。

直接调用专业 Skill 时若开发者改变目标，该 Skill 先记录明确的变更及影响，并提示开发者显式调用统筹处理同步；不自行反向启动统筹，不擅自改整体计划。此处的同步触发和暂停规则仍待用户决定。

用户已明确作出的目标决定不应被当作未获确认的提案反复询问；只有尚未决定的影响和取舍需要进一步确认。记录结构、版本关联以及恢复时如何识别新旧目标由交接票细化。

### 2026-09-07 — 目标变更优先同步（用户已确认）

用户对 Q15 回答“认可”：普通进度允许稍后同步；目标或范围变化时，先由统筹检查影响、更新安排，再继续受影响的工作。直接调用专业 Skill 时发生此类变更，专业执行者记录变更并提醒开发者显式调用统筹；已经明确的用户决定不重复确认，仅补齐未决定的影响与取舍。

## Answer

### 工作流的组织方式

六阶段为全生命周期的覆盖参照：方向与范围、核心玩法验证、完整体验验证、正式生产、发布准备与发布、上线迭代。它们不是固定顺序的强制评审关卡，也不使用统一的文档数量、市场调查深度或投入测试模型作为放行门槛。

具体项目根据开发体量、投入、难度、已有状态和关键不确定性组织工作。允许合并阶段、在依赖允许时并行工作，以及从已经核实的现状接入已有项目。专业工作不能只因没有独立阶段而被默认为完成；已有验证证据可以在核实仍适用后沿用。

### 迭代与检查

- 优先明确下一份可试玩成果，围绕小目标交替开展设计、实现和人工试玩；当前一步需要的设计清楚即可推进，不等待整款游戏的设计文档定稿。
- 简单、熟悉的工作采用轻量方式；会导致大量返工的关键不确定性，应针对性验证。必要时由方案设计制作隔离原型，制作实现负责正式成果的集成和验证。
- 验证与继续、调整、缩减范围或停止的判断，结合开发者本人参与。人工试玩和主观体验判断可以成为决定依据，不强迫所有问题量化为测试模型。
- 可以在仍有不确定性时由开发者决定继续探索。记录区分已验证、未验证和人工选择继续，不将决定继续写成验证已通过。
- 具体 Input / Output、验收与退回记录由[项目记录、角色交接与跨会话恢复](04-project-handoffs.md)细化；为当前小目标定义，不要求每轮输出整套项目文档。单独调用专业 Skill 仍按该次局部请求交付。

### 整体目标与变更同步

- 制作统筹负责维护当前目标、范围与后续安排，并使任务、专业设计及验收要求与当前目标保持一致。普通任务的完成事实由专业执行者记录，统筹下次被显式调用时核对并同步整体进度。
- 目标或范围变化时，优先识别受影响的计划、设计、进行中工作和验收要求；统筹更新项目管理记录，组织专业角色调整对应产物，对已过时内容作出明确标记。完成必要同步后再继续受影响工作，未受影响且仍被授权的工作可以继续。
- 历史成果保留；目标变化不构成自动删除已有产物的授权。用户已经作出的目标决定不重复确认，新的影响与取舍仍需厘清。
- 若目标变更发生于直接调用的专业 Skill，专业执行者记录变更并提示开发者显式调用统筹同步，不自行反向启动统筹，也不擅自更改整体计划。

角色的职责、冲突处理与独立审查沿用[专业角色的职责、产出与决定权](02-role-responsibilities.md)。本票确定的是适合个人开发的推进与控制规则，不授权实际游戏开发、上传或发布操作。
