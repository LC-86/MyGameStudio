## Question

角色在不同平台、工具和引擎下如何确定可用执行方式？什么情况使用已有能力、进一步调查或交给开发者处理？专门适配需要提供哪些信息与验证方法，如何在遵守显式调用边界的同时保持通用角色职责完整？

### 下一轮：未受控写入工具的处理（助手建议，待用户确认）

建议第一版只向自动执行流程开放已经验证可约束的写入能力。尚未适配、身份无法确认或写入范围无法判断时，停止相关自动写操作，给出缺少的接入条件；可由开发者明确选择手动完成并回传结果。已有受控能力和互不依赖的工作继续推进。

该规则会限制某些工具的自动使用，但保留平台与引擎无关的工作职责。具体禁用、隔离或受控入口机制需在目标运行环境验证。

## Answer

### 能力与依赖

角色职责保持完整，执行方法按项目条件确定。准备任务时检查现有项目资料和可用能力；可自行查明的事实先调查，需要开发者取舍或额外授权的事项明确提出。实际交付与验证按证据记录。

分发和升级必需通用能力时，使用[依赖分发方案](../proposals/dependency-policy.md)：自有技能、模板和必要的通用 Skill 及引用资源随插件提供固定版本；外部引擎、编辑器和服务按项目选择，调用时核对实际条件。调用定位不能依赖开发机个人路径，也不能因全局同名 Skill 更新而悄悄改变内置流程。

### 显式调用与文档方法

所有插件 Skill 显式调用，统筹在被调用后按已有范围组织技能；保持单独调用专业 Skill 的入口。文档写入使用 writing-for-agents。

确定实际元信息和安装发现方式时，读取[Codex 承载能力研究](../research/codex-capability-boundaries.md)。实现必须验证直接调用、普通对话不触发和统筹委派三条路径，不能仅依据其他客户端的元信息字段推定行为。

### 写入限制

首版实现工具调用前的越界写入拦截。按[工具拦截设计](../proposals/tool-interception.md)统一定义角色、任务及资源权限，优先在受控执行环境落实；同一边界内更换工具复用限制，工具调用方法独立适配。

连接新的执行环境、既有外部进程或远端服务时核对新增访问通路。权限层不按每个工具重新设计；仍需查明该通路是否满足当前保障要求。尚未证明的能力保留明确缺口，不报告为已具备强制限制。

### 实现验证与后续接口

工具拦截的可信身份、检查故障、间接写入、同文件竞争及控制规则保护，按[拦截契约研究](../research/tool-interception-contract.md)验证。架构方向已确定，目标客户端的运行能力尚未通过实测；第一版不能以仅有 Skill 指令或 hook 配置替代验收。

新建或接手项目时如何选择、检查和配置这些能力，由[项目接入、深度分析与初始化](08-project-onboarding.md)确定。具体 Skill 清单、依赖版本、执行接口和验收计划，由[Skill 划分、Agent 分工与完整设计验收](06-skill-contracts.md)细化。
