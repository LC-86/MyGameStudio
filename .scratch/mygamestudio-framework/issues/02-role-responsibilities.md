## Question

围绕个人独立游戏开发，需要哪些专业角色？每个角色负责什么、不负责什么、交付什么、由谁检查，其与制作统筹及开发者的决定权如何划分？如何处理跨角色工作与意见冲突，避免个人项目承担不必要的交接成本？

### 2026-09-07 — 三角色起点（助手建议，尚未确认）

| 候选角色 | 主要上下文与责任 | 候选写入范围 |
| --- | --- | --- |
| 制作统筹（已确定） | 目标、范围、进度、任务、依赖、风险和协作 | 项目管理文档 |
| 方案设计（待讨论） | 玩家目标、体验约束、规则及相互关联的设计决定 | 对应设计方案与规格 |
| 制作实现（待讨论） | 已确认方案、当前工程或资源、工具限制及运行或预览证据 | 代码、资源、工程配置及实现记录 |

方案设计可按需使用玩法、数值、关卡、叙事、交互及视听方向等技能；制作实现可按任务分别使用代码、视觉资源、音频及资源集成等技能。这仅为候选分组，完整的市场、发行、运营等能力归属尚待以场景检查，不能视为已覆盖或被排除。

本轮要检验的分界：代码实现与视听资源制作是否可以作为制作实现角色下的不同技能及独立执行实例，还是存在必须拆成不同角色的稳定上下文或权限差异。

### 2026-09-07 — 方案设计的验证原型职责（用户已确认）

用户认可方案设计角色具备原型实现能力，以判断设计可行性；用户以 AI 时代产品经理需要实现原型来验证想法说明其意图。该类比只解释角色设计意图，不作为用户职业或个人经历的事实。

用户认可的建议包括：原型围绕明确的验证问题制作，放在隔离位置；方案设计说明验证目标并记录试玩结论；进入正式工程的代码和资源由制作实现角色负责。角色分界依据成果用途与责任，不能简单按“写文档”和“写代码”划分。

这项确认不意味着三个角色已作为完整清单定案。原型后续复用、整理或重写的具体规则仍需根据成果质量及正式工程约束确定，不预设一律丢弃或直接纳入正式工程。

### 下一轮场景（助手建议，待用户讨论）

以“实现已确认的火球技能”为例：代码、动画或特效、音效和资源接入共同服务一个可试玩结果。建议由制作实现角色对完整结果负责，按任务调用专业 Skill；可将相对独立的素材任务交给独立子代理，明确交接条件，并由一个执行者负责集成和验证。无需仅因使用美术或音频技能而增加常设角色。

需用户决定：是否认可制作实现角色覆盖这些专业工作并对集成结果负责。具体委派机制与统筹的分工后续细化，不据此推断专业角色已经获准无限层级调度。

### 2026-09-07 — 制作实现的完整交付责任（用户已确认）

- 用户认可上述制作实现职责：统一负责代码、视听资源及其集成，按需使用专业 Skill；相对独立的工作可以交给不同执行实例，但必须明确最终集成和验证的责任者。
- 用户可以直接调用某个专业 Skill 处理局部工作，交付范围依该次请求确定，不自动扩大为完整功能制作。
- 用户提出必须设计各环节的 Input 与 Output，特别关注方案设计到制作实现的交付；用户同意若后续已有讨论安排，沿当前问题节奏继续。具体交接内容由[项目记录、角色交接与跨会话恢复](04-project-handoffs.md)承载，各 Skill 输入输出由[Skill 划分、Agent 分工与完整设计验收](06-skill-contracts.md)展开。

### 下一轮：市场、发行与运营的职责覆盖（助手建议，待用户确认）

检验能否继续使用这三个角色：方案设计负责结合市场与玩家反馈形成产品、发行或运营方案；制作实现负责将确认方案落实为素材、构建、分析工具或版本改动；制作统筹负责目标、排期、依赖、任务及执行状态。

例如上线后玩家反馈某一关卡困难：方案设计调查反馈并提出调整及验证方案；制作实现完成关卡或数值改动并验证；制作统筹组织工作与版本安排。市场或运营相关专业资料按需加载，不要求角色在一次会话中拥有所有资料。

这一建议尚未确立方案设计与制作实现的完整业务范围。上传、发布、消息发送、付费等外部动作仍需对应明确授权；不能由角色能力范围推导操作授权。

### 2026-09-07 — 三角色覆盖市场、发行与运营（用户已确认）

用户认可将市场、发行与运营工作纳入现有三个角色：方案设计形成相关方案，制作实现落实确认后的方案，制作统筹组织任务和跟踪结果。用户明确当前没有必要独立设置市场、发行、运营角色；待游戏产品正式上线，某些职责的重要性上升后，再考虑角色独立。

当前三角色的覆盖方向已确认，具体成果写入归属和协作规则仍待完成。不设置独立角色不表示推迟或移除上线前必要的市场研究、发行准备等专业工作，也不设定上线后自动拆分角色的规则。

### 下一轮：直接调用专业技能后的进度同步（助手建议，待用户确认）

开发者绕过统筹直接调用一个专业 Skill 时，需要同时保留直接使用的便利和整体进度的真实性。建议专业执行者维护本次专业产物及其交付、验证、遗留事项记录；制作统筹在下一次被显式调用时读取这些记录，核对后更新整体进度与后续安排。专业 Skill 不必自行启动制作统筹，也不需额外常驻监控。

要确定的是记录与总进度的维护责任；字段、文件位置、同步检查和跨会话恢复规则由交接票细化。此建议尚未确认，不改变现有调用边界。

### 2026-09-07 — 直接调用后的进度同步（用户已确认）

用户答复“认可”：专业执行者维护本次交付物、验证结果与遗留问题记录；制作统筹在下一次被显式调用时读取记录、核对实际成果，再更新整体进度和后续安排。专业 Skill 不自行启动制作统筹，也不替统筹调整整个项目计划。整体进度允许在统筹下次介入时同步，专业工作事实必须留存。

具体记录格式、存储位置、缺失或过期记录的处理，由[项目记录、角色交接与跨会话恢复](04-project-handoffs.md)细化；当前不建立自动调度或后台监控。

### 下一轮：设计与实现冲突的处理责任（助手建议，待用户确认）

以“确认的同屏敌人数在目标设备上无法达到性能要求”为例，区分工程实现细节与玩家体验、范围的改变。建议制作实现先提供测量证据及备选路径；不改变已确认设计要求且处于授权范围内的技术调整由制作实现处理；需要修改玩法或体验时交由方案设计评估并修订建议；涉及重要体验取舍、范围或预算变化时由开发者决定。制作统筹负责组织处理并记录决定，不直接改设计或代码。

这一建议仍待用户确认，不能把发现困难视为自行降低需求或扩大授权的依据。

### 2026-09-07 — 冲突处理规则（用户已确认）

用户答复“认可”：制作实现提供证据与备选方案，在授权范围内自主处理不改变设计要求的技术调整；方案设计评估玩法与体验调整并提出修订方案；开发者决定重要体验取舍和范围、预算等变化；制作统筹组织讨论、记录决定、调整任务，不直接修改设计或代码。实现方不能自行降低需求，设计方需要回应实际验证结果。

## Answer

以下为本票最终决定；上方 Comments 保留提案、修正及用户确认的历史，不将早期候选表当作当前角色清单。

### 角色划分原则

当前保留制作统筹、方案设计、制作实现三个角色。优先按共享上下文、相互关联的成果、写入权限和责任划分，减少重复理解与无意义交接。每个角色可使用多个专业 Skill；角色不等于人类岗位，也不等于一个永久会话。具体任务可以使用独立执行实例，不以角色少为由混入无关资料。

### 职责与产出归属

| 角色 | 主要责任 | 主要产出与写入范围 |
| --- | --- | --- |
| 制作统筹 | 理解需求、检查整体状态、组织技能组合、安排任务和依赖、汇总反馈 | 项目管理文档、整体进度和任务安排；不能直接改设计文档、代码或其他专业产物 |
| 方案设计 | 形成并检验产品体验、规则及市场、发行、运营方案；依据证据修正设计 | 设计方案和规格、验证原型及验证结论 |
| 制作实现 | 将确认方案落实为正式成果，按需使用程序、美术、音频等技能，对完整结果负责 | 代码、视听资源、工程配置、可运行版本、验证和交付记录；局部调用仅交付请求范围内的成果 |

后续文档讨论已明确技术架构与 TDD 也归制作实现维护，详见[项目记录、角色交接与跨会话恢复](04-project-handoffs.md)中 Q18 的用户确认；产品体验要求仍由方案设计维护。

方案设计具备原型实现能力。原型围绕明确的验证问题在隔离位置制作，用于判断设计可行性；正式工程的集成与维护由制作实现负责。是否复用原型内容要按质量和工程要求判断，不预设必须重写或直接接入。

三个角色同时覆盖市场、发行和运营的专业工作，当前不另设对应角色；游戏正式上线后，再根据实际需要决定是否拆分。平台、引擎、工具适配后续完善，角色职责保持完整。外部写入、发布等动作仍受用户对应授权约束。

### 审查、交接与决定权

- 不设置常设评审角色。通过如 Game-Review 的技能启动同一专业的独立子代理审查；关键设计、代码改动和阶段交付安排独立评审，轻微修改采用自查和必要验证。示例名不是已经实现的技能。
- 制作实现可以组织不同执行实例处理相对独立的工作，但必须明确最终集成和验证的责任者；具体委派机制在 Skill 设计中细化。
- 直接调用专业 Skill 后，专业执行者记录交付物、验证结果及遗留问题。制作统筹下一次被显式调用时读取记录并核对实际成果，再更新整体进度；专业 Skill 不自行启动统筹，不替统筹调整整个项目计划。
- 上述延后同步适用于普通工作进度；目标或范围变化优先同步的规则另见[游戏开发工作流与阶段通过条件](03-workflow-gates.md)，不能继续按旧目标推进受影响工作。
- 不改变设计要求、且在当前授权范围内的技术调整，由制作实现处理。涉及玩法或体验变化，由方案设计评估；重要体验取舍、范围或预算等变化交由开发者决定。统筹组织处理并记录结果，不代替专业角色改产物。
- 阶段通过的重要决定由开发者保留。对有证据的实现限制需要评估，不能以困难为由自行降低需求，也不能忽略验证结果无限尝试。

### 后续设计的明确归属

- [游戏开发工作流与阶段通过条件](03-workflow-gates.md)：各阶段的工作、检查点、继续或返工的条件及责任。
- [项目记录、角色交接与跨会话恢复](04-project-handoffs.md)：各环节 Input / Output，特别是方案设计到制作实现的交付、接手、验收、退回规则，以及文件归属、同步和恢复。
- [通用职责与具体执行能力的衔接](05-capability-adaptation.md)：工具能力不足、适配与交接。
- [Skill 划分、Agent 分工与完整设计验收](06-skill-contracts.md)：具体技能清单、执行实例和委派机制、技能输入输出及可验证的职责约束。

本票确认角色职责，不表示详细交接或 Codex 技术权限隔离已完成；上述内容继续由对应决策票确定。
