## Question

哪些记录是项目决定、进度、任务、资源和验证证据的依据，保存在哪里？角色交接及新会话恢复需要哪些最少信息？当记录冲突、验证过时或工作中断时，怎样确定真实状态和下一步，避免把计划或助手声明当成完成事实？

重点定义各环节的 Input 与 Output，先以“方案设计 → 制作实现”为例：交付包含哪些设计内容、原型或资源引用、验证证据与未决事项；什么条件下可以接手，输入不足如何退回补充，输出由谁验收，以及设计变更后如何同步。项目级交接规则在本票保存，各 Skill 的具体输入输出约定由 Skill 划分票展开。

### 2026-09-07 — 方案设计到制作实现的最小输入（助手建议，待用户确认）

建议以一份面向当前小目标的简短设计说明，配合必要的原型、资源和已有文档引用，作为主要交接依据。已有设计说明足够时直接使用，不另外维护一份重复的交接文档；不要求实施者依赖完整聊天历史来猜测要求。

最少说明四类内容：

1. 本次目标与范围：关联当前项目目标，说明这次做什么、暂不做什么。
2. 行为与约束：玩家怎样操作、系统怎样响应，以及会影响实现或体验的已确认要求。
3. 完成标准：怎样运行、检查或试玩，什么结果表示当前目标完成，哪些体验判断由开发者作出。
4. 参考与未决：必要的原型、资源、相关设计及验证结果引用，已知限制和仍未确定的事项。

这四类信息可以合在一份短说明中，不要求四份文档，也不要求为所有未来功能先写完整规格。用户已明确的设计与授权需保留可追溯依据；具体授权记录、输入缺失及接手确认规则在后续问题展开。

### 下一轮：三个角色与 Review 的基本 Input / Output（助手建议，待用户确认）

| 环节 | 最少需要的输入 | 主要输出 |

| 制作统筹 | 开发者需求或反馈、当前项目目标与约束、已有成果和工作记录 | 当前工作目标、范围、任务安排、适用设计与验收依据的引用、需要开发者决定的事项 |

### 下一轮：原子任务粒度与完成责任（助手建议，待用户确认）

**原子任务**：建议每项围绕一个可交付、可检查的小成果组织，目标是能在一个清楚的工作上下文内执行、交接或恢复。当前及近期目标细化为任务，更远的想法保留较粗粒度。任务可以是局部专业成果，例如可导入的动画资源，不要求每项都成为完整玩家体验；技术拆解由相应专业角色提供，统筹组织整体安排。

**完成责任**：建议任务事先说明验证方式，以及是否需要开发者人工验收。结果满足适用基线、约定检查及必要独立审查时，统筹可将无需人工验收的任务记为完成；需要人工判断的任务保留待验收状态，取得实际反馈后更新。专业执行者提交成果与证据，统筹核对后维护整体状态；直接调用时沿用已确认的延后同步规则。

两项均待用户决定。遗留问题、未验证范围及基线变化按其实际影响处理，完成状态以满足本任务约定为准。

- 组织本轮工作时，使用[游戏开发小闭环](../proposals/game-work-loop.md)：目标澄清、当前约定、原子任务、制作验证、审查验收、状态同步；按需要进入环节，Game-* 具体名称在 Skill 划分中确定。
- 分流请求与设计任务字段时，使用[任务分流设计](../proposals/task-triage.md)：保留五类 triage 状态，独立记录执行责任、验收方式、进度与依赖。
- 原子任务围绕一个可交付、可检查的小成果；当前和近期目标细化，专业执行者提供技术拆解，统筹组织整体安排。
- 完成条件满足适用基线、约定检查及必要独立审查时，统筹核对后更新状态。需人工判断的任务保持待验收，依据实际反馈更新；专业执行者记录成果和证据。
- 并行执行前核对依赖与修改范围。互不影响的工作可以并行；同一可写产物由一名执行者在同一时间维护，重叠工作协调先后或拆开后由明确责任者集成。实际写入保护仍需后续实现验证。

### 接手、输入缺口与恢复

1. 从入口定位当前目标、适用基线及任务记录。完成条件：能说明当前要处理的工作、引用版本及尚未完成的部分。
2. 核对实际成果和证据与记录是否一致、基线是否仍适用。可从项目查明的信息先调查；影响当前工作的缺口和实质取舍明确交给相应责任者，相关工作等待补齐。
3. 在当前授权、依赖与修改协调条件满足后推进剩余工作。已完成且依据仍有效的成果按记录复用；新改动或具体疑点需要复核时，检查受影响部分。

目标或范围变化优先由统筹组织影响检查与同步，沿用[工作流决定](03-workflow-gates.md)。直接调用专业 Skill 的普通完成事实可在统筹下次介入时同步，目标变化的相关工作先同步再继续。
