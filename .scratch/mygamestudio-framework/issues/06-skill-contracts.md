## Question

如何把已确定的工作流与职责映射为可显式调用的 Skill？哪些工作需要独立 Agent 执行或评审，哪些可由同一会话完成？每个 Skill 的输入、工作范围、交付、验证、停止和交接条件是什么？用哪些典型场景检查整份设计是否完整、一致并适合个人开发者，如何组织最终设计文档？

## Comments

### 游戏开发小闭环

用户要求参考 Matt 的目标澄清、规格、拆单、实现与审查工作流，重新设计符合本项目约束的版本。讨论闭环或技能拆分时，读取[游戏开发小闭环提案](../proposals/game-work-loop.md)；核对能否直接调用原始技能时，读取[兼容性核对结果](../research/matt-workflow-fit.md)。提案中的 Game-* 名称和技能边界尚未定案。

最终设计需区分执行者与验收者、Agent 是否具备开工条件、静态审查与实际体验验收，并覆盖未提交或新建成果。文件定位、显式调用及写入方法等依赖由能力适配与初始化决定提供。

### 调用机制的适用性

编写 Skill 时已读取 writing-for-agents 的 SKILL-MECHANICS.md。该参考关于“用户调用型路由只能提示、不能调用其他 Skill”的说明不直接套用：用户已明确要求制作统筹在显式入口后可以委派专业技能。最终实现以 Codex 适用元信息、显式的调度与资源定位协议及实际验证为准，保留用户决定的调用语义。

## Answer

2026-09-08，根据已确认的入口、调用方式及用户要求继续完成设计，形成[MyGameStudio：插件工作方式完整设计](../spec.md)。上方 Comments 是讨论历史；当前分工和行为以完整设计及其指向的合同为准。

- 十四个业务入口均有输入、工作范围、输出、写入责任和完成条件，从[共同合同](../contracts/common.md)进入各专业分支。
- Game-Init 已包含项目协作配置、新建与接手分析、文档及目录补齐；任务后端、五类标签与核心文档位置分别配置。当前设计仓库的本地 tracker 保持不变。
- [模板集合](../templates/README.md)包含十三份项目、任务、交接、决定、研究、初始化、审查与试玩模板，按需实例化并复用原项目有效资料。
- [运行保障](../contracts/runtime.md)与[包合同](../contracts/package.md)明确可信角色绑定、资源范围、工具复用、固定内部依赖、任务后端和扩展边界。
- 已静态核对十四个典型场景、三角色与十四入口对应关系、模板映射和内部文档引用；链接检查无缺失。验收范围与结果分层见[验收矩阵](../acceptance.md)。

本票完成的是设计交付，不代表全部技术机制已在宿主验证。有限原生隔离实验已回读；完整插件安装、角色拦截、故障处理、后端连接与真实项目验收留给后续实现，并保留明确的发布条件。本轮未实现或安装插件，未修改客户端治理文件，未提交、推送或写入外部服务。
