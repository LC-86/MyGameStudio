# MyGameStudio：统一游戏设计问答框架

Status: ready-for-agent

**Progress:** 规格已整理，未开始实施。

日期：2026-09-13。范围：形成完整游戏设计、优化调整或删减已有设计，以及共用的问答交互、决定记录、规格同步、检查和效率验收。

## Problem Statement

开发者希望与 AI 一起设计游戏，但实际使用中需要反复提醒 AI 保存已采纳的内容、控制输出长度和恢复讨论进度。同类问题被拆成多个回合，开发者不断回复“合适”；每个小答案又可能引发多份文档的更新与检查，打断讨论。

开发者还需要从想法逐步获得约定版本的完整游戏设计文档，并在已有设计上优化、调整或删减功能。仅规定问答排版与记录速度，不能确保设计覆盖完整、规则能用于制作，或局部变更的连带影响得到处理。

本次优先解决：决定及时保存，同时减少记录这些决定所花的时间和步骤；按功能或模块组织问题，并让每题的问题、选项、推荐和结果清楚可辨。

## Solution

采用一套统一问答框架，按当前请求和实际资料进入两种模式：新设计模式从想法与已有信息形成约定范围内的完整设计；已有设计变更模式从当前有效设计出发，处理补充、优化、调整和删减。实现偏差另行标明，不通过改写设计迁就错误实现。

方案设计先整理本轮范围内的功能或模块及其先后关系，再围绕一个模块提出一组当前可以决定的问题。每题提供可辨认的编号、选项、推荐答案和主要取舍；开发者可以逐题回答、整体采纳建议或只修改部分答案。AI 负责调查、规则提案、数值推演和影响分析，开发者决定体验目标与重要取舍。

收到回答后，及时保存已经明确的决定，区分未回答、需补充和依赖未满足的问题。重新计算下一轮可讨论的问题；一个模块收敛后，再统一整理其规格与确有影响的引用。沿用既有核心基线和角色职责，不为每个小答案建立新的文档体系。

新设计流程：理解想法 → 明确设计范围 → 建立设计地图 → 按模块成组问答 → 形成模块规格 → 检查整体衔接 → 汇总完整设计文档并核对交接标准。

已有设计变更流程：读取当前设计 → 明确变更目标和保留项 → 分析影响 → 成组讨论关键取舍 → 场景推演或提出验证要求 → 更新受影响设计、旧规则和验收依据。已明确且无真实取舍的局部修改，在已有修改授权内直接处理。

共用小循环：核实前置事实 → 提问与回答 → 保存本轮决定 → 重组后续问题 → 收敛后同步规格。需要原型或试玩才能判断的事项及时转为待验证，不以无限追问替代验证，也不自动开始制作。

每轮只读取当前需要的资料，完成决定保存所必需的检查；模块结束时统一完成规格及受影响引用的检查。已通过且输入未变的检查不重复执行。除行为正确外，还需通过相同场景的前后对比，证明步骤和实际等待时间减少。

## User Stories

1. 作为开发者，我希望先看到功能或模块划分，以便知道当前讨论属于哪一部分。
2. 作为开发者，我希望知道模块之间的先后关系，以便先确定会影响后续方案的条件。
3. 作为开发者，我希望同一模块中当前能决定的问题一起提出，以便一次理解完整方案。
4. 作为开发者，我希望依赖未定答案的问题留到下一轮，以便避免基于猜测作决定。
5. 作为开发者，我希望 AI 自行核实可以查到的事实，以便把注意力放在真正需要我选择的事情上。
6. 作为开发者，我希望每轮说明模块名称和问题数量，以便估计阅读与回答的范围。
7. 作为开发者，我希望每题都有明显的 ❓ 和 Q 编号，以便快速识别问题边界。
8. 作为开发者，我希望问题正文和答案选项分开显示，以便看清楚究竟在问什么。
9. 作为开发者，我希望选项具有 A、B 等标识并说明取舍，以便比较不同方案。
10. 作为开发者，我希望 AI 用 ➡️ 单独标明建议和理由，以便获得设计判断，而非只收到问题。
11. 作为开发者，我希望能用“Q1 选 B，Q2 选 A”回答，以便减少重复描述。
12. 作为开发者，我希望能用“整体按建议，第 2 项调整为……”回答，以便快速确认一组问题。
13. 作为开发者，我希望可以提出选项以外的方案，以便讨论不受预设答案限制。
14. 作为开发者，我希望只回答部分问题时，其余问题保持待讨论，以便未回答不会被当作默认同意。
15. 作为开发者，我希望回复含义不明确时只澄清相关问题，以便已经确定的内容可以继续保留。
16. 作为开发者，我希望收到 ✅ 已确定和 ⏳ 待讨论两类结果，以便明确本轮推进了什么。
17. 作为开发者，我希望明确采纳的决定及时保存并保留来源，以便无需再提醒 AI 补录。
18. 作为开发者，我希望记录区分用户决定、助手建议和候选方案，以便接手者不会把建议当作要求。
19. 作为开发者，我希望模块完成后再统一整理规格，以便减少每个小答案引发的重复写入。
20. 作为开发者，我希望具体规则集中维护，其他材料引用它，以便修改时不必同步大量重复内容。
21. 作为开发者，我希望用具体边界场景检查规则，以便发现正常流程之外的遗漏。
22. 作为开发者，我希望中断后能从已有决定和未决项继续，以便不必重新回答已经定好的问题。
23. 作为开发者，我希望术语及时统一，详细决策文档只用于重要取舍，以便记录有用且不过度膨胀。
24. 作为开发者，我希望长问题组按完整内容单元分批展示，以便阅读清楚且编号不会混乱。
25. 作为开发者，我希望讨论、记录和正式实现的授权保持清楚，以便采纳方案不会触发未要求的开发或发布。
26. 作为开发者，我希望每轮只读取与当前问题和改动相关的资料，以便减少重复加载长文档的时间。
27. 作为开发者，我希望每轮完成必要的保存检查，模块结束后再做整体同步检查，以便及时记住决定且无需反复等待全量检查。
28. 作为开发者，我希望已通过的检查在输入未变时可以复用，以便不会因为新的简短回答重复执行相同工作。
29. 作为开发者，我希望修改、失败或资料变化时只重新检查受影响的部分，以便效率提升不会造成遗漏或覆盖他人的修改。
30. 作为开发者，我希望记录处理用时和完整模块用时都有前后对照，以便确认实际等待减少。

32. 作为开发者，我希望 AI 根据我的请求和现有资料选择新设计或变更模式，以便不用自己选择技术流程。
33. 作为开发者，我希望用自然语言描述玩法片段，并沿用已经明确的内容，以便无需先学会策划术语或重新讲述整个游戏。
34. 作为开发者，我希望完整愿景、当前版本和后续方向分开，以便当前设计能收敛且长期想法不丢失。
35. 作为开发者，我希望 AI 维护覆盖全游戏的设计地图，以便关键系统、内容和体验不会遗漏。

37. 作为开发者，我希望优先讨论影响大、返工风险高或阻碍后续的问题，以便先解决最重要的不确定性。
38. 作为开发者，我希望 AI 将体验目标转成规则、初始数值和可比较方案，以便专业设计工作不全部落到我身上。
39. 作为开发者，我希望回答“不知道”后仍能获得方案、推演或验证建议，以便讨论能够继续。
40. 作为开发者，我希望每个必要系统都有可执行的规格，以便后续制作不需要猜测关键规则。
41. 作为开发者，我希望 AI 检查完整游玩流程和跨系统关系，以便各模块组合后仍然一致。
42. 作为开发者，我希望完整文档包含系统、数值、内容、视听和版本验证要求，以便知道需要制作什么。
43. 作为开发者，我希望设计成稿和体验验证有各自的完成条件，以便未知不会被包装成已经证明的结论。
44. 作为开发者，我希望设计缺口、设计优化和实现偏差被区分，以便问题进入正确的处理方式。
45. 作为开发者，我希望一次变更先明确对象、原因、预期改善和保留项，以便讨论范围清楚。

47. 作为开发者，我希望 AI 主动分析规则、经济、界面、内容、数据和验收的连带影响，以便无需自己找全依赖。
48. 作为开发者，我希望影响检查符合项目的实际阶段，以便不会遗漏已有数据，也不会被追问并不存在的玩家迁移问题。

## Implementation Decisions

以下为已确认方向的具体约定；实现时沿用方案设计、制作统筹、核心基线等既有领域概念。共用问答约定适用于确有待决定问题的场景；已有明确授权且无新增取舍的局部修改按变更模式直接处理。

1. **职责与入口。** 改进现有 Game-Design 讨论、包内 grill-with-docs/grilling/domain-modeling 方法及 Game-Spec 同步衔接，不新增公共 Skill 或永久运行角色。方案设计维护设计过程与决定；核心基线经 Game-Spec 或等效的明确文档步骤同步。涉及项目目标的变更仍由制作统筹处理。
2. **按模块组织。** 对本轮目标给出简短模块划分、当前模块与必要前置条件。一个问题只属于一个明确讨论主题，跨模块依赖用引用说明，避免反复询问同一决定；不要求开场就展开整个游戏的全部细节。
3. **按依赖成组。** 一轮包含当前模块内所有已具备前置条件的问题，不机械地每轮只问一题，也不硬性规定题数。依赖本轮某个答案的问题放到后续轮次；缺少可查事实时先调查，其余不受影响的问题可以继续。
4. **固定阅读结构。** 轮次开头写明模块、轮次和问题总数。每题依次显示“❓ Q编号｜问题标题”、必要的问题正文、“选项”及 A/B 等分项、“➡️ 我的建议”及理由。问题之间保留空行和明显分隔。推荐不是采纳结果；开放问题可以允许自由回答，不为凑选项制造虚假选择。
5. **完整分批。** 遵守当前每条消息及单次工具参数不超过 6,000 字符、每批约 4,000 字符的限制。需要分批时按完整问题拆开，标出本批覆盖的编号并保持同轮编号连续。整体采纳只覆盖已展示且指代明确的问题，不能覆盖尚未展示的后续内容。
6. **回答方式。** 支持逐题选项、整体采纳推荐、整体采纳但修改个别题、自由方案以及部分回答。将回答逐项对应到当时展示的题目和建议；未回答或含义不明的部分不补默认值。已明确的答案保留，只澄清真正有歧义的部分。
7. **结果与下一轮。** 回答后简短列出“✅ 已确定”和“⏳ 待讨论”；待讨论项说明缺答案、缺事实或缺前置决定。用本轮回答重新计算可讨论问题，必要时通过具体边界场景检验规则。模块完成意味着本轮约定范围内的必要决定已明确；主动延期事项列明，不伪装为已解决。
8. **及时保存。** 在已有记录授权内，每次收到明确答案后先保存该轮的最小决定记录，再进入依赖它的下一轮。记录模块与问题关联、采纳内容、决定者及日期、用户回复和对应建议的出处、未决项、影响与基线同步状态。纯讨论模式继续只读，并明确尚未保存；写入失败时保留已决定事实并报告保存失败，不能声称落盘成功。
9. **减少重复维护。** 沿用已有记录位置，按模块聚合维护，不为每个 Q 编号强制新建文件、工单或完整结果报告。模块收敛后统一整理其规格；具体规则集中维护，其他资料优先引用。仅同步实质受影响的资料，不因全局进度变化重写所有文档。必要的保存确认、一致性和权限检查仍保留。
10. **同步与恢复。** 决定已采纳、已保存、已同步核心基线、已实现、已验证分别记录。尚未同步的决定保持可定位，后续工作先核对它们，不能只读旧基线后重新提问或据此开工。被更改的决定保留历史及替代关系；重复处理同一次回答不重复创建决定。依赖实际记录完成接续，不要求新增自动交接系统。
11. **术语与重要决定。** 术语含义明确后及时维护已有术语表；普通规则进入模块规格。只有同时具有改变成本高、缺少背景会令人困惑、经过真实取舍这三个条件，才为决定单独建立详细 ADR。术语表不承担完整规格或实施过程记录。
12. **授权保持。** 显式调用、用户决定权、既有角色范围与受控写入边界继续适用。缺少同步授权或运行条件时明确留下待同步项，不自动签发凭据、不扩大权限、不绕过写入通道。采纳问题组或保存规格不自动授权正式实现、提交、推送或外部发布。

### 模式识别与共同设计责任

先核对请求、当前有效设计、已有决定和实际项目阶段，再选择模式并简短说明依据。能够自行查明的情况不要求用户另填模式选择表。新设计与已有设计变更共用 Game-Design、Game-Spec 及现有记录通路；需要验证时衔接已有 Game-Prototype 或相关验收能力，不新增公共入口。实际制作或外部操作仍需相应授权。

| 识别结果 | 处理方式 |
| --- | --- |
| 只有想法或局部资料，需要建立整体设计 | 新设计模式：提取已有信息，补齐约定范围的设计地图 |
| 已有设计未写清某项必要规则 | 在已有设计变更模式中补充规格；已有明确结论直接沿用 |
| 希望优化、调整或删减已定设计 | 已有设计变更模式：明确改善目标、保留项与影响范围 |
| 设计已明确，但实际实现不符合设计 | 标明实现偏差与依据，交给相应后续修复流程；不擅自改写设计迁就实现 |

文档与实现矛盾时分别列出证据；意图不能确认时只澄清相关取舍。一个请求包含多类问题时分别处理，不因出现实现偏差就重开全部设计。

开发者负责体验目标、必须保留的内容、不能接受的代价与重要方向选择。方案设计负责提取自然语言信息、核实事实、提出具体规则与数值方案、计算依据、边界场景、依赖分析和验收方式。体验目标不自动等同于某项具体机制；例如“轻松”不能直接采纳为“无失败”。已有明确回答不再增加一次形式性确认。

“不知道”或难以选择时，依问题提供不同方案与例子、提出有标记的临时推演假设、延期非阻断细节，或形成验证问题。临时假设保持提案身份，不进入已采纳核心基线，也不授权依赖该假设的正式实现。

在原有 ✅ 已确定和 ⏳ 待讨论之外，按实际需要展示 💡 我的提案、🧪 待验证、🚫 当前不做，不要求每轮输出空类别。采纳与验证是不同维度，“已采纳但待验证”可以同时成立；保存、同步、实现也不由这些图标自动推定。当前不做、永久取消和未知分别保留含义。

### 新设计模式：覆盖与成稿

从开发者描述的玩法、画面、操作、感受及提供的参考开始；已有项目先读取可用资料和已定内容。整理一段典型游玩经历及已知目标，标明原始意图、助手提案和信息缺口。先明确完整愿景、当前成稿版本、后续方向与范围外内容，不擅自把全部愿景列成首发任务。

方案设计维护以下覆盖地图。它是内部查漏与推进依据，不是一次发给开发者的固定问卷，也不要求每个领域单独建文件。

| 设计领域 | 应覆盖的结果 |
| --- | --- |
| 项目目标与边界 | 目标玩家、使用场景、平台、投入约束及明确不做的内容 |
| 核心吸引力 | 玩家角色、目标体验、关键乐趣、参考差异及设计原则 |
| 核心玩法与决策 | 反复执行的行动、可用信息、限制、选择后果与反馈 |
| 完整游玩过程 | 开始、推进、成功或失败、主动退出、结束及再次进入 |
| 系统与相互关系 | 必需对象、资源、功能、输入输出及依赖 |
| 成长与资源流动 | 获得、消耗、解锁、难度、随机性和长期目标 |
| 内容与叙事 | 角色、关卡、事件、剧情、变化方式、制作模板和数量范围 |
| 操作、界面与引导 | 输入、页面流转、信息表达、错误恢复及适用的可访问性要求 |
| 美术、动画与声音 | 风格、镜头、关键表现与所需资产 |
| 商业化与发布需求 | 商业化边界、渠道地区、语言及必要的平台运营条件 |
| 技术与数据约束 | 存档、离线、联网、设备与输入限制、关键技术风险 |
| 版本范围与验收 | 当前阶段、原型与首发范围、后续方向、验证问题和交付标准 |

每项标明适用性、当前状态及已有规则或未决项的位置；不适用需有理由，未查清不能冒充不适用。不为补齐模板添加系统。只在实际变化时更新相关地图项，避免每轮全量重述。

下一轮优先处理影响全局、返工风险高或阻碍后续的问题，再按依赖形成当前问题组。阶段可以依次形成概念说明、足以回答核心问题的原型规格和当前版本完整设计；阶段边界由所需成果决定，不按固定轮数推进。涉及手感或乐趣的关键未知，可在完整设计成稿之前提出验证计划；未获制作授权时只交付验证目标、方法和判定依据。

### 模块规格与完整文档交付

每个必要系统将已采纳意图逐步转换为下列可执行内容。不适用的字段注明理由，不以空占位或“适量、合理、适中”代替关键行为。

| 规格内容 | 要说明什么 |
| --- | --- |
| 设计目的 | 服务的体验与存在理由 |
| 参与对象 | 角色、物品、资源、界面及相互关系 |
| 前提与触发 | 生效条件、触发者与触发时机 |
| 正常规则 | 输入、操作、处理、状态变化和结果 |
| 例外与边界 | 条件不足、上限、重复操作、失败、中途退出及适用的同刻事件 |
| 数值与配置 | 初值、单位、范围、计算关系、取整、可调项和依据；区分已定值与候选试验值 |
| 玩家反馈 | 玩家看到或听到什么、如何理解结果及继续操作 |
| 数据与持续性 | 保存内容、保存时机、退出重进、离线或跨次游玩的保留规则 |
| 验收方式 | 明确初始条件、玩家操作及预期结果；主观体验列出实际验证方法 |

模块规格完成后，按玩家视角推演首次进入、理解目标、操作、选择、结果、结束及再次进入，并核对资源流动、解锁、失败恢复等跨系统关系。检查资源耗尽、重复操作、达到上限、忽略提示、退出等适用反例。能核实的事实与一致性检查由 AI 完成；真正改变体验的取舍才成为后续问题，主观手感或乐趣转为待验证。

最终以一个清晰入口组织四类内容，沿用当前主文档和分模块规格、附表，不强制合并为单个文件：

- **游戏设计主文档**：易读概述、核心体验、核心玩法、完整流程、系统关系及版本边界。
- **系统规则与数值**：必要系统的上述规格、初始配置、资源收支和依据。
- **内容与视听制作需求**：关卡和事件结构、内容模板、角色、场景、界面、动画、特效、声音需求及制作范围，与相关规则可相互定位。
- **版本与验证方案**：当前阶段、原型和首发范围、后续方向、依赖、验收场景、风险与待验证项。

设计交接必须满足：覆盖地图无未解释的空缺；关键流程闭合；当前准备制作的必要规则可执行；范围明确；内容与表现对应；各处现行规则一致；关键未知有方法与影响说明；未参与讨论的执行者无需翻原始聊天即可理解本次交付并继续工作。

有阻断当前交接的关键缺口时，标为设计草案或相应模块待完成；不能因目录齐全而宣称全游戏设计完成。可交接的独立模块明确其边界，不替代整体交付结论。需要试玩的问题可以保留待验证，但必须说明是否阻断当前阶段；没有原型、试玩或玩家证据时，不声称体验或市场效果已验证。

### 已有设计变更模式

先从当前有效设计提取四项变更说明：修改对象、原因、预期改善、需要保留的内容。分清开发者只提出问题还是已经作出修改决定；已明确的删除或调整方向直接进入后续处理讨论，不重复询问是否采纳原决定。确有重大新影响时说明依据并只处理新增取舍。

由方案设计沿玩法规则、成长资源、界面引导、内容资产、数据及验收分析依赖，把结果分成“必须同步”“需要开发者取舍”“不受影响”。影响检查可以递进扩展，发现间接依赖时继续追踪，边界依据是实际关联而非文件是否相邻。无关问题不顺手扩成全面重做。

检查范围随实际阶段调整：

| 阶段 | 需要检查的对象 |
| --- | --- |
| 只有设计，尚未实现 | 规则、流程、数值、内容制作清单和验收要求 |
| 已开发，尚未发布 | 上述内容及现有实现、界面、资源、测试、已有数据与存档兼容 |
| 已发布，有实际玩家 | 上述内容及玩家进度、待领资源、已有权益、迁移和发布安排 |

阶段和对象存在性先核实，未知不得当作不存在。不机械追问并不存在的补偿或迁移；发现需要处理时形成明确设计与后续工作范围，不在仅讨论或仅修改文档的任务中自动执行数据迁移、代码删除或发布。

按变更深度组织工作：局部明确微调直接在授权内处理；模块调整用一组或多组关键取舍问题；结构性修改检查受影响的多个模块并按需提出验证；方向性变化重新审视有关核心方向，保留仍有效的决定。每个候选说明改什么、保留什么、预期改善与代价；仅换名或转移复杂度不能被报告为已经解决原问题。

删减时必须检查原功能承担的作用：明确是一起取消、转移给已有系统，还是以更简单方式保留。检查奖励和成长、引导、入口、教程、内容、数据及验收中的残留依赖；并非每个被删功能都必须有替代品。分别记录正式取消、当前版本不做和明确承诺的后续范围，不能把取消自动转成未来承诺。

变更成稿交付更新后的当前有效设计，以及一份简短变更记录：原因、旧设计与新设计、影响、采纳依据、待验证项及各阶段状态。获准同步时，失效规则、引用和验收要求退出当前有效版本；历史及替代关系保留。只同步实际影响的内容，不重造全套文档。

设计变更完成要求目标和关键取舍明确、关联文档已同步、旧规则已处理、没有未说明的关键断点、待验证内容有方法。实现与效果验证另行判断：只有实际运行符合新设计、关联功能检查通过且改善目标有证据时，才能报告相应实现或效果完成。受影响的旧验证结论标明适用版本，不能沿用为新版本已通过。

### 读取与检查时机

| 时机 | 必须完成的工作 | 范围与复用规则 |
| --- | --- | --- |
| 开始或恢复当前模块 | 核对工作模式、实际项目阶段、当前目标、授权、模块决定与未决项、有关基线和必要前置事实 | 先从资料入口定位，仅展开相关内容；恢复时读取实际状态，不只凭聊天记忆 |
| 每轮决定保存前 | 对照题目和用户答案，确认采纳范围、来源、未决项及与已有相关决定的矛盾；确认本轮可写范围和目标当前版本 | 核对当前模块及直接依赖；受控通道逐次权限和版本校验不得缓存跳过，不扫描无关模块 |
| 每轮决定保存后 | 回读实际写入内容，核对本轮决定完整、无重复、历史未丢失及同步状态准确；检查本次新建或修改的引用 | 检查改动记录和新增影响；本轮未改变核心基线时，不因新增决定就重跑全项目基线、所有链接或远端任务检查 |
| 模块收敛并获准同步规格时 | 汇总未同步决定，更新模块规格及受影响引用，核对已定与未决、历史、版本、指纹和相关链接 | 按实际受影响范围执行一次统一核对；确有跨模块或全局影响时才扩大到对应范围。已有必需检查仍执行 |
| 出现新增修改、失败或状态变化 | 重新读取变化内容，作废受影响的旧检查结果，执行针对性复查 | 版本冲突、断链、写入失败、授权变化或实际证据不足才触发必要重查；无新证据不重复整套已通过检查 |

同一会话中，规则、模板、模块资料首次读取后保留内容版本和使用范围；未变化且仍在适用范围内时复用理解与检查结果。转入新模块、发现外部修改或原检查输入发生变化时，按需补读并重新检查。复用依据是本次可核对的文件版本、内容指纹或等效证据，不能仅以修改时间未变判断有效，也不能替代写入时的当前版本校验。新会话只复用可核验的已有结果；否则补做相应检查。

读取、指纹、链接和范围核对优先使用已有统一工具；相同目的的检查合并执行，不每轮生成一套新脚本或逐文件重复调用。不增加独立缓存服务、后台监控或新的持久化系统。检查明细在已有工作记录中简短保留，日常回复只说明保存结果、必要限制和下一组问题。

纯讨论且未获准保存时，不运行写入与落盘检查。保存失败时保留采纳事实并明确失败，先解决相关问题；不能以减少步骤为由略过必要回读、历史保留、权限和版本检查。

## Testing Decisions

验收方式由本轮根据已确认行为补充，属于实施时需执行的验证设计，并非已经通过的测试或已经取得的性能结论。

优先复用现有“把功能想法形成当前可执行规格”的高层验收入口，贯穿 Game-Design 提问、开发者回答、决定落盘及 Game-Spec 同步。主要检查真实可见回复与最终项目记录，不新增独立对话框架或低层测试接口。已有的质询/决策地图场景、历史决定与未决项夹具，以及核心基线一致性检查可继续使用；包内文本检查仅用于规则完整性，不能代替真实交互验收。

验收场景：

1. **成组与依赖。** 同一模块有三项可立即决定的问题，第四项依赖第三项；首轮完整提出前三项，第四项等依赖确定后再提出。另一个模块不会被无故混入本轮。
2. **阅读结构。** 模块、轮次、问题数量准确；每题有 ❓、Q 编号和标题，选项及 ➡️ 推荐独立显示；数量与编号一一对应。
3. **完整与自由回答。** 分别覆盖逐题选项、整体采纳、只改一项、自由方案；保存结果与用户实际回答一致，不把已拒绝选项写成要求。
4. **部分与模糊回答。** 用户只答两题，第三题保持待讨论；含义不明的“可以”只触发必要澄清，不能批量采纳其他内容。
5. **边界场景。** 给出与本模块有关的具体例子，暴露真实矛盾；用户明确修正后，后续问题及现行规则使用修正结果，旧决定保留可追溯关系。
6. **及时保存与恢复。** 在已授权环境中，回答后未结束模块就中断，再恢复；已采纳内容可从记录读取，不丢失、不重问，也不会重复创建同一次决定。
7. **轻量同步。** 模块内多次回答先维护模块决定记录，收敛后统一整理规格；相关规则只在权威位置更新，无关管理资料和其他模块内容保持不变。检查实际写入范围，不以文件越少越好作为唯一判断。
8. **未同步与失败。** 分别覆盖记录已保存但基线未同步、保存失败和只读讨论；报告准确区分状态，不宣称已保存、已同步或已实现。
9. **长问题组。** 超出单批预算时按完整问题分批，编号连续，每批题目与选项完整；对当前批的整体采纳不影响未展示的问题。
10. **事实与权限。** 可自行查明的事实由 AI 调查；只有依赖缺失事实的问题等待。项目写入沿既有通道与角色范围，不因节省步骤取消必需的回读或权限检查。
11. **文档用途。** 普通规则不强制生成独立 ADR，术语表只承载术语；重要且有真实取舍的决定按既有方法留存背景。
12. **检查分层。** 连续多轮仅新增本模块决定时，每轮都有保存前后检查，但不重复执行与改动无关的全项目检查；模块结束时，确实执行一次受影响范围的统一同步与核对。不能只在回复中声称已减少检查。
13. **复用失效。** 输入未变时不重复读取同一整份资料或重做已通过的检查；在外部改动引用目标、撤销授权、出现版本冲突或写入失败后，旧结果失效且相关复查实际执行。无关模块不因局部失败被全量重查。
14. **新设计入口与覆盖。** 从自然语言玩法和部分已定资料开始，形成范围与设计地图，沿用已知答案；适用领域有规则或明确缺口，不适用领域有理由，不为填模板新增系统，不把后续愿景自动放进当前版本。
15. **AI 参与设计。** 面对体验描述与“不知道”，提出有理由的具体规则、计算或验证建议；不把调查责任推回用户，不将“轻松”直接定为“无失败”，临时假设不进入已采纳基线。
16. **模块规格完整性。** 在固定小型游戏场景中，检查必要模块的目的、对象、触发、规则、边界、数值、反馈、数据和验收内容；缺少关键规则时准确报告未完成，不能以填满模板通过。
17. **整体流程与文档交付。** 将模块组合成首次进入到再次进入的完整经历，植入一处资源或解锁矛盾并确认能够发现；最终四类交付内容可定位，现行规则一致，执行者不依赖聊天即可继续工作。
18. **阶段与证据。** 区分概念、原型规格和当前版本设计；已采纳但未试玩的规则仍标待验证，并说明是否阻断当前阶段。不会自动制作原型或报告手感、乐趣与市场效果已验证。
19. **变更识别。** 分别提供规格缺口、实现违背明确设计、设计本身需要优化及混合请求；分类和依据正确，实现偏差不会导致擅自修改原设计。
20. **变更目标与影响。** 从明确修改诉求提取对象、原因、改善目标与保留项；不重复询问已定选择，主动找出规则、经济、界面、内容、数据与验收的直接及间接影响，仅将真实取舍提交用户。
21. **阶段适配。** 用只有设计、已开发有存档、已发布有玩家进度三个夹具检查适用范围；未知不当作不存在，不追问无关补偿，也不遗漏实际存在的数据或权益处理。
22. **删减闭合。** 删除同时承担奖励和引导作用的功能，检查作用取消、转移和简化保留三类处理；旧入口、引用和验收要求退出现行设计，历史仍保留，永久取消与本版不做不混淆，不自动增加同类替代功能。
23. **局部微调。** 输入已授权、无歧义且无连带影响的文案或提示调整，直接完成对应差异和必要核对，不强行提问、不重开设计地图、不修改无关模块。
24. **方向变化与旧证据。** 调整某一核心方向后，仅重新讨论和同步受影响模块，其他有效决定保留；对应旧验证结果仍属于旧版本，不能直接证明新方案已经通过。
25. **变更交付与授权。** 更新后的有效设计与简短变更记录一致，含目标、前后差异、影响和待验证方法；设计完成、实际保存、同步、实现、验证分别有依据。只授权设计文档修改时，产品代码、资源、用户数据及外部系统不发生变更。

### 步骤与耗时对比

效率验收复用上述高层交互入口，不另建测试接口。以固定的完整模块场景比较优化前版本与候选版本：包含一组无相互依赖的问题、至少一项后续依赖、部分回答后补答、多轮决定保存及最后的规格同步。用户答案按相同语义提供；两种流程的题号或分组不同不能改变最终要完成的决定和成果范围。

分别设置新设计与已有设计变更两类固定场景，独立报告，不混合均值掩盖某一类退化。新设计场景覆盖范围提取、轻量设计地图、完整核心模块和约定范围交付；变更场景覆盖当前设计读取、影响分析、一次有关联引用的调整或删减、简短变更记录与最终同步。局部无歧义微调另按场景 23 核对最小步骤，防止小修改走完整访谈。若优化前版本无法完成相同的成果语义与范围，说明该场景不可直接比较，不用缺失工作的短耗时作为基准，也不据此宣称提速。

固定模型及推理设置、宿主、工具和权限、起始项目副本、已有记录、需要完成的决定集合及正确性标准；各次使用新的相同起始副本和可比较的会话状态。记录两个被测版本的内容标识，交错执行先后顺序。每种模式采集三组有效配对，保留每次原始时间与结果；外部故障、缺失记录、失败及重试必须单列。候选自身的错误属于失败，不能作为环境异常剔除。

统一计时口径：

| 指标 | 起止与累计方式 |
| --- | --- |
| 本轮决定保存用时 | 从本轮用户完整回答到达开始，到该轮已明确决定实际保存并完成必要回读检查为止；没有采纳内容的轮次标为不适用，不伪造零耗时样本 |
| 本轮继续讨论等待 | 从用户完整回答到达开始，到下一组完整问题或本轮明确结果已经呈现为止；第一句进度提示不算完成，分批问题以本轮应展示部分全部呈现为准 |
| 完整模块处理用时 | 从初始模块请求到达，到最终规格同步、必要检查和完成回复结束；扣除有明确起止记录的用户思考与输入等待，计入 AI 处理、工具和网络等待、失败重试及最终同步 |
| 模块累计决定保存用时 | 汇总同一完整模块各次决定保存用时，避免把单题与整组回答的单轮时长直接相比 |

同时记录讨论回合数、实际资料读取次数及内容规模、文档写入次数及涉及文件数、检查执行次数和工具调用数。区分必要操作和输入未变的重复操作；一个工具调用内部操作多个文件时仍分别计数，合并工具调用不能冒充减少实际文件操作。Token 用量在可取得可靠记录时附上，缺失标为未知。

以宿主与工具实际事件时间、写入回读结果和完整输出作为依据，不能用助手自己填写的估计时长作证。记录处理与同步不得在计时结束后继续执行；如果有未完成的保存或同步，本次只能记为未完成。

### 效率通过条件

- 正确性场景全部通过，采纳内容、未决项、历史、权限和最终成果范围保持完整；不能以漏记录、少检查必要条件或推迟同步换取速度。
- 至少一项可核实的重复步骤数量减少；未改善或增加的指标如实列出并说明原因。新增决定不应触发无关全量检查，同一输入已通过的检查不得无理由重复。
- 每种模式的三组有效配对中，候选的完整模块处理用时中位数和模块累计决定保存用时中位数均低于优化前；两项指标各自至少两组配对变快，并展示全部单次结果。不能只挑最快的一次；两种模式均满足各项条件后才能报告统一框架效率验收通过。
- 缺少可比较样本、计时边界不完整或存在明显环境干扰时，结论为“效率尚未验证”。若步骤减少但耗时未满足条件，只能报告步骤改善，不能将本项验收判为通过。

不预设节省时间或 Token 的百分比，也不凭小样本保证所有任务都更快。上述条件用于本次固定场景的验收；实际差值、比率及限制在实施后的报告中据实给出。本轮只补充规格，不运行该效率验收。
