# Game-Status 检查细则

本文件是 [SKILL.md](../SKILL.md) 的分类、输出与失败场景参考。执行检查时读取;只读检查不需要读取包内 writing-for-agents。

## 读取顺序与入口判定

1. `<项目根>/docs/mygamestudio/INDEX.md` 是唯一默认资料入口。项目若在其他位置维护入口,以 CONFIG 或项目约定中明确记录的入口为准;两者都缺失时按"未接入"处理。
2. INDEX 中每行"读取条件 → 资料位置"逐条解析:指向的文件存在则读取,不存在或不可读记为缺口,不视为已读,也不猜测替代位置。
3. 协作配置(CONFIG)给出任务后端与位置、标签映射、文档映射:
   - 后端为 local-markdown 时,任务记录位于其声明的任务根(默认 `docs/mygamestudio/work/`),每个任务一个目录,`task.md` 为工作请求与状态。
   - CONFIG 声明的后端与实际存在的记录不一致(例如声明 github-issues 但任务根下还有本地任务)时,记为配置冲突:存在两个当前任务来源,状态报告不能只取其一冒充完整。
4. 项目约定(PROJECT)给出当前目标、范围、本轮成果与安排、当前状态与待决事项、基线版本。

## 任务分类规则

对任务后端中每个任务,先读 `task.md`(分流、进度、验收方式、依赖、结果索引),再核对结果索引指向的 results 与 evidence 是否实际存在并支持结论。按以下顺序判定,命中即停:

| 分类 | 判定条件 | 典型依据 |
| --- | --- | --- |
| 已完成 | 进度为已完成,且验收方式要求的证据实际存在并支持结论;要求人工验收的,已有人工反馈记录 | task.md + results/ + evidence/ |
| 待验收 | 实际成果存在(结果记录或可定位产物),但验收方式要求的独立审查或人工反馈缺失、未进行 | task.md + results/,evidence 缺失 |
| 受阻 | 记录了阻塞原因或依赖,且依赖未满足;或进度标记暂停并给出原因 | task.md 的依赖/阻塞字段 |
| 待做 | 尚未开始,或已分流待执行(如 ready-for-agent/ready-for-human)且无成果记录 | task.md |
| 未知/存疑 | 记录缺失、结果索引指向的文件不存在、进度与证据矛盾、引用的基线版本与当前基线不一致、或与 CONFIG/PROJECT 声明冲突 | 逐条列出矛盾双方 |

规则:

- 缺失记录不得解释为完成;没有结果与证据时,"进度:已完成"只是声明,归入待验收或存疑。
- 分流状态回答"请求交给谁",进度回答"做到哪";两者分开报告,不用分流推断进度。
- 依据过时:任务引用的基线版本低于当前基线版本时,单独列入"基线核对",并说明其结论仍基于旧版本事实,不自动作废。

## 基线核对

对照 PROJECT 与设计基线(GAME_DESIGN 等)声明的当前版本,检查:任务结果引用的版本、evidence 引用的版本、PROJECT"当前状态"引用的版本。不一致项列入报告"基线与依据核对",说明哪一方较新、影响哪些结论。

核心基线若登记了内容指纹(内容指纹/归一指纹),经统一接口 `records/mgs_records.py baseline --project <项目根>` 核对:内容与登记指纹不符说明发生过版本号未同步的手工修改——疑似格式修正(仅空白差异)不影响既有结论,如实注明即可;实质变更(字符增删)则把引用该基线的结论列入"未知与存疑"的依据过时项,交回统筹处理,不自行改判成果与证据的有效性。

## 报告结构

输出为中文 Markdown,固定以下结构:

```
## 项目状态报告:<项目名>

只读检查:本次未写入、未创建、未删除任何项目文件。
检查时间:<时间>;插件版本:<plugin.json 版本>;目标项目根:<路径>。

### 当前目标与范围
<引用 PROJECT 的当前目标、本轮包含/不包含,附文件路径>

### 已完成
<任务身份 + 一行事实 + 依据路径;无则写"无">

### 待做
<同上>

### 待验收
<同上;注明等待谁的什么验收>

### 受阻
<同上;注明阻塞原因与依赖>

### 未知与存疑
<同上;注明缺失或矛盾的具体记录>

### 基线与依据核对
<版本一致性、过时项、冲突;无则写"未发现不一致">

### 缺口
<未能读取的入口/文件、配置缺口;无则写"无">

### 可接续的工作
<从记录推导的下一步,注明仍需谁决定;不替用户决定>

### 本次读取清单
项目资料:
<实际读取的项目文件路径>

检查规则(包内材料,注明从安装位置读取):
<实际读取的技能说明、检查细则与包内合同;未读取的注明原因>

未能读取或不存在:
<路径及原因>
```

## 失败场景

- **项目未接入**:`docs/mygamestudio/` 不存在或无 INDEX.md。输出专用的未接入缺口报告,不使用五分类小节结构:开头声明"项目未接入 MyGameStudio";列出接入所需的最小内容(资料入口 INDEX、协作配置 CONFIG、项目约定 PROJECT、任务记录位置);明确本报告无法给出项目状态、所有分类均为无法判断,不虚构任何分类结论;提示接入属 Game-Init 职责且当前包未提供。不得扫描项目源码后冒充状态报告。检查到此结束。
- **资料冲突**:入口指向缺失文件、CONFIG 与实际记录矛盾、基线版本不一致。逐条列出冲突双方与影响;受影响任务的分类归入"未知/存疑"或按规则降级,并在"缺口"中说明需要谁澄清。
- **读取受限**:文件存在但不可读(权限、编码损坏)。如实记录,不猜测内容。
