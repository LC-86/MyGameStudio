# Game-Design:产品与体验方案讨论

方案设计角色的讨论入口:把本轮问题组织成可决定的方案。按问题形态选分支:**局部功能**问题走质询分支收紧设计;**多项未决问题**走决策地图分支先图后决。可以只讨论不写入;讨论产出的采纳内容由 Game-Spec(或等效的明确文档步骤)同步基线,本入口不写产品基线。

## 分支选择(内部方法按问题需要加载)

读取问题后判断,只加载对应分支需要的内部方法;这些方法是包内固定版本材料,**不提供同名公共入口**:

- **质询分支(局部功能)**:范围清楚、疑问集中在少数决定点。读取 [grill-with-docs](../../internal/methods/grill-with-docs/SKILL.md);它组合的 [grilling](../../internal/methods/grilling/SKILL.md)(按轮次问前沿问题)与 [domain-modeling](../../internal/methods/domain-modeling/SKILL.md)(术语与边界场景)按其指引使用。
- **决策地图分支(多项未决问题)**:想法大、雾多、决定点互相牵连。读取 [wayfinder](../../internal/methods/wayfinder/SKILL.md);其研究类工单配合 [research](../../internal/methods/research/SKILL.md) 使用,原型类验证走 Game-Prototype,不另建执行入口。
- 两类问题都需要外部事实时,先调查再提问:能自己查的事实(代码、文档、可本地核实的一手资料)自己查并记出处,不向开发者问可以查到的东西;查不到的列为待调查项。

## 任务识别

开始讨论前先核对请求、当前有效设计、已有决定和实际项目阶段,再选择处理方式并在可见回复中简短说明依据。能自行查明的情况不要求用户另填模式表。不新增公共 Skill。

- 只有想法或现行设计未覆盖本轮请求 → 新设计
- 已有设计未写清必要规则 → 补充规格,沿用已有明确结论
- 优化、调整或删减已定设计 → 设计变更
- 设计已明确但实现不符 → 实现偏差:标明依据,交给后续修复,不擅自改写设计迁就实现
- 同一请求含多类问题 → 混合请求,分别处理

已授权、无歧义且无连带影响的局部文案或提示调整走简短流程:直接完成差异与必要核对,不强行提问,不重开设计地图。未授权的产品改动与外部发布不执行。

## 检查时机与复用（减少重复读取与检查）

同目录 [checks.py](checks.py) 是**检查时机与复用接缝**(状态基元与判定规则见 [check_state.py](check_state.py),证据与报告见 [check_evidence.py](check_evidence.py)):按「读取与检查时机」统一新设计成稿与已有设计变更两条流程的读取、保存与收敛检查,不新增独立缓存服务、后台监控或持久化系统——会话就是全部状态。两个模式都从 `begin` 建立会话,轮次与保存、收敛、失效都经同一组 interface 记录。

- **开始或恢复**(`begin`):核对模式、项目阶段、目标、授权、相关决定与未决项,从现有入口定位资料;缺口如实报告,无关模块不进入核对范围。恢复时读取实际状态,不只凭聊天记忆。
- **读取计划**(`plan_reads` / `record_read`):按当前模块与必要依赖只展开相关内容;已读资料与已通过检查在**内容身份**(路径 + 内容指纹/SHA-256)与适用范围未变时复用,不能仅以修改时间未变判断有效;新会话只复用可核验的既有读取结果,否则补读。同一目的检查合并执行,不每轮临时生成一套脚本或逐文件重复调用。
- **每轮保存前后**:保存前(`before_save`)核对实际答案、采纳范围、来源、矛盾、当前可写范围及目标版本;保存后(`after_save`)回读核对本轮完整、无重复、历史、同步状态与新改引用。连续多轮只新增本模块决定且未改核心基线时,不重跑全项目基线、全部链接或无关远端任务检查;跳过项如实记入台账。既有必需检查(保存确认、一致性、权限与版本)不被取消。
- **模块收敛**(`converge`):汇总未同步决定,按真实影响做**一次**统一核对;确有跨模块或全局影响才扩大到对应范围。`spec_draft`/`full_design`/`change_flow`/`removal` 的 `apply_*` 都接受可选 `session`,在落盘前收敛核对、逐文件计数写入,落盘后回读。
- **失效触发**(`invalidate`):外部修改引用目标、撤销授权、版本冲突、写入失败、断链或证据不足时作废旧结果,**只重新读取和检查受影响部分**,无关模块不因局部失败被全量重查。每次写入的权限和版本校验仍由受控通道**逐次**执行(见 `gate_commit.py`),复用只适用于读取理解与已通过检查结果,**不缓存也不跳过写入校验**。
- **纯讨论**:未获保存授权时不运行写入与落盘检查,回复明确**尚未保存**;保存失败时保留采纳事实并准确报告,先处理相关问题。日常回复只保留保存结果、必要限制与下一组问题,检查明细经 `summary`/`ledger` 在已有记录中简短保留,`measure` 给出实际读取、写入、检查与调用计数(一条调用内部的多次文件操作仍分别计数)。

本接缝是被其上各入口 import 的包内模块,不提供独立命令行入口;会话经 `apply_*` 的 `session` 参数与各步骤串联。

## 模块问答

确有待决定问题时,质询可见回复在 grilling 方法之上采用本入口固定结构。同目录 [rounds.py](rounds.py) 是高层入口的结构接缝:`run_round` 把本轮请求、已读事实、题目目录和开发者回答变成可见回复与决定/未决对应;`inspect_reply` 核对实际回复文本。发出前必须对可见回复运行核对;只检查本文件含关键词不能判为交互通过。

```
python3 <本技能目录>/rounds.py run < turn.json
```

轮次开头写明目标、模块、轮次和本批问题数量。每题依次为「❓ Q编号｜问题标题」、问题正文、「选项」及 A/B 分项、「➡️ 我的建议」及理由;题间空行加 `---`。开放问题允许自由回答,不凑选项。依赖未定答案或缺失事实的问题留到后续;不混入无关模块。优先处理全局影响、返工风险和阻断问题。

遵守每条消息及单次工具参数不超过 6,000 字符、每批约 4,000 字符;按完整问题分批,编号连续。整体采纳只覆盖已展示且指代明确的建议。未回答、含义不明或未展示的内容不补默认值。已明确答案保留,只澄清有歧义的部分;同一题多次作答按原文顺序、以最后一条为准,逐题否定、排除或明确暂不决定视为例外,覆盖整体采纳并保持待讨论。题目身份按当前模块解析,其他模块的同编号问题不进入本轮展示、采纳与保存。

「不知道」或体验目标须给出有理由的方案、计算、例子或验证问题;临时假设保持提案身份,不进入已采纳。按需显示 ✅ 已确定、⏳ 待讨论、💡 我的提案、🧪 待验证、🚫 当前不做;空类别不输出。边界场景暴露矛盾并明确修正后,后续问题使用修正结果。

## 决定保存与恢复

同目录 [decisions.py](decisions.py) 是保存接缝(记录格式见 [decision_records.py](decision_records.py),命令行见 [decisions_cli.py](decisions_cli.py)),与 rounds.py 串联:`plan_save` 把本轮可见题目与作答整理为模块最小决定记录(模块与问题关联、采纳内容、决定者与日期、用户回复及建议出处、影响、未决项、基线同步状态),给出目标版本与写入前核对;`apply_save` 经**受控通道**(mgs-gate 的 `mgs_write`,或同一条 GateService 通道)提交并逐次核对当前授权与目标版本,再**回读**确认本轮完整、历史未丢失、无重复、同步状态正确——没有回读成功不得称为已保存,也不换通道绕过保障。`plan_sync` 只在有**同步授权**时把指定决定标记为已同步;`restore_from_records` 从实际记录恢复已定、未决与待同步内容,供后续轮次沿用而不是重问。

```
python3 <本技能目录>/decisions_cli.py plan|save|sync|restore ...
```

- 每次收到明确答案后,先保存本轮最小决定记录,再进入依赖它的下一轮;按模块沿用已有记录位置(默认 CONFIG 的「术语、ADR 与历史」行),不为每个 Q 新建文件或工单。
- 纯讨论且未获写入授权时保持只读:`plan_save` 返回 `read_only`,回复中明确**尚未保存**;已采纳事实保留,等授权后再保存。
- 助手建议、候选方案与临时假设保持其身份,不冒充用户决定;同一次回答重复处理不重复创建决定;用户改口时保留旧含义与替代关系,不覆盖其他有效决定。
- 状态分别表达:已采纳 / 已保存 / 已同步核心基线 / 已实现 / 已验证。已保存但未同步的内容保持可定位(`to_sync`),不能只读旧基线后重问或据此开工。
- 写入被拒、版本冲突、保存失败时按实际 `decision` / `rule_stage` / `reason` 原样报告,不重试绕过;授权已撤销或缓存视图都不能替代逐次权限与版本校验。中断恢复先读实际记录与版本,再只续未完成部分。

## 模块规格交接

模块收敛后,同目录 [spec_draft.py](spec_draft.py) 是交接接缝(命令行见 [spec_draft_cli.py](spec_draft_cli.py),九类渲染与缺口核对见 [spec_render.py](spec_render.py),版本与同步范围见 [spec_sync.py](spec_sync.py),报告措辞见 [spec_report.py](spec_report.py)):`plan_handoff` **消费票 03 的已采纳决定记录**(沿用 `decision_records` 的同一解释与 `restore_from_records` 的同一口径),汇总该模块已采纳且未同步的决定,排除候选与临时假设,把九类内容整理为可交接模块规格——设计目的、参与对象、前提与触发、正常规则、例外与边界、数值与配置、玩家反馈、数据与持续性、验收方式;不适用的类别写明理由,关键行为不以「合理、适中」类形容词代替。数值说明单位、范围、计算或取整与依据,已定值与候选试验值分开;验收含初始条件、玩家操作与预期结果,主观体验列出验证问题、验证方法及是否阻断当前阶段。

```
python3 <本技能目录>/spec_draft_cli.py plan|apply|verify ...
```

- **未完成如实报告**:阻断当前交接的关键缺口(缺关键规则、未决项无影响说明等)返回 `incomplete`,不产出可落盘内容、不用默认值补齐;未决项与延期事项连同影响保留,候选方案保持候选身份。
- **只同步实际受影响的资料**:模块规格、核心基线引用与版本、术语表、决定记录的同步状态;其他模块与无关管理资料保持零改动(`untouched`)。具体规则集中维护在模块规格,基线只引用、不重复规则正文。
- **沿用既有 Game-Spec 文档映射与版本纪律**:实质变化才递增基线版本并登记双指纹与采纳依据;纯格式修正不触发新版本、不算新产品要求,报告单独注明。回读核对新旧规则、采纳来源、未决项与历史替代关系。
- **术语与重要决定**:已明确术语补进已有术语表;只有改变成本高、缺背景会令人困惑、存在真实取舍三项同时成立才单独记录重要决定背景,普通规则留在模块规格。
- **边界**:目标或范围变化只输出**统筹同步交接**(建议显式调用 Game-Producer),不代写 PROJECT 等管理资料;缺写入或同步授权时明确留下待同步项,不自行签发凭据。模块可交接不等于全游戏完成或体验已验证:没有原型或试玩证据不报告验证通过,也不自动启动制作。
- 写入与票 03 的 `apply_save` 同一条受控通道:`apply_handoff` 逐文件提交、逐次核对授权与目标版本,每个文件写入后回读;没有回读成功不得称为已同步。

## 已有设计变更（补充、优化、调整）

开发者要在已定设计上补充规格、优化或调整时,同目录 [change_flow.py](change_flow.py) 是变更接缝(命令行见 [change_flow_cli.py](change_flow_cli.py),影响与阶段分析见 [change_impact.py](change_impact.py),材料整理见 [change_input.py](change_input.py),交付渲染见 [change_render.py](change_render.py),报告措辞见 [change_report.py](change_report.py)),与新设计共用 Game-Spec 与记录通路,**不新建公共入口**。`plan_change` 先从当前有效设计提取**四项变更说明**——修改对象、原因、预期改善、需要保留的内容;开发者只提出问题时按待讨论处理,已经作出修改决定时直接进入后续处理讨论,**不重复询问是否采纳原决定**;确有重大新影响时说明依据,只处理新增取舍。

同目录 [change_impact.py](change_impact.py) 的 `analyze` 沿**实际依赖**(不以文件相邻为边界)追踪玩法规则、成长资源、界面引导、内容资产、数据及验收的直接与间接影响,分成**必须同步**、**需要开发者取舍**、**不受影响**;取舍项带候选处理方式与推荐,成为新增取舍问题。有取舍未定时只提问、不写入。

```
python3 <本技能目录>/change_flow_cli.py plan|apply|verify ...
```

- **阶段适配**:`stage_check` 按**只有设计，尚未实现**／**已开发，尚未发布**／**已发布，有实际玩家**三档给出需要核对的对象(规则、流程、数值、内容清单、验收,及实现、界面、资源、测试、已有数据、存档兼容、玩家进度、待领资源、已有权益、迁移、发布安排)。存在性分「存在、不在、未核实」:阶段未知不得当作对象不存在,查得到的不追问;**核实为不存在**的补偿或迁移不追问。只讨论或只改文档的任务不自动执行迁移、删代码或发布。
- **变更深度**:局部明确微调在授权内直接处理;模块调整用一组或多组关键取舍问题;结构性修改检查受影响的多个模块并按需提出验证;方向性变化重新审视相关核心方向,其余有效决定继续保留。无关问题不顺手扩成全面重做。
- **候选与推演**:每个候选说明改什么、保留什么、预期改善与代价;事实调查、计算与关联分析由 AI 承担,不把技术细节转成用户逐项作答的问题。只换名或转移复杂度**不构成改善证据**,不得报告为原问题已解决。用新玩家、已有进度、资源不足、退出、相关路径等适用场景推演;数值/流程**自洽性**与实际**体验改善**分开,需要试玩时保留具体方法与是否阻断当前阶段。
- **同步与历史**:获准同步后更新真正受影响的当前设计与验收依据,失效规则与引用**退出现行版本**,历史与替代关系保留在模块规格的历史段;不受影响内容不动,不重造整套文档。写入与票 03～05 同一条受控通道逐文件提交并回读,没有回读成功不得称为已保存或已同步。
- **简短变更记录**:含目标与原因、旧设计到新设计、影响范围、采纳来源、待验证方法,以及保存、同步、实现、验证状态;`verify_change` 回读核对当前设计保留未受影响内容、新规则就位、旧规则与引用退出、版本与双指纹已登记。
- **旧证据与完成**:受影响的旧验证结果标明**原适用版本**,不能证明新方案已通过;缺少实际运行或效果证据时不称实现或优化效果完成。关键取舍未明确、关联未同步或仍有未说明的关键断点时不宣布设计变更完成。删减功能的原作用处理(取消、转移、简化保留)由后续删减入口深化,本接缝为它保留接缝。

## 功能删减（完整处理原作用与残留依赖）

删减按「已有设计变更」同一流程走,并完整处理原功能承担的作用。同目录 [removal.py](removal.py) 是删减接缝(命令行见 [removal_cli.py](removal_cli.py),原作用盘点与残留依赖见 [removal_impact.py](removal_impact.py)),沿用票 06 的四项变更说明、影响分析、阶段核对、受控写入与简短变更记录,**不另造记录体系、不新建公共入口**。`plan_removal` 先查清原作用再整理,开发者**已明确删除方向时不反复询问是否删除**——只对尚未明确且影响体验的处理方式提问(编号接当前模块问题组)。

```
python3 <本技能目录>/removal_cli.py plan|apply|verify ...
```

- **原作用盘点**:奖励来源与成长节奏、行动引导、解锁条件、入口、教程、内容、数据、验收八个方面逐项写明原功能实际承担的作用与关联的现行设计元素;缺项如实报告,不因目录齐全判为完成。
- **三类作用处理**:对每项原作用分别按**一起取消**、**转移给已有系统**或**更简单方式保留**处理;不强制每个被删功能都有替代品,也不接受以实质相同的功能换个名字恢复原有负担(如移除每日任务后自动添加每日目标)。
- **残留依赖检查**:沿实际依赖追踪直接与间接引用并写明经由路径,分为**一起取消**、**需要重新配置**与**不受影响**;失效规则、旧入口、旧引用与旧验收要求退出当前有效版本,历史与替代关系保留在规格历史段,不受影响内容不动。
- **数据与权益**:按**真实项目阶段**核对已有存档、玩家进度、待领资源与权益。存在的给处理方案(保留读取、迁移或清理),核实为不存在的**不机械讨论**补偿或迁移,未知的**先核实**再判断;处理方案与实际迁移、清理、退款行为保持**授权分离**——需另行授权的动作单列,本入口不执行。
- **取消范围**:分别记录**正式取消**、**当前版本不做**与**已明确承诺的后续范围**;删除不自动转成未来任务,延期不误报为永久取消,已承诺事项写明内容与来源。
- **交付与状态**:更新后的设计与简短变更记录一致,能看清删掉什么、原因、原作用如何处理、关联变化与待验证方法;`verify_removal` 回读核对失效规则退出正文、作用处理与取消范围在记录中就位。**设计完成不代表实现或效果完成**,实际删除代码、资源或清理用户数据需**另行授权**;仅授权文档处理时产品代码、资源与用户数据不动。

## 完整设计成稿（新设计模式）

从开发者描述的玩法片段、画面、操作、感受与提供的参考开始;已有项目先读取可用资料和已定内容,不要求用策划术语重新解释。同目录 [coverage_map.py](coverage_map.py) 整理已知内容与**十二领域覆盖地图**(项目目标与边界、核心吸引力、核心玩法与决策、完整游玩过程、系统与相互关系、成长与资源流动、内容与叙事、操作、界面与引导、美术、动画与声音、商业化与发布需求、技术与数据约束、版本范围与验收):逐项给出适用性、状态及已有规则或缺口/未知定位;不适用须有理由,未查清不得冒充不适用,不为填模板新增系统。地图用于查漏与推进:不一次抛出全套问卷、不每轮全文重述、不要求每个领域新建文件。完整愿景、当前成稿版本、后续方向与范围外内容分开保存,当前范围不足时只澄清必要取舍,不把全部愿景列入首发任务。推进焦点按阻断、全局影响与返工风险排序;AI 主动提出有理由的规则、数值与边界方案,保持提案身份。

同目录 [journey.py](journey.py) 按玩家视角推演首次进入、理解目标、操作、选择、结果、结束与再次进入,检查适用的资源耗尽、重复操作、退出、解锁与失败恢复(不适用写明理由),并检出资源收支与解锁要求等跨模块矛盾;发现矛盾先处理真实影响,不因目录齐全宣称完成。

模块规格收敛后,同目录 [full_design.py](full_design.py) 按交接标准核对:覆盖地图无未解释空缺、关键流程闭合、当前准备制作的必要规则可执行、范围与内容清楚、各处现行规则一致、关键未知有方法与影响说明。任一阻断缺口或未处理矛盾返回 `incomplete`,只报告草案或相应模块未完成,不产出可落盘内容;通过后组织**四类交付物**并提供清晰入口:游戏设计主文档(入口)、系统规则与数值(现行权威位置引用模块规格,同一规则只有一处权威维护位置)、内容与视听制作需求、版本与验证方案。沿用现行主文档与附表,不强制单文件、不重造文档体系。

```
python3 <本技能目录>/full_design_cli.py check|apply|verify ...
```

- **阶段与证据**:概念说明、原型所需规格与当前版本完整设计按所需成果判定,不按轮数或页数;需要原型或试玩的事项写清目标、方法与判定依据及**是否阻断当前阶段**;未获制作授权不自动实施,**不自动启动制作**;没有实际证据不报告体验或市场效果已验证,已采纳但未试玩的规则保持**待验证**。
- **写入**:与票 03/04 同一条受控通道逐文件提交并回读;只读时明确尚未保存、尚未同步;版本与验证方案列出阶段、范围、依赖、验收场景、风险与未知;管理资料与技术设计不被代写。

## 质询分支步骤

1. 先查事实:读项目资料(CONFIG/INDEX 指向的基线、相关实现与任务),把可自行核实的事实查清并记出处(文件与位置);事实与决定分开。读取与检查都经「检查时机与复用」的 `checks.begin`/`plan_reads` 建立会话,已读且内容身份未变的资料不重复加载。
2. 按「任务识别」分流后,整理当前模块设计树,用 `rounds.py` 的 `run_round` 组织本轮前沿;可见回复必须符合「模块问答」结构,每个问题附候选选项与取舍,并给出**助手建议**(明确标注为建议,不是决定);然后等开发者回答,不代答、不自问自答。
3. 开发者回答到达后经 `run_round` 对应到决定与未决项,用 `inspect_reply` 核对后再发出;保存经 `decisions.plan_save`/`apply_save` 并传入同一 `session`,由 `before_save`/`after_save` 完成保存前后核对;重组前沿,必要时进入下一轮;前沿清空即讨论收敛。
4. 收敛后整理本轮产出:先按「模块规格交接」用 `spec_draft.py` 汇总已采纳且未同步的决定,整理九类模块规格并只同步实际受影响的资料(核心基线经 Game-Spec 或等效明确文档步骤);仍有未决项时如实保留未决并注明影响,不补默认值。
5. 新设计模式在约定范围收敛后按「完整设计成稿」用 `full_design.py` 核对覆盖地图、玩家视角流程与交接标准,组织四类交付物;存在阻断缺口或未处理矛盾时报告未完成,不宣布整体完成。
6. 已定设计的补充、优化或调整按「已有设计变更」用 `change_flow.py`:提取四项变更说明与影响、按阶段核对对象、用场景推演,再经受控通道同步真正受影响的当前设计与简短变更记录。
7. 删减已有功能按「功能删减」用 `removal.py`:盘点原作用与关联、追踪残留依赖与间接引用、按三类处理原作用并区分取消范围,再经受控通道同步失效规则与变更记录;仅授权文档时不删代码、资源或用户数据。

## 决策地图分支步骤

1. 先与开发者确认**目的地**:这轮工作最终要交付什么(可执行规格、锁定决定还是方案变更);目的地决定范围。
2. 广度扫描未决问题:能精确表述的列为**决策工单**(每张一个决定点,标注类型:质询/研究,以及先后阻塞关系);还看不清的留在**未定雾区**;明确不在目的地内的放入**范围外**。
3. 制图轮只画图:地图与工单写入设计过程记录(见「写入」),**不代替开发者作任何决定,不顺手解决工单**。
4. 后续轮次按地图逐张解决:质询类工单收敛为开发者决定,研究类工单产出带出处的调查结论;每张工单解决后更新地图状态与对应决定/研究记录。

## 写入(经 mgs-gate)

- 写入落点按 CONFIG 文档映射的「术语、决定与历史」行(默认 `docs/mygamestudio/records/`),使用包内模板 `templates/records/`:
  - 决定记录:状态只写实际达成的(提议/已采纳/已被替代);未决内容明确标**未决**,不写成已采纳;候选方案与取舍保存在「选项与决定」过程记录,不进基线。
  - 研究记录:结论、依据表(事实或判断/原始来源/适用限制)、对当前工作的影响。
  - 决策地图:作为设计过程记录保存(如 `records/decision-map-<主题>.md`),含目的地、决策工单(类型/阻塞/状态/对当前工作的影响)、未定雾区、范围外。
- 采纳标注必须区分来源:开发者实际作出的决定注明**决定者与日期**;助手建议与候选方案保持其建议身份,不冒充用户决定。
- 不写 GAME_DESIGN 等产品基线;基线同步归 Game-Spec。发现目标或范围变化时不改 PROJECT,按共同合同的变更同步规则交回统筹。
- 每次文档写入前读取包内 writing-for-agents 并采用其方法;写入更新已有文件携带 `expected_sha256`,回读核对。

## 报告结构(固定)

```
## 设计讨论报告
### 分支与依据(本轮选择的分支及实际读取的内部方法)
### 研究事实(附出处;无则如实说明)
### 候选方案与取舍(助手建议明确标注)
### 开发者已作出的决定(仅列实际由开发者给出的;无则如实说明)
### 未决项(每项注明对当前工作的影响)
### 写入结果(本轮未写入时如实说明)
### 边界核对(要求核对时的原始输出;未要求时写"本次未执行")
```

## 边界

- 助手建议不冒充用户决定;未收到开发者明确回答的内容一律保持未决。
- 事实与决定分开:调查结论记出处,不自动采纳为产品要求。
- 只写设计过程与决定记录;越界写入被拒即停止该项并原样记录,不换路径重试。
- 任务说明要求边界核对时,按[受控写入协议](../../internal/protocols/gate-protocol.md)《越界探针》执行直接写探针与越界 `mgs_write` 探针,记录与未要求时的处理均按该节纪律。
- 凭据处理按[受控写入协议](../../internal/protocols/gate-protocol.md)《执行凭据》一节;需要人决定的事项原样保留,不用占位内容冒充已确定。
