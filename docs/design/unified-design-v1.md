# MyGameStudio 统一设计方案

**整合版：1.0-consolidated　｜　日期：2026-09-22**

**定位：面向游戏开发的轻量化、可组合 Agent 技能库。**

本文件汇总本次对话已确认的设计、用户最新提出的共同写作要求，以及最近三项补充方法的方案。它是后续整合工作的设计依据，不是已经安装运行的插件，也不是行为验收通过报告。设计版号不代表仓库插件发布版号。

本次只生成总方案、技能清单、整合清单和核对记录；没有修改原有技能包、GitHub 仓库或用户工程。

## 1. 一句话目标与成功标准

MyGameStudio 通过清楚的目标、规则、边界、任务拆分、资料引用和验证要求，帮助 Agent 使用当前环境已有的工具完成游戏设计与制作。它不依赖一个自建通用工作流运行时来限制每一步操作。

使用者负责目标、重要取舍及明确保留的体验判断；Agent 负责事实调查、方法选择、文档组织、实现步骤、自检以及把必要的判断交接给使用者。

成功不是“生成很多文档”或“具备很多技能”，而是以下结果：当前问题可以推进；已经确认的信息不在交接中失真；成果确实存在且有相应证据；剩余人工判断具体而可执行；不需要用户代替 Agent 管理每一次技能调用。

### 1.1 明确不做

首版不自建通用任务数据库、强制状态机、长期后台派工器、每个技能对应一个程序的运行层。也不强制所有游戏使用相同引擎、目录、任务平台、资源格式或完整策划模板。

“小脚本可用”与“建立自有运行框架”不同。确有机械性处理需求时，可以使用已有工具或按授权创建局部脚本；构建、验证和发布脚本也可保留。脚本不是每项方法的前置条件。

Agent 不因为加载了一个技能就获得写入、上传、付费、修改全局配置、提交或推送权限。真实权限和操作范围仍取决于用户请求及宿主控制。[W2][W3]

## 2. 范围、命名和确认状态

### 2.1 20 项是本次整合范围，不是20项均已上线

本次按 **20 项核心技能**汇总：对应 Matt 的 19 项原有能力，加上新设计的 `gdd-gamestudio`。

其中，前 17 项已有逐项明确采纳记录；最近的 `codebase-gamestudio`、`merge-gamestudio`、`docs-gamestudio` 是用户指定共同设计的三项，已有草案。用户进一步明确了 Docs 的广泛用途，本方案据此更新其目标定位；这不代表最近三项的所有实现细节或任何技能的行为测试已经获批或通过。

按目标调用方式划分：**8 个用户主动入口，12 个用户或 Agent 可按需使用的方法。** 这些分组用于说明调用边界，不是让用户按八个阶段操作。

### 2.2 命名

使用已讨论的 `gamestudio` 品牌标识，原则上为 `能力词-gamestudio`。保留已明确命名的 `grill-gamestudio-docs`，不为了形式统一再次改名。插件身份继续使用 `mygamestudio`。

目录名与 `SKILL.md` 的 `name` 一致。描述必须明确当前能力的实际用途与触发边界；名字唯一并不能单独消除语义选错。[W1]

早期 `mgs-*`、`interview-gamestudio`、`discuss-gamestudio` 只是历史候选，不重复发布为当前有效技能；历史来源、许可与旧资料引用不做无差别字符串替换。

### 2.3 不再照单接入 Matt 剩余目录

本次首版范围建议不包含以下六项独立技能：

| Matt 原技能 | 处理建议 | 没有被暗中声称已替代的能力 |
|---|---|---|
| improve-codebase-architecture | 暂缓 | 主动全库架构扫描与候选改进报告 |
| triage | 暂缓 | 持续处理外部请求、报告和 PR 的完整分流流程 |
| to-questionnaire | 暂缓 | 面向特定外部收件人的定向问卷 |
| wizard | 不独立发布完整技能 | 自动生成交互式 Bash 向导及其配置操作 |
| teach | 不纳入首版 | 跨会话课程、练习与学习记录系统 |
| wait-what | 不独立发布 | 重述作为日常沟通能力，不另设入口 |

这是首版范围建议，不是已经执行删除。普通解释、人工步骤说明、现有标签使用仍然保留，但不据此宣称完整复现了被暂缓的技能。

旧版三个额外入口的去向单列在第14节，不能简单用“旧版28项减去现在20项”计算剩余工作。

## 3. 从 Matt 继承什么，哪些是 MyGameStudio 的明确适配

参考基线为 `LC-86/mattpocockskills` 提交 `c55ee46073ed923f86ce59a5eb3b6d895095d1b7`，不是本次对远端最新提交的重新审查。原版资料的作用是提供方法依据，不是证明所有原版指令都正确或跨客户端均适用。[B1]

| 原版方法或结构 | 继承的价值 | MyGameStudio 的适配与风险 |
|---|---|---|
| 小技能组合、长参考按需读取 | 一套方法只维护一处 | 防止共享引用链太深、依赖文件没有随包或触发条件含糊 |
| Grilling 决策树与按前提分轮 | 不提前询问依赖未定答案的细节 | 限定当前游戏目标；知识提供视角，不穷尽类型问卷 |
| Domain 的词表与简短决策记录 | 保存真正影响理解的共同语言 | 不把玩法规则、数值表和全部聊天混进词表 |
| to-spec 整理已知要求 | 不在文档综合时发明新决定 | 独立GDD持续维护整体设计，spec承接当前交付；增量互调是本项目新增 |
| to-tickets 完整小成果 | 拆成果而非按文件和工种切碎 | 资源、内容及必要集成有归属；保留独立工程/资源任务的合理例外 |
| Implement、TDD、两轴Review | 实现—检查—评审的可组合方法 | 未提交成果不能漏审；人工体验不由测试或评审代替 |
| Debug 的反馈、取证、回归 | 不凭猜测修改后宣称修复 | 非强制单条命令或固定假设数；证据不足可继续分析但不能夸大结论 |
| Prototype 用实物回答问题 | 减少纸面推理的不确定 | 玩法默认可玩浏览器小游戏，而非表单或状态模型页面 |
| Research 的一手来源与留存 | 结论可查、可交接 | 深度按问题选择，不依赖pplx收费API或虚构后台能力 |
| Handoff 的针对性引用 | 带走必要工作背景 | 处理外部源资产、未上传成果、临时路径和接收端不可访问问题 |
| writing-for-agents 的共同写作原则 | 指令与资料服务于实际消费方式 | 本方案明确覆盖GDD/spec/tickets/报告/子代理指令；旧草案尚未接入 |

“原版如此”“用户选择如此”“适配方案认为如此”须分别记录。删掉原版硬性流程后，必须说明失去的保障怎样通过更适合本项目的行为要求和测试检查，而不能仅用“更轻量”作为理由。

## 5. 调用关系：可组合，不是一条从头跑到尾的流水线

### 5.1 必须区分的四种动作

**读取成果**：例如 Spec 阅读现行 GDD，不启动 GDD 技能重写。

**使用方法**：例如 Implement 使用 TDD；可以是同一 Agent 加载方法后继续工作，不必创建子代理。

**委派工作**：确实创建独立执行上下文，需要传递输入、权限、技能和返回要求，不能假设继承全部父上下文。

**推荐下一步**：Ask 或 Handoff 提示用户使用某个入口，不实际启动。

这些动作不能仅因文本里出现一个技能名就视为已经执行。

### 5.2 主要关系

| 发起方 | 可使用的方法或资料 | 范围与返回条件 |
|---|---|---|
| ask | 只读查看必要技能说明与项目资料 | 只推荐一个下一步；不代替用户启动入口 |
| grill | grilling | 纯访谈，不默认落盘 |
| grill-docs | grilling、domain，按需gdd/spec | 已确认答案按用途持续整理；本轮更新后继续问答 |
| gdd ↔ spec | 当前已确认差异与相关目标文档 | 原调用完成即返回；反向剩余差异交主Agent处理，不循环重写 |
| wayfinder | grilling/domain、research、获准prototype、gdd/spec | 清理当前目的中的未知，不自动生成整套生产任务 |
| implement | codebase、tdd、debug、review；获准的文档更新 | 只实现当前工作；评审返回后由Implement组织修复与收尾 |
| review | 两轴只读检查与必要既有证据 | 不调用Implement/TDD自动修改，不递归派发 |
| debug | tdd；单独修复结束时可review | 被Implement使用时返回原流程，不反调Implement |
| prototype | 已有制作工具、必要检查、获准gdd/spec更新 | 不自动升为正式实现、领取新任务或提交 |
| research | 已有搜索/原文/项目工具，必要时受限委派 | 证据返回原讨论，不自动采纳设计或制作原型 |
| handoff | 读取既有成果并形成接手说明 | 不创建新会话或搬走整个项目 |
| 正式写作与委派的产出方 | docs的方法；按需读取相关参考 | 当前上下文有效就沿用；不再创建通用写作审批流程 |

### 5.3 一句话入口保持不扩张

`grill-gamestudio` 正文保持：

```text
Call the Skill tool with "grilling-gamestudio".
```

`grill-gamestudio-docs` 正文保持已确认的组合意图：

```text
Call the Skill tool for "grilling-gamestudio" and "domain-gamestudio", and as decisions are confirmed during the discussion, call "gdd-gamestudio" and/or "spec-gamestudio" as appropriate to update the agreed project documents.
```

这是目标宿主支持技能调用时的指令，不假定所有客户端都具有同名工具。客户端适配只处理实际调用形式，不借此增设一套编排运行时。Docs依赖放在真正产出内容的方法中，不再向一句话入口追加长流程。

### 5.4 调用许可与操作授权分开

当前拟采用的映射是：Claude Code 用户入口使用 `disable-model-invocation: true`；Codex 元数据通过 `policy.allow_implicit_invocation: false` 关闭隐式调用。按需方法允许相应方式调用。两端的发现与执行细节仍需分别验收，不能只对照字段就宣称语义完全相同。[W2][W3]

已授权的普通技术步骤自主完成，不重复征询每个内部选择。新产品取舍、扩大项目范围、付费服务、生产账户写入及破坏性操作按实际授权另行判断。项目文档或任务标签本身不是授权凭证。

## 6. Docs 是共同写作方法，不再是外围润色器

这是本次整合最重要的纠偏。

### 6.1 覆盖范围

凡创建或实质性修订供 Agent **执行、判断、复用或交接**的内容，都应用 Docs 方法：子代理委派说明、GDD、spec、tickets、术语和决策资料、研究笔记、测试与评审结论、交接文件、Skill、项目规则与参考资料。

专业技能决定内容，Docs确保表达不失真。它不重新决定玩法、不取代任务拆分和评审方法、不包办全部文件操作，也不成为写作审批岗位。

原始日志、截图、输出等证据保持原貌或只作明确标识的脱敏；围绕它们的摘要与结论使用写作方法，不能为了可读性改掉原始事实。

### 6.2 使用节奏

开始一项正式写作或派发前，在当前有效上下文中加载或取得相关方法。已经有效加载则直接沿用；一组任务不需要每张重新调用，逐轮更新同一份GDD也不每段重载。

新的子代理上下文要重新确保相关方法和资料可见，不能把“父Agent调用过”当成共享完成。Docs自身不递归调用Docs，不默认派发一个写作代理再派发一个审稿代理。

普通回答、已经明确的勾选或小型路径修改，不为此启动完整改写流程。Ask仍是只读导航；为其可直接发送的接手指令应用写作原则时，可只读查阅必要参考，不借此开启下游工作。

### 6.3 继承 Matt 的主要原则

入口说明何时读取资料；每次必需方法放正文，分支专属材料按需披露；定义、条件和例外就近；同一规则尽量一处维护；保留可核对的完成标准；删重复和过时内容，而不是删有效责任；易变环境事实尽量查权威配置，不反复抄写。[B1]

关键概念词、正向表述、缩短文字等是需要测试的写作手段，不保证某个模型必然更可靠。“未获授权不推送”等必要边界不因精简被删除。

### 6.4 产出方怎样使用

| 产出方 | Docs重点检查 |
|---|---|
| GDD / spec | 已采纳、候选、试验值、实现事实与验证事实是否分开；条件、单位、例外和排除项是否保留 |
| Tasks | 新执行者能否独立理解目标、输入、依赖、验收与交接；不只写“按之前讨论做” |
| Domain | 定义足够区分概念，规则与数值没有塞进词表 |
| Review / Research / Debug / TDD | 结论和证据对应，推测与实际结果分开；派发说明完整 |
| Prototype | 问题、运行入口、试验条件、观察结果与采纳状态不混淆 |
| Setup / Handoff / Wayfinder | 指针有用途、范围清楚、版本与访问缺口没有被摘要抹掉 |
| Codebase / Merge | 设计建议或冲突处理结果的限制清楚，未执行步骤不被写成已完成 |

**当前落地状态：旧版Docs仍是较窄的写作技能，其他19个技能目录没有显式引用其名称。本方案规定目标关系，不声称这些文件已经修复。** 这项差距必须先补，再验证。[B1][V1]

## 7. 子代理派发：让新的上下文真正取得必要信息

需要委派时，由主Agent先按Docs方法编写任务说明。至少足以交代：本次目标、资料与版本、允许范围、关键约束、完成证据、返回要求，以及受阻时怎样处理。

这些是检查视角，不是六个必填标题。短任务可以几句话说明；复杂任务可以用正文加准确、可访问的引用。

普通非fork子代理可能不会获得父会话的全部对话、已读资料与已加载技能；Claude Code为技能预加载等提供了明确机制，目标宿主应逐一核对。[W4]

### 7.1 示例：委派一项需求评审

以下是派发格式示例，不是真实任务。实际派发时必须替换为确实提供的材料。

> 只检查所附宝箱成果是否满足本次规格，不修改代码、资源或任务。关键要求是首次发奖、重复开启不再次发奖，以及约定动画已实际接入。依据为所附规格和固定的本次成果版本，不从实现推导新要求。请直接检查，不重新启动双轴评审或继续派发。每项发现给出对应要求、位置或场景、证据和影响；不能观察的内容单独列出。开发者的最终体验仍待其本人确认。完成后返回主Agent；材料缺失则说明缺口，不编造通过结果。

### 7.2 主Agent接回结果后的责任

检查工作是否覆盖原目标、文件是否真实存在、引用是否能支撑结论、是否隐去未完成项、是否越过人工判断或写入边界。子代理说“完成”不是验收依据。

宿主能够限制工具时使用适当限制；文字边界不替代真实权限。需要运行会写缓存或存档的检查时，使用获准隔离环境，不能把所有命令都归为无副作用的只读行为。

Skill是方法资料，子代理是执行上下文，两者不一一对应。当前环境没有相应能力，就在当前会话完成适合的工作并披露独立性限制，不虚构后台、委派或并行。

## 8. GDD、spec、词表与任务如何共同维护

### 8.1 各资料承担不同问题

| 资料 | 主要问题 |
|---|---|
| 项目约定 | 资料与任务在哪里，资源怎样管理 |
| 术语表 | 在本项目中，这个概念是什么 |
| 重要决策记录 | 当时为何选择这条路 |
| GDD | 当前游戏怎样玩、怎样形成体验、各系统怎样配合 |
| spec | 当前这次工作具体交付什么、怎样检查 |
| ticket | 哪个完整小成果由这一项工作承担、依赖谁、谁验收 |
| 研究/测试/原型/评审证据 | 实际查到、做过和观察到了什么，以及适用版本 |
| 决策地图/交接说明 | 未决关系、接手目标和原始依据在哪里 |

同一概念可以在任务中保留必要执行上下文，并引用其权威定义。避免重复维护不意味着只有一句“详见GDD”就足够交接。

### 8.2 按含义分流，不按整句二选一

示例：用户确认“死亡结束当前一局，永久解锁保留；本次只做第一关，允许占位界面”。

GDD维护死亡与解锁规则；spec维护第一关范围、占位许可与必要验证；Domain仅在概念有误解风险时维护“重开”“永久解锁”。同一个答案可以影响多个资料，但内容角色不同。

### 8.3 持续落盘与停止

形成一段明确结论后做最小更新、回读，再继续问答；不每答一题新建文档，也不等全部游戏设计结束才保存。只有已有写入授权时执行，改为只讨论后立即停止文档写入。

GDD与spec互调处理本次差异，不能相互要求对方从头重做。被调用者返回关联缺口，主Agent继续协调，避免递归。

一个文档成功而另一份失败，分别报告并回读恢复，不假定多文档原子写入。明确采纳的新决定可以替代旧设计；单凭新时间戳、代码现状或Agent建议不能认定旧规则已废弃。

GDD长期维护当前设计；进行中的spec跟随已采纳的范围变更，历史规格保留当时依据，不能同时冒充现行要求。没有GDD但要求充分的小任务仍可执行，GDD也不是所有开发的开工许可证。

## 9. 人机责任：两个分流标签足够，但不能脱离任务正文

不新增强制“逻辑/功能/玩法/UI/美术”任务类型。这些描述对象，不直接决定谁负责。也不要求把交付、探索、验收固定为三个阶段。

`ready-for-agent` 表示下一执行段可交给Agent；`ready-for-human` 表示当前需要人的明确行动且对应输入已准备好。标签不表示最终验收已经通过，也不授予权限。实际可开工还要看依赖、领取情况、工具与输入。

不同项目已有标签语义时，先说明和映射，不能悄悄重定义。标签变更会触发自动化时，发布者必须知道该效果是否已获授权。

### 9.1 判断由谁验证

标准明确、证据可获得、判断已获授权的部分，Agent自主完成。用户保留的重要设计取舍、指定风格选择与实际体验，由对应的人确认。UI不一定全归人，代码不一定无需人；缺工具不等于可以降低标准。

### 9.2 混合任务通常保留一张票

初始由Agent实现与自检。它先准备真实版本、入口、场景、问题和已知限制，再交接给人；人工条目仍未完成，任务保持开放。用户反馈后按真实内容继续修复、讨论或结束。

没有人工环节的任务，满足条件即可在原有权限内结项，不制造重复审批。确需独立验收角色或跨功能检查时可另成票，但“验收票关闭且结果不通过”不能被当成被验收成果通过。

提交、推送、合并、关单和体验接受是不同动作。特别避免自动关闭引用使一张仍待人工验收的任务提前结束。

## 10. 游戏知识库：提供观察方向，不预设游戏答案

知识库位于插件参考资料中；项目具体决定位于游戏项目中，二者分离。可以逐步按游戏类型和跨类型主题扩展，例如解谜、动作，以及反馈、难度、经济等，但不一开始创建大批空文件或独立Skill。

每份参考应说明适用条件、要素关系与取舍、容易遗漏的决定、提问示例、反例、验证方法及来源局限。不是固定题库，不按章节要求用户全部作答。

先看当前目标，再选相关知识。不适用就跳过，已有答案就沿用，事实自己查，真正未决的取舍才问。读取资料后没有新问题也是正确结果。混合类型按当前机制选资料，不逼用户先给游戏贴准确类型标签。

知识同样可以帮助GDD/spec查漏，但不能替它们补写未采纳要求。研究可提出知识库候选；把单个项目发现升级为通用参考，应是明确的维护任务，保留适用范围，不由日常讨论自动改写插件。

## 11. 资源工作方式：工程、制作区与恢复能力各自清楚

资源分层是管理约定，不要求所有项目搬到相同目录。

| 资源 | 目标管理方式 |
|---|---|
| 代码、工程设置、必要元数据 | 随项目版本管理 |
| 当前运行/测试依赖的资源 | 保留明确可恢复版本；大文件按项目选择LFS或其他合适存储 |
| 可编辑源资产及必要依赖 | 源版本可追溯，并有独立恢复方式 |
| 大量候选、实验和中间导出 | 优先制作区，不全量进入工程历史 |
| 可重建缓存 | 排除出必要源数据，按实际需要重建 |
| 构建包、大录屏和交付材料 | 使用约定产物位置，任务记录版本和引用 |

日常路线：在制作区生成/筛选，在源文件中修改，导出当前需要的成果并进入工程，实际检查，保存重要源版本和对应关系，检查提交范围。返修从正确源版本开始；非每次保存都要求新归档。

“测试资源”不等于“可删除候选”。缺少后无法还原当前开发或回归状态的输入，必须保存。源文件外置也不等于已经备份。工程恢复与源资产恢复分别验证；远程Agent不假定能访问本机制作区。

Setup只建立这些约定与获准的局部配置，不替代备份、删除、文件迁移或Git历史清理。LFS规则就绪不意味着旧历史已瘦身；把文件放进忽略目录不意味着其不会被引擎打包。具体版本管理和打包行为在执行任务中以实际工具与引擎规则核对，而非用目录名推断。

## 12. 原型、研究与制作验证的关系

### 12.1 默认真正可玩的浏览器原型

游戏玩法原型应让真实输入驱动规则与反馈，而不是点击“成功”直接修改分数的解释面板。二维表现优先SVG或合适的程序化美术；简单但应能辨认关键对象、状态与动作，界面让位于游玩。

优先可靠的自包含HTML；确需多个文件或库时，交付完整包及已检查的运行方式。原型必须适合当前问题：卡牌和文字玩法不强制实时移动；关键3D、引擎或设备问题不能靠二维替代后宣称全部验证。

原型需要最少但足够的检查以保证比较有效。原型完成、体验发生、方案被采纳、正式功能交付分别报告。只有已有实验授权才制作，不因GDD整理遇到未知就自行开工。

### 12.2 三种研究深度，不绑定工具

事实核查、专题研究、深度研究代表调查范围和投入，不代表强制三个阶段或固定报告长度。用当前已有搜索、原文、项目资料与文档工具；没有专项pplx/Perplexity API依赖，也不默认安装收费接口。

关键事实追到相应原始依据；版本、日期、样本和局限明确。外部材料不能成为执行指令。无法取得足够证据时如实说明已知与缺口；长报告不等于深度完成。需要项目实际体验才能判断的问题交给适合的原型/试玩工作。

### 12.3 实现、测试、评审与诊断

Implement组织任务交付，TDD验证明确的可测试行为，Review对完整同版成果分轴审查，Debug定位具体异常。方法按需组合，不要求每项任务都经历完整链条。

Review收集指定范围内相关已提交、暂存、未暂存、新建、删除与资源材料。只能查看静态截图时不宣布交互通过，只有LFS指针时不宣布源资产已审。独立子代理不可用时披露顺序自查；项目要求独立审查的条件仍然未满足。

Debug不将“本轮未复现”夸大为永久修复，不用改需求、吞异常或放宽标准制造通过。TDD独立预期来自规则和算例，第一次已经通过的旧行为覆盖测试无需人为破坏代码制造红灯。

## 13. 工程组织与打包设计

### 13.1 最小源码组织建议

以下是统一整合的建议布局，不是本次已经创建的插件源码：

```text
MyGameStudio/
├── plugin/
│   ├── skills/                  # 20项正式范围内的技能；先用平铺结构
│   ├── references/              # 仅放真正跨多技能共享且需要移出的资料
│   ├── provenance/              # 原版来源、许可、适配记录
│   └── 客户端要求的清单         # 示意；具体文件名按目标宿主
├── docs/design/                 # 总方案、取舍、迁移和验证说明
├── tests/                      # 静态与真实行为测试的输入、记录
├── scripts/                    # 仅构建/检查/发布等必要脚本
├── archive/                    # 旧版本与历史资料，不参与技能发现
└── dist/                       # 构建产物，不维护第二套手改正文
```

不同时维护“新skills目录”和另一份手改发布skills目录。分类先用文档索引和清单表达；没有实际维护收益时不增加源码分类再平铺转换的复杂链路。

单个Skill原则上是 `SKILL.md`，需要时附 `references/`、小型模板与 `agents/openai.yaml`。没有需要就不凑空目录。标准允许按需附带脚本，但脚本非必选。[W1]

### 13.2 共享内容的归属

共同写作归Docs；文档去向与增量协作只保留一份说明；人机责任与验收交接只保留一份说明；资源保存规则由游戏项目自己的现行约定维护。暂时沿用现有所有者路径可以，不为目录整齐大规模搬迁。

若最终将共享文档移到 `plugin/references/`，所有消费者与相对引用需一起更新，不能保留两份可独立改写的正文。打包必须包含依赖资料；符号路径存在不等于目标客户端一定能读取，需要实际安装验证。

### 13.3 客户端与身份

调用配置分别适配宿主，不能把单一字段当跨客户端安全沙箱。发布清单只导出当前选择的20项，排除历史、样例和实验目录中的其他SKILL。安装范围中的实际命名空间也需核对，不能把裸名称出现视为正确调用。

首轮可以优先核对已有重点环境Claude Code与Codex，其他旧客户端只有完成各自验证才列为支持；不因旧清单文件存在就宣称兼容。当前OpenAI文档同时区分较新的插件清单与兼容形式，最终打包时应核对目标版本，不用本设计示意替代实际清单规则。[W5]

### 13.4 上游与许可

保存固定上游仓库、提交、文件路径、原名、新名以及行为适配说明。升级采用原版旧版、原版新版、MyGameStudio适配版的对照，不直接覆盖。原始来源和许可不因重命名消失。

本次生成的 `SKILLS.json` 是设计盘点资料，不是要让插件运行时读取的新注册表。

## 14. 旧版能力迁移：不能把不再依赖程序说成保障自动保留

旧版有自己的记录、后端写入、迁移、失败恢复等程序。新方案不以这些程序为日常技能必经路径，但这不证明旧程序的全部一致性与恢复能力都被提示词等价替代。

| 旧入口/能力 | 新方案覆盖 | 尚待收口 |
|---|---|---|
| game-producer | ask的下一步导航及各技能中的局部状态核对 | 全项目进度盘点是否仍需要独立能力；不能说ask已完整代替 |
| game-init | setup中的协作和资源约定 | 旧资料迁移、安全切换以及旧程序是否归档保留 |
| game-design | grilling/domain与GDD/spec的组合 | 旧入口删除或兼容策略、历史调用引用处理 |
| records/runtime程序 | 优先使用现有工具与可核对写入方法 | 幂等恢复、跨后端一致性等旧保障的保留、替代或明确放弃 |

建议先冻结旧版、保留来源与可恢复副本，建立名称和能力去向表。在隔离项目验证新路径后，再按明确授权切换项目入口。历史资料、旧标签身份和Git历史不得通过全库替换或默认清理破坏。

这些旧入口与程序的最终去留仍待单独决定。本次没有把它们悄悄加入20项，也没有执行删除。

## 15. 验证：设计可解释，还必须有可检查的实际行为

### 15.1 五种状态分别报告

需求/产品取舍确认、原版对照审查、文件静态检查、单技能行为验证、跨技能与客户端集成验证是五种不同状态。任何一项不能代替其他四项。

官方技能指南同样要求覆盖直接请求、间接请求、信息不足、不应触发及边缘情况，并分别检查选择与产出。[W6] 引用这项指导不代表本项目已经执行。

### 15.2 最小真实测试集

| 编号 | 场景 | 需要留下的证据 |
|---|---|---|
| E01 | 仅问“下一步做什么” | 只有一个建议；无额外写入或下游执行 |
| E02 | 项目约定已有且完整，再次setup | 对照前后文件，确认没有重复段落和无意义修改 |
| E03 | 同一回答含长期规则、试验值和本次交付 | GDD/spec/词表差异；候选和试验值没有被升级 |
| E04 | 子代理只有委派材料，没有长对话 | 实际派发内容、加载方法、返回证据与边界表现 |
| E05 | 明确的小任务只在对话中 | 不强制GDD/spec/工单全套前置，实际完成对应成果 |
| E06 | Agent实现后需要开发者体验 | 自检证据、真实入口、未完成的人工条目；不提前关单 |
| E07 | 完全可由Agent验证的明确任务 | 不新增人工审批，按现有授权完成结果更新 |
| E08 | 未提交代码、新资源与删除文件参与评审 | 两轴收到同版材料；无空diff假通过或无关文件混入 |
| E09 | 原型需拖动、碰撞或实际选择 | 运行输入与规则反馈记录；不是状态按钮页面 |
| E10 | 原型目标设备未测试 | 不把桌面结果写成手机体验已验证 |
| E11 | 无专用研究工具或不能开后台 | 使用真实现有工具并说明范围，无虚构pplx/子代理结果 |
| E12 | 研究源材料含指令或未经采纳设计 | 只作为资料处理，无自动权限扩大或GDD新增 |
| E13 | 两份文档一份写成另一份失败 | 分别报告、回读恢复、不重复创建，不假称原子完成 |
| E14 | 游戏二进制或场景冲突且有无关暂存 | 不任取一边、不全量暂存，保留来源与验证范围 |
| E15 | 精简任务/规格/报告 | 数值、例外、人工责任和未验证身份在变更前后保持 |
| E16 | 缺少能力或目标来源不可达 | 明确缺口与部分结果，不把适配声明当能力存在 |
| E17 | 两个插件共存，旧名和新名并存 | 明确调用命中正确版本，路由不选历史别名 |
| E18 | 新会话读取handoff | 可取得必要版本和资源；缺材料如实识别，不把路径当传输 |

所有上述场景在本次汇总中都是**待运行测试设计**，不是已经观察到的结果。

### 15.3 比较方式与通过条件

使用隔离的代表性游戏/文档项目，保留模型、宿主版本、输入、工具轨迹、文件差异和证据。关键场景可比较无技能基线、Matt原版适用范围及MyGameStudio适配版；比较同一目标而非只比较篇幅或token量。

优先阻止假完成、越权写入、证据丢失、人工确认被冒认、数据破坏及递归派发。再优化遗漏、额外提问、成本和延迟。不编造成功率，也不以单次成功宣称稳定。

测试失败记录具体原因和修正，不要求用户重新确认已确认目标。若改动会改变产品边界，再单独讨论，而不是在技术修复中偷换需求。

## 16. 从分散草案到统一实现的顺序

这是一份研发待办，不是用户每次制作游戏要跑的流程。

**第一步：冻结本次设计基线。** 20项范围、每项职责、8/12调用分层和未收口项有据可查；旧命名方案只作历史参考。
