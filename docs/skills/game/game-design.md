# Game-Design

围绕当前闭环讨论玩法、数值和体验。

## 什么时候用

三句话能说清“现在在玩什么”，但规则、手感或数值还没定，需要候选方案和取舍时。

## 什么时候不需要用

规则已经写进现行规格、只差改代码时，直接走任务与 `implement`。
路线又大又互相牵连时，应提示你调用 `wayfinder`，而不是在本入口里自动串调。

## 开始前准备什么

- 项目如已接入，准备好现行规格位置（常见为 `docs/mygamestudio/INDEX.md`）
- 本次只讨论哪个最小闭环，不要默认做全游戏设计

## 如何调用

```text
请使用 MyGameStudio 的 game-design。
我希望把当前体力系统从“按次数扣除”改成“随时间恢复”。
先读取已采纳规则，说明会影响哪些系统，再和我讨论候选方案与取舍。
这一轮不要修改正式规格，也不要开始编码。
```

## 一次调用会做什么

读取已采纳规则与阶段资料中真正受影响的模块，整理成组问题、影响面和试验值。开发者作答后可保存讨论过程。

## 会读取和修改什么

读取现行设计、历史讨论与包内阶段资料。讨论过程可写入记录；**正式规格必须等你调用 `to-spec`**。无显式请求不增加隔离原型。

## 你会得到什么

候选方案、取舍、试验值、已作出的决定、仍待验证的问题。助手建议不会冒充你的决定。

## 怎样判断成功

- 未受影响的系统没有被重新盘问一遍
- 未采纳的试验值没有写进正式规则
- 没有开始编码或自动调用 `implement`

## 一个游戏开发示例

体力从按次扣除改为随时间恢复：先列出影响（战斗节奏、道具、UI、存档），给出 2–3 个恢复曲线，等你选。示意见 [最小玩法闭环](../../../examples/first-playable-loop/README.md)。

## 常见问题与限制

- 核心玩法与重要取舍由你决定
- 不自动新增系统，不安排外部玩家
- 复用 `grilling` 与 `domain-modeling`，不另写一套同义方法

## 下一步通常用哪个技能

你主动调用 `to-spec`。范围大时再 `to-tickets`。

## 来源与本插件适配差异

本项目原创游戏入口。讨论记录不是现行规格。
