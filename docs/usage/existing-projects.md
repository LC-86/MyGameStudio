# 接入已有游戏项目

已有项目不需要重新组织一遍。要做的是把**你项目的真实约定**记下来，让 21 项技能沿用它们工作。

## 1. 先记录约定：`setup-gamestudio`

在游戏项目仓库里调用它。它会先探查已有约定，只补会影响工作的配置，提出最小修改清单等你确认，然后写入并回读。

```text
请使用 setup-gamestudio 为当前游戏项目补齐协作约定。

先探查项目已有的做法，提出建议清单等我确认，再做获准的最小文档修改并回读。
需要覆盖：任务来源、分流约定、术语与决策资料入口、游戏资料与资源管理方式。
已有的约定直接沿用，不要换成模板写法。
不要执行引擎初始化、不要做资源制作或清理，也不要写入远端。
```

约定已经完整时，重复运行不改文件。它建立的是**普通项目配置**，不是插件安装、不是引擎初始化，也不需要专用程序解析。

模板在 `skills/setup-gamestudio/templates/`（`issue-tracker.md`、`triage-labels.md`、`domain.md`、`game.md`、`assets.md`）。模板只是起点，最终内容应反映你项目的实际做法。

## 2. 你的 GDD 与 spec 是运行时资料

技能运行时读取的项目资料不随技能分发：项目自己的 GDD、spec、任务记录、术语表、决策记录、资源约定与工程文件，都在你的仓库里，位置由 `setup-gamestudio` 记录。

- 装技能不会给你带来一份 GDD 或 spec。
- 缺少这些资料时，相关技能会说明缺口并保留可独立完成的部分，不会因此失效，也不会凭空补一份「完成说明」。
- 本仓库的 `docs/`、`provenance/`、`tests/`、`scripts/` 是维护资料，不随技能安装。

写入纪律见 [数据、写入与权限](../reference/data-and-permissions.md)：V3 没有专用记录运行层，技能用项目已有工具读写，写后回读，部分失败分别报告，不宣称原子多文档写入。

## 3. 项目规则还指向 V2 入口怎么办

如果你的 `AGENTS.md`、`CLAUDE.md` 或项目文档里还写着 `game-producer`、`game-init`、`game-design`、`setup-matt-pocock-skills`、`to-spec`、`to-tickets`，这些名字在 3.0.0 不是可执行入口，V2 的插件安装命令也已全部退出。

处理顺序：

1. 用 `setup-gamestudio` 探查时，它会指出引用失效并建议改写；它只改约定文档，不迁移数据。
2. 按 [从 2.0.2 迁移到 3.0.0](../migration-v3.md) 的对照改写引用，注意其中明确**没有等价能力**的部分（全项目进度盘点、资料迁移与安全切换、设计快照）。
3. 改写属于文档修改，需要你授权；不要顺手做批量替换。

## 4. 第一次实际使用

先做一次不修改文件的导航或讨论，确认技能能读到你项目的真实资料：

- 想知道现在该做什么：`ask-gamestudio`
- 要讨论一个设计问题并落盘已采纳内容：`grill-gamestudio-docs`
- 要把已明确的工作拆成票：`tasks-gamestudio`

组合方式见 [常用工作流](workflows.md)；第一次会话的完整文案见 [从安装到第一次有效使用](../getting-started.md)。

## 不要做的事

- 不要把本仓库的 `AGENTS.md` 复制进游戏项目：那是维护本仓库的协作说明。
- 不要把技能之间的引用箭头当成自动授权；用户入口不自动串调。
- 不要在没确认的情况下让 Agent 批量迁移旧资料或改写既有记录。
