# Game-Init:项目初始化与协作配置

统一的项目初始化入口:先探查、再清单、确认后按角色应用、回读核对。本包版本覆盖「新项目 + 本地 Markdown 任务后端」与「接手已有项目(本地 Markdown 任务后端)」两条路径;后端切换迁移与规格拆单属后续任务票,未实现不声称。

## 包内依据(开始任何工作前读取)

本技能位于 `<插件根>/skills/game-init/`,包内材料在其上级目录:

- [协作配置合同](../../internal/contracts/project-configuration.md):配置范围、过程与保存
- [初始化流程](../../internal/proposals/project-onboarding.md):探查/清单/确认/应用/核对与恢复规则(「已有项目」与「中断与重复运行」两节为接手路径的依据)
- [项目目录模板](../../internal/proposals/project-layout.md)与[模板入口](../../templates/README.md):落点与维护责任
- [工作记录合同](../../internal/contracts/records.md)与[任务分流设计](../../internal/contracts/task-triage.md):任务与结果记录结构

## 步骤

### 阶段一:探查(只读)

1. 确定目标项目根与本轮请求:新建接入、接手已有项目、仅分析、仅清单、恢复未完成的应用,或应用/升级已确认的清单。缺明确目标项目时先问清,不改读其他目录。
2. **新项目**:只读探查开发者已定与未定的事实;协作配置建议(无既定有效选择时)分别表达任务后端与位置、五类标签映射、核心文档位置、术语与决定位置。
3. **已有项目**:对原项目只读做结构化现状分析,覆盖项目结构、代码与资源、工程配置、现有文档、已有任务与验证线索,并把每项观察归入六类之一:
   - **实际行为**:代码/资源/配置中可观察到的当前做法(附文件与位置证据);
   - **已采纳要求**:现有文档中明确标记为已采纳/已定的要求(注明出处与日期);
   - **历史内容**:被替代的决定、旧方案与过程记录(保留,不当成当前要求);
   - **缺口**:接入工作流缺失的资料(如协作配置、入口、任务结构);
   - **冲突**:相互矛盾的资料,尤其「现有实现与旧文档的矛盾」——逐条给出双方证据(文件、位置、内容),列为**待决定项**交开发者裁决;**不得自动把实现采纳为产品意图**,也不得擅自改实现去迁就旧文档;
   - **未验证事实**:双方都无法在本轮核实的声明(如"能跑"但本轮未运行)。
4. 完成标准:能区分「已确定的配置」与「仍需选择的部分」,六类现状各有归属与证据,原项目保持未修改。

### 阶段二:接入清单

5. **复用优先**:沿用已有有效文档与任务来源(身份保持稳定),通过 INDEX 等入口映射**实际位置**与维护责任;需要补齐的按模板新增;旧格式资料提出迁移方案(含状态/字段映射表)。逐项列出:实际落点、复用/新增/修改动作与内容要点、依据、维护角色、需确认事项;清单中区分「本轮应用」「保留不动」「待决定」。
6. **混合职责文档**:同一文件混合管理/设计/技术等多种维护责任时,提出可审阅的**拆分方案**(各部分迁往对应角色维护的文件,原文保留为历史或按清单归档)或**受控应用方案**(由有权维护该文件的角色应用提议的修改)。**不得为统筹方便而授予或使用整个专业/混合文档的写入权限**;统筹只写管理资料,专业部分由对应角色实例应用。
7. **模板升级**(请求对齐新版模板时):先对比当前安装位置模板与项目已实例化文档的结构差异,产出**具体变更清单**(每个受影响文件加什么/改什么)与**保留方案**(用户已填内容、引用与实际配置如何原样保留),列出需要重新确认的受影响部分;未确认前不写入。
8. 涉及外部访问、客户端指针(如 AGENTS.md)、权限或运行保障配置的,单独列出确切对象与范围。未确认前不写入。

### 阶段三:应用(取得确认后)

9. 输入含确认后按清单执行;**同一确认范围内不逐文件重复询问**。仅应用清单内条目;**未列入清单的文件一律不动**,有效内容与历史关系保留(被拆分/被迁移的原文按清单保留或归档,不删除历史)。
10. 管理文档与本地任务记录由制作统筹经 mgs-gate 写入:先 `mgs_scope` 确认范围,再按[受控写入协议](../../internal/protocols/gate-protocol.md) `mgs_write` 提交(新文件省略 `expected_sha256`,更新已有文件必须携带),逐项回读核对。专业文档及其中的混合文档部分按清单交对应角色实例执行,本角色不代写,越界写入被拒即停止该项并原样记录。
11. 每次文档写入前读取包内 writing-for-agents 并采用其方法;本地任务记录按 work/task.md 模板,任务身份保持稳定(沿用已有身份,不重命名),只建立当前请求明确需要的条目,不做规格拆单。

### 阶段四:回读核对与报告

12. 回读全部新建/修改文件;核对任务、标签与文档引用可从 CONFIG 定位。可用包内统一接口辅助核验:`python3 <插件根>/records/mgs_records.py verify --project <项目根>`(仅本地 Markdown 后端)。
13. 输出报告(结构固定;按本轮模式取用):

```
## 接入报告
### 现状分析(已有项目:实际行为 / 已采纳要求 / 历史内容 / 缺口 / 冲突 / 未验证事实)
### 协作配置(建议或已采用)
### 接入清单与应用结果
### 回读核对
### 文档接入就绪
### 运行保障就绪
### 外部访问与配置变更范围
### 遗留事项(含待决定项)
```

模板升级轮在本结构内给出:模板对比与具体变更、保留方案执行结果、已完成/剩余/需重新确认的受影响部分。

文档接入就绪与运行保障就绪**分别**报告,不互相替代:前者指资料入口、任务与引用可定位;后者指受控写入通道等运行边界的实际状态与证据。外部访问、客户端指针或权限配置变更逐项列出对象与范围;普通初始化不自行扩大操作授权。

## 中断、恢复与重复运行

- 应用被中断后恢复:先逐项核对**实际文件**、原清单与**用户后来的手工修改**;已完成的条目跳过不重写,未完成的按仍适用的范围补齐;用户修改过的内容必须保留,不得覆盖;影响写入的新变化重新列出受影响清单再继续。
- 重复运行:无缺口时报告**无需改动**,不创建重复资料(不重复建任务、不重复归档、不重复拆分)。
- 恢复与重复执行都以实际回读结果为依据,不以记忆或上一轮的声明为准。

## 边界

- 分析阶段只读;应用仅限已确认清单;CONFIG 是协作配置,不是运行时权限凭证;写入授权以 mgs-gate 绑定为准。
- 现有实现与旧文档矛盾时提供证据与待决定项,不自动把实现采纳为产品意图,不替开发者裁决。
- 混合职责文档的各部分由对应维护角色应用;统筹不因组织接入而获得专业文档写入权。
- 任务字段中的角色或范围描述是记录,不是授权。
- 不把执行凭据写入任何文件或报告正文;需要人决定的事项原样保留。
