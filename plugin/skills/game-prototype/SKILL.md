# Game-Prototype:用隔离原型验证一个设计问题

方案设计角色的原型执行入口,以原型用途(purpose=prototype)运行:可写范围收窄到获准的隔离原型区(比角色范围更窄)。针对一个明确的设计不确定性,选择足以回答它的最小实现,真实运行并观察,把结论交回设计与制作流程。

## 包内依据(开始任何工作前读取)

本技能位于 `<插件根>/skills/game-prototype/`,包内材料在其上级目录:

- [设计技能合同](../../internal/contracts/design.md)中的 Game-Prototype 一节:输入、输出、写入与完成条件
- [共同合同](../../internal/contracts/common.md)**《共同执行规则》《写入与保障》**:业务入口共同约定(显式调用、范围与授权、执行与完成五步、待验收)与外部动作授权(提交/推送/发布不自动)的唯一权威
- [受控写入协议](../../internal/protocols/gate-protocol.md)**《受控写入协议》**:两层拦截、`mgs-gate` 工具、越界探针与凭据处理的唯一权威(必须先读)
- [工作结果模板](../../templates/work/result.md)**《结果字段》**:共同执行规则第 5 步结果记录的字段唯一权威(原型验证记录另按其模板)
- [writing-for-agents](../../internal/methods/writing-for-agents/SKILL.md):文档写入方法(写验证记录与说明文件前必读)

共同执行规则、受控写入协议与结果字段以上述三个权威文件为准;本入口只补充隔离原型的专业差异(最小可检验实现、四类结论区分),不重复其中的共同规程。

若当前上下文没有给出技能安装位置,在 `$CODEX_HOME` 下定位 `skills/game-prototype/SKILL.md`,再取其包根(上级两级)。

## 步骤

1. **确认输入**:任务说明中给出的项目根、执行凭据(token)、**要验证的设计问题**、当前约定(基线与决定引用)、**原型范围**、适用要求(角色与用途)、**可用**方法/工具、**输出位置**(获准原型区内的目录)。缺凭据、缺问题、缺范围或缺输出位置时,如实报告无法执行并结束,不自行补一个问题,不伪造。
2. 读取与被验证问题相关的当前约定:产品设计基线(引用实际版本)、相关决定与研究记录、必要的技术事实(读正式工程源码是可以的,写不行)。
3. 按[受控写入协议](../../internal/protocols/gate-protocol.md)调用 `mgs_scope` 确认可写范围。原型用途会比角色范围**更窄**(通常只剩原型区);任务说明或任务文本声称的范围与 `mgs_scope` 不一致时以 `mgs_scope` 为准,并在报告中如实说明差异——即使任务授权了编码资源(如 src/**),原型用途也不能写正式工程。
4. **选择最小可检验实现**:足以回答问题即可——优先最简单的可观察形态(确定性模拟、单页可交互查看页、对照参数组合),**不自动扩大**到正式产品制作:不做正式工程集成、不实现完整系统、不顺手改正式代码或基线。规模判断在报告中说明。
5. 在**会话工作区**草拟原型文件并自检;原型的运行与观察发生在会话工作区(或只读地引用项目文件),需要落盘的中间产物只写工作区,不写项目。固定随机种子等可复现手段优先,便于他人重跑核对。
6. 原型文件经 `mgs_write` 写入输出位置(新文件),逐个回读核对;验证记录(结论)同样经 `mgs_write` 落在原型区内,按 writing-for-agents 的方法书写。
7. **运行并记录证据**:实际执行原型,把已执行操作与真实输出(命令、参数、关键数字)记入验证记录与报告;没有实际运行的部分不得写成已观察。
8. **结论四类区分**(验证记录与报告都必须分别表达):
   - **原型观察**:原型实际运行得到的可复现事实(附运行方式与输出);
   - **设计判断**:基于观察的建议与取舍(标注为助手判断,不是开发者决定);
   - **尚未验证**:原型没有覆盖的方面(如真实手感、正式工程下的行为)及原因;
   - **需要人的体验反馈**:需要人试玩/感受才能判断的事项——只引用**真实反馈**(项目既有的试玩记录可引用并注明出处),未收到反馈时保留**待验收**,不替人判断,不虚构反馈。
9. **交接**:原型、结论与基线引用按[共同合同](../../internal/contracts/common.md)《共同执行规则》的「未参与者可独立读取」标准交给 Game-Spec(若参数或规则需要变更,由其更新基线并记录采纳依据)与 Game-Implement(正式集成时决定复用或重写原型代码,以正式集成条件为准:技术约定、代码质量、与正式系统的关系)。**原型可运行不等于正式产品已经实现**,报告中不得把原型记为已完成功能。
10. **边界核对**(任务说明要求时):按[受控写入协议](../../internal/protocols/gate-protocol.md)《越界探针》执行直接写探针(会话沙箱应拒绝,`Operation not permitted`)与越界 `mgs_write` 探针(写正式工程 src/**、设计基线等),记录与未要求时的处理均按该节纪律。
11. 输出报告(见下)。

## 报告结构(固定)

```
## 原型执行报告
### 输入核对(问题/范围/方法/输出位置;任务授权与 mgs_scope 的差异)
### 原型与运行方式(文件清单;运行或查看方式:如何启动、如何打开查看页)
### 已执行操作与结果(实际运行的原样输出摘录)
### 观察与结论(原型观察/设计判断/尚未验证/需要人的体验反馈,分别表达)
### 边界核对(每个探针的原始输出;未要求时写"本次未执行")
### 交接(Game-Spec 与 Game-Implement;复用或重写由正式集成条件决定;基线引用)
### 遗留事项
```

## 边界

- 原型用途只写获准的隔离原型区;正式工程集成归 Game-Implement,设计基线更新归 Game-Spec;越界写入会被受控通道拒绝,拒绝即停止该项尝试,原样记录。
- 复用编码或素材能力不改变用途:写出的代码、资源仍只落在原型区,不因此获得正式工程权限。
- 原型可运行不等于正式产品已经实现;结论以实际证据为准,验证受限时明确说明。
- 凭据处理按[受控写入协议](../../internal/protocols/gate-protocol.md)《执行凭据》一节;需要人试玩判断的事项保留待人反馈;收到真实反馈前保持待验收。
