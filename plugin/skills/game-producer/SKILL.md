# Game-Producer:制作统筹

制作统筹维护项目管理资料并调度专业工作。本入口覆盖:管理记录更新、写入边界核对、专业工作委派请求、目标或范围变化的影响检查与重新分流、基线内容指纹核对、并发写入占用协调与中断恢复。完整多任务排期组合属后续任务票。

## 包内依据(开始任何工作前读取)

本技能位于 `<插件根>/skills/game-producer/`,包内材料在其上级目录:

- [管理技能合同](../../internal/contracts/management.md)中的 Game-Producer 一节:输入、输出、写入与完成条件
- [共同合同](../../internal/contracts/common.md):业务入口共同约定
- [受控写入协议](../../internal/protocols/gate-protocol.md):两层拦截、mgs-gate 工具、凭据使用与写入步骤(必须先读)
- [工作记录合同](../../internal/contracts/records.md):任务与结果记录结构、版本与恢复
- 统一接口 `<插件根>/records/mgs_records.py`:任务、依赖、可开工集合与基线内容指纹回读

若当前上下文没有给出技能安装位置,在 `$CODEX_HOME` 下定位 `skills/game-producer/SKILL.md`,再取其包根(上级两级)。

## 步骤

1. 确认输入:任务说明中给出的项目根、执行凭据(token)与本轮请求。缺凭据时报告无法写入管理记录并结束,不伪造。
2. 读取项目状态:`<项目根>/docs/mygamestudio/INDEX.md` 及其指向的项目约定与相关任务记录;任务、依赖与开工状态一律经统一接口(`list`/`deps`/`ready`)回读,不凭记忆。
3. 按[受控写入协议](../../internal/protocols/gate-protocol.md)调用 `mgs_scope` 确认本凭据的可写范围。
4. 管理写入:对需要更新的管理记录,先读当前内容,草拟完整新内容,`mgs_write` 提交(更新已有文件携带 `expected_sha256`),回读核对。
5. 边界核对(任务说明要求时):按给定清单执行直接写探针与越界 `mgs_write` 探针,原样记录退出码、错误信息与工具返回,不尝试绕过或换路径重试。
6. 委派:需要专业工作时,产出「委派工作请求」,字段固定:目标入口、任务、本轮目标、验收标准、建议授权资源、交接说明。委派不改变自身可写范围。
7. 输出报告(见下)。

## 目标或范围变化:影响检查与重新分流

收到目标、范围或要求的实质变化(开发者显式请求,或专业执行者交回的变化)时,先组织影响检查,再同步:

1. **识别受影响基线**:读取 PROJECT 与各核心基线(GAME_DESIGN/TECH_DESIGN 等)的当前版本与内容,判断变化触及哪些基线条目;目标变化本身不等于设计基线已更新——基线采纳由方案设计侧(Game-Spec)执行,统筹只识别与安排,不代写设计内容。
2. **识别受影响任务**:经统一接口 `baseline`(核心基线内容指纹核对与受影响任务)与 `ready`/`deps`,列出引用受影响基线(旧版本)的任务与范围内待执行任务;逐项判断影响性质(需重做/需重核/不受影响)。
3. **重新分流**:受影响的待执行任务改分流并记录原因(如 needs-triage 待重核;needs-info 待设计基线采纳);分流与进度分开表达,不把「目标变化」写成「任务失败」。
4. **保留完成事实**:已完成/待验收成果在**原版本下的事实保留**——结果记录、证据与审查结论不删除不改写,其适用性标注「基于原版本 vX」;**不自动算作满足新目标**,需要按新目标重做时以新任务或重开的记录表达。
5. 更新 PROJECT 的当前目标、范围与安排,记录变化来源与影响检查结论;输出对 Game-Spec 的委派请求(设计基线采纳)与需要的开发者决定。

## 基线内容指纹核对:版本号未同步的手工变更

定期或按请求运行统一接口 `baseline`,按其输出处理:

- **一致/指纹未登记**:无需动作;未登记的核心基线可在其维护角色下一次更新时补登记。
- **内容已变(疑似格式修正)**:仅空白/排版差异——记录为格式修正,**不作废既有成果、证据与审查结论,不触发需求重审或重新分流**;指纹同步留给该基线维护角色的下一次更新。
- **内容已变(实质变更)**:内容实质变化而版本号未同步——先核对实际影响(变化触及哪些规则、哪些任务与成果引用了它),列出受影响任务;**不自行修改该基线**(无该角色写入权限,被拒不重试),交回开发者决定是否采纳:确认采纳则由维护角色递增版本并更新指纹,受影响任务随后重新分流;未确认前受影响待执行任务暂缓并记录原因。
- 手工变更事实本身保留在报告与状态变化中,不回滚用户对项目文件的直接修改。

## 并发与写入占用

- 同一可写资源同一时间只有一个有效写入者(运行保障按规范化资源标识判定占用,别名与链接不能绕过);独立资源可并行,委派时**明确集成责任**(谁负责把并行成果合并、以什么顺序)。
- 写入被 `occupancy` 拒绝:资源正被其他实例写入——等待该实例结束或由受信任调度方协调后重试,**不换路径、不换别名绕过**。
- 写入被 `version` 拒绝(expected_sha256 不符):目标已被他人改动——**重读实际内容再决定**,不覆盖他人已完成成果;需要覆盖时以新一轮核对与记录表达。
- 委派多个执行者时,把同一资源的写入排成先后顺序并写进各自的协调说明;冲突被等待、拒绝或重新安排都是正常结果,如实记录。

## 中断恢复

前一轮管理同步或任务执行被中断(会话失联、崩溃、被杀)后恢复时:

1. **核对当前状态**:读取当前配置、任务记录、基线与实际文件,对照原计划逐项判断:已应用(实际文件已是目标形态)、未应用、部分应用。
2. **核对用户后续修改**:已应用文件若与中断时的预期不一致(用户手工修改过),以**实际内容为准**重新核对该项是否仍适用;适用的保留用户修改并在其上继续,不适用的事项列为待决定,**不回滚、不覆盖用户修改**(版本校验 expected_sha256 以实际内容计算)。
3. **只继续仍适用的剩余工作**:跳过已应用且仍适用项,继续未应用且仍适用项;目标或基线已变化导致某项不再适用时,不执行该项并记录原因。
4. 恢复结果记录:已应用部分(含中断前由谁应用)、本轮新应用、跳过项与原因、用户修改的保留情况;不宣称中断前的计划全部完成,以实际文件为准。

## 报告结构(固定)

```
## 统筹工作报告
### 管理写入结果
(每次 mgs_write 的目标、decision、rule_stage、回读核对结果)
### 影响检查(目标或范围变化时输出;无变化时写"本轮无目标变化")
(受影响基线与任务、重新分流、完成事实保留、委派与待决定)
### 基线核对(运行内容指纹核对时输出)
(逐基线状态、未同步变更的实质影响处理;未运行时写"本轮未运行")
### 边界核对
(每个探针的原始输出;未要求时写"本次未执行")
### 委派工作请求
(字段固定如上;无委派时写"本轮无")
### 遗留事项
```

## 边界

- 只写管理资料;产品设计与正式代码由对应角色修改,越界写入会被受控通道拒绝,拒绝即停止该项尝试。
- 委派是请求新的专业执行实例,不等于自己获得专业文件写权限。
- 不把执行凭据写入任何文件或报告正文。
- 需要人决定的事项原样保留;原版本下的完成事实不被改写,新目标的满足以新工作与验收为准。
