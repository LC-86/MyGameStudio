# Game-Playtest:试玩、运行观察与人工反馈

审查与试玩角色的试玩执行入口(试玩不新增常设角色,按被试对象选择相应专业执行实例)。输入是**明确的版本与入口、要检查的场景或问题、适用要求、可用控制工具及人工参与约定**,输出是版本与场景、已执行步骤、观察和证据、缺陷或反馈、尚未执行的部分。**所称已试玩部分必须有实际执行证据;人工结论只来自实际反馈;仅制定计划的工作明确标为计划。**

- [工作记录合同](../../internal/contracts/records.md):任务记录结构与证据关联(人工验收引用实际反馈)

## 步骤

1. **确认输入**:任务说明中给出的项目根、执行凭据(token)、**被试对象(明确的版本与运行入口)**、要检查的场景或问题、适用要求、可用控制方式及人工参与约定。**没有明确的版本与入口时不开始**——试玩对象必须显式引用(如某任务的构建产物与入口文件),不从可开工集合选取(ready 是开工视角,待验收成果不在其中);缺场景或问题时向请求方明确要回答的问题,不自行编造;缺凭据时报告无法写入试玩记录并结束,不伪造。
2. **读取项目实际约定**:经统一接口 `show/deps` 读取被试任务记录与依赖(不凭记忆);再读取适用要求(设计基线条文、任务完成标准、验收方式原文)、运行入口约定(技术设计的构建与导出约定、入口文件与启动方式)、CONFIG 执行条件中的**可用控制方式**(本机可用的无头驱动、静态服务、检查工具)。**控制方式来自项目实际配置**——CONFIG 未声明的能力不假定可用;请求中给出的控制工具与 CONFIG 不一致时如实报告差异。
3. **制定必要场景**:从明确版本、运行入口、要回答的问题和可用控制方式**制定必要场景**(每个场景:输入步骤、预期或观察问题、判定依据);场景数量与要回答的问题匹配,不无限展开。区分两类:**可自动执行的场景**(headless 可编程控制可覆盖)与**需要人的体验判断的场景**(手感、审美、听感、真实浏览器感受)。**仅制定了计划而尚未实际执行的场景在记录中明确标为尚未执行/计划**,不写成已观察。
4. **实际执行可用检查**:对可自动执行的场景**实际运行并记录真实输出**——如按入口文件的实际引用顺序在无头环境(DOM 桩/脚本沙箱)加载并驱动,记录驱动输入(帧步进、时间推进)与实际观察(初始化、递减、强调时机、结算边界、幂等);入口可达与引用解析(本地静态服务取回、产物文件存在且一致)。一次性检查脚本放**会话工作区或系统临时目录**(不进项目、不引入第二套工具链)。**没有实际运行的部分不得写成已观察**;运行失败或环境受限(如会话禁止绑定端口)时如实记录未完成项及原因,不重试绕过、不当作通过。
5. **版本绑定**:登记**被试版本指纹**——入口与产物文件的清单与 SHA-256,写入试玩记录;结论只对登记版本成立。本轮发生新改动、检查失败或出现具体疑点时**触发相关复测**(重新登记指纹并重新执行受影响场景);未变化且仍适用的既有证据(如构建任务的运行检查记录)**核对仍针对当前版本后可以引用**,注明出处与核对方式。
6. **人工体验判断(需要人时)**:对手感、审美、听感等只能由人判断的场景,**给出明确的试玩任务与回传要求**:具体操作步骤(打开什么入口、玩什么、注意什么问题)、需要的观察问题、样本要求(次数、时长)、**回传格式**(实际原话或忠实概述、时间与来源,需要计数的要求回传尝试次数与结果数)。记录中把每个人工项的当前状态分别表达:**未反馈(待人工)/明确通过/需要修改**;实际反馈保留来源(原话或忠实概述、时间、来源);**未收到反馈时保留待反馈,不以 Agent 观察或推断冒充人工反馈**;收到「需要修改」的反馈时输出交接(返回对应执行流程修复),收到「明确通过」的反馈记录来源供验收参考。
7. **缺陷与目标变化处置**:检查或反馈发现缺陷时,在记录中逐项登记(场景、输入、观察、影响)并**输出交接**——返回对应制作或设计任务修复,试玩实例**不改产品基线来迁就观察结果**,也不自行修复被试成果;发现适用要求本身冲突或目标变化时,记录影响并交回统筹与设计流程,不代为决定。
8. **核对范围并写入**:按[受控写入协议](../../internal/protocols/gate-protocol.md)调用 `mgs_scope` 确认可写范围——试玩实例写入**仅限本次试玩记录、证据及允许的测试运行状态**(项目 evidence/ 区,按[试玩与运行记录模板](../../templates/evidence/playtest.md)字段,经 `mgs_write` 写入并回读核对)。**运行状态和测试输出受本次用途限制**:检查脚本与测试输出只落在会话工作区或系统临时目录,不进项目;被试成果、任务记录、设计基线都不在本入口的写入范围。记录关联被试任务身份、版本指纹与证据位置。
9. **控制通路边界**:已验证的控制方式(CONFIG 声明且实际运行过)如实记录;**真实浏览器 GUI 控制、外部 MCP 控制工具等新增通路不被假定继承本地边界**——未经验证的通路保持**未就绪**,相关场景归入尚未执行并说明所需条件(如需要真实浏览器环境),不以无头结果替代真实手感,覆盖限制如实标注。
10. **不代验收**:试玩记录与人工反馈是被试任务验收方式中「试玩/人工验收」一项的事实来源;**试玩记录生成不等于验收通过**,任务进度与分流归统筹维护,本入口不改任务记录;需要统筹同步的事项写入记录的交接说明,试玩结果供管理流程决定进度。
11. **边界核对**(任务说明要求时):按[受控写入协议](../../internal/protocols/gate-protocol.md)《越界探针》执行直接写探针与越界 `mgs_write` 探针(如对被试产物文件),记录与未要求时的处理均按该节纪律。
12. 输出报告(见下)。

## 报告结构(固定)

```
## 试玩与运行观察报告
### 被试版本(对象与任务身份;入口与产物文件清单与 SHA-256 指纹;与既有证据的版本关系)
### 场景与执行(逐场景:输入步骤/预期或观察问题/实际观察/证据;可自动执行与需人工的划分)
### 观察与缺陷(逐项:场景/输入/观察/影响;输出交接的修复项)
### 人工试玩任务(逐项:具体任务与回传要求;当前状态[未反馈(待人工)|明确通过|需要修改];已有反馈的来源)
### 尚未执行与覆盖限制(未执行场景及原因;未就绪的控制通路)
### 交接(试玩记录与证据位置;返回执行流程的修复项;统筹同步事项)
```

报告按[共同合同](../../internal/contracts/common.md)《共同执行规则》的「未参与者可独立读取」标准书写,引用实际任务身份与版本指纹,不依赖对话记忆。

## 边界

- **明确的版本与入口是前提**:没有明确被试对象不开始;场景与问题来自请求与任务记录,不自行编造要回答的问题。
- **实际执行才算已试玩**:每个已执行场景有真实输入与观察记录;仅制定计划的场景明确标为尚未执行/计划,不冒充已观察。
- **人工结论只来自实际反馈**:试玩任务给出具体步骤与回传要求;未反馈、明确通过与需要修改分别表达;反馈保留来源(原话或忠实概述、时间、来源);Agent 的观察或推断不冒充人工反馈,不以自动检查替代人工判断。
- **结果绑定实际测试版本**:结论只对登记指纹的版本成立;新修改、失败或疑点触发复测;引用既有证据先核对仍针对当前版本。
- **不改产品基线来迁就观察结果**:缺陷输出交接返回执行流程;目标变化交回统筹与设计;试玩实例不修改被试成果、任务记录与设计基线。
- **写入仅限本次试玩记录、证据及允许的测试运行状态**(evidence/);运行状态和测试输出受本次用途限制,检查脚本不进项目;进度与分流归统筹,试玩记录生成不等于验收通过。
- **控制通路边界**:控制方式来自项目实际配置并实际运行;新增 GUI/MCP 通路不被假定继承本地边界,未经验证保持未就绪,如实标注覆盖限制。
- 凭据处理按[受控写入协议](../../internal/protocols/gate-protocol.md)《执行凭据》一节;不执行任何外部动作(提交、推送、发布等),外部动作边界见[共同合同](../../internal/contracts/common.md)《写入与保障》。
- 失败或中断时保存已完成的试玩部分与缺口,如实交接。
