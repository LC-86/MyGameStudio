# Game-Design:产品与体验方案讨论

方案设计角色的讨论入口:把本轮问题组织成可决定的方案。按问题形态选分支:**局部功能**问题走质询分支收紧设计;**多项未决问题**走决策地图分支先图后决。可以只讨论不写入;讨论产出的采纳内容由 Game-Spec(或等效的明确文档步骤)同步基线,本入口不写产品基线。

## 包内依据(开始任何工作前读取)

本技能位于 `<插件根>/skills/game-design/`,包内材料在其上级目录:

- [设计技能合同](../../internal/contracts/design.md)中的 Game-Design 一节:输入、输出、写入与完成条件
- [共同合同](../../internal/contracts/common.md):业务入口共同约定
- [工作记录合同](../../internal/contracts/records.md):决定与研究记录的结构、出处与版本
- [受控写入协议](../../internal/protocols/gate-protocol.md):写入通道(需要写入时必读)
- [writing-for-agents](../../internal/methods/writing-for-agents/SKILL.md):文档写入方法(**所有文档写入步骤必读**)

若当前上下文没有给出技能安装位置,在 `$CODEX_HOME` 下定位 `skills/game-design/SKILL.md`,再取其包根(上级两级)。

## 分支选择(内部方法按问题需要加载)

读取问题后判断,只加载对应分支需要的内部方法;这些方法是包内固定版本材料,**不提供同名公共入口**:

- **质询分支(局部功能)**:范围清楚、疑问集中在少数决定点。读取 [grill-with-docs](../../internal/methods/grill-with-docs/SKILL.md);它组合的 [grilling](../../internal/methods/grilling/SKILL.md)(按轮次问前沿问题)与 [domain-modeling](../../internal/methods/domain-modeling/SKILL.md)(术语与边界场景)按其指引使用。
- **决策地图分支(多项未决问题)**:想法大、雾多、决定点互相牵连。读取 [wayfinder](../../internal/methods/wayfinder/SKILL.md);其研究类工单配合 [research](../../internal/methods/research/SKILL.md) 使用,原型类验证走 Game-Prototype,不另建执行入口。
- 两类问题都需要外部事实时,先调查再提问:能自己查的事实(代码、文档、可本地核实的一手资料)自己查并记出处,不向开发者问可以查到的东西;查不到的列为待调查项。

## 质询分支步骤

1. 先查事实:读项目资料(CONFIG/INDEX 指向的基线、相关实现与任务),把可自行核实的事实查清并记出处(文件与位置);事实与决定分开。
2. 整理设计树,按轮次提出前沿问题:每轮编号列出当前可决定的问题,每个问题附候选选项与取舍,并给出**助手建议**(明确标注为建议,不是决定);然后等开发者回答,不代答、不自问自答。
3. 开发者回答到达后重组前沿,必要时进入下一轮;前沿清空即讨论收敛。
4. 收敛后整理本轮产出并按「写入」落盘;仍有未决项时如实保留未决并注明影响,不补默认值。

## 决策地图分支步骤

1. 先与开发者确认**目的地**:这轮工作最终要交付什么(可执行规格、锁定决定还是方案变更);目的地决定范围。
2. 广度扫描未决问题:能精确表述的列为**决策工单**(每张一个决定点,标注类型:质询/研究,以及先后阻塞关系);还看不清的留在**未定雾区**;明确不在目的地内的放入**范围外**。
3. 制图轮只画图:地图与工单写入设计过程记录(见「写入」),**不代替开发者作任何决定,不顺手解决工单**。
4. 后续轮次按地图逐张解决:质询类工单收敛为开发者决定,研究类工单产出带出处的调查结论;每张工单解决后更新地图状态与对应决定/研究记录。

## 写入(经 mgs-gate)

- 写入落点按 CONFIG 文档映射的「术语、决定与历史」行(默认 `docs/mygamestudio/records/`),使用包内模板 `templates/records/`:
  - 决定记录:状态只写实际达成的(提议/已采纳/已被替代);未决内容明确标**未决**,不写成已采纳;候选方案与取舍保存在「选项与决定」过程记录,不进基线。
  - 研究记录:结论、依据表(事实或判断/原始来源/适用限制)、对当前工作的影响。
  - 决策地图:作为设计过程记录保存(如 `records/decision-map-<主题>.md`),含目的地、决策工单(类型/阻塞/状态/对当前工作的影响)、未定雾区、范围外。
- 采纳标注必须区分来源:开发者实际作出的决定注明**决定者与日期**;助手建议与候选方案保持其建议身份,不冒充用户决定。
- 不写 GAME_DESIGN 等产品基线;基线同步归 Game-Spec。发现目标或范围变化时不改 PROJECT,按共同合同的变更同步规则交回统筹。
- 每次文档写入前读取包内 writing-for-agents 并采用其方法;写入更新已有文件携带 `expected_sha256`,回读核对。

## 报告结构(固定)

```
## 设计讨论报告
### 分支与依据(本轮选择的分支及实际读取的内部方法)
### 研究事实(附出处;无则如实说明)
### 候选方案与取舍(助手建议明确标注)
### 开发者已作出的决定(仅列实际由开发者给出的;无则如实说明)
### 未决项(每项注明对当前工作的影响)
### 写入结果(本轮未写入时如实说明)
```

## 边界

- 助手建议不冒充用户决定;未收到开发者明确回答的内容一律保持未决。
- 事实与决定分开:调查结论记出处,不自动采纳为产品要求。
- 只写设计过程与决定记录;越界写入被拒即停止该项并原样记录,不换路径重试。
- 不把执行凭据写入任何文件或报告正文。
- 需要人决定的事项原样保留,不用占位内容冒充已确定。
