# Game-Code:技术方案、代码与代码级验证

制作实现角色的代码执行入口。输入是**所需行为、技术约定、现有工程、可用检查与允许修改范围**,输出是代码、必要技术设计更新、运行或检查证据及遗留问题。约定行为必须得到**实际验证**;未运行的检查明确列出,不虚构通过。

## 包内依据(开始任何工作前读取)

本技能位于 `<插件根>/skills/game-code/`,包内材料在其上级目录:

- [制作技能合同](../../internal/contracts/production.md)中的 Game-Code 一节:输入、输出、写入与完成条件
- [共同合同](../../internal/contracts/common.md)**《共同执行规则》《写入与保障》**:业务入口共同约定(显式调用、范围与授权、执行与完成五步、待验收)与外部动作授权(提交/推送/发布不自动)的唯一权威
- [工作记录合同](../../internal/contracts/records.md):任务记录结构与结果落点
- [受控写入协议](../../internal/protocols/gate-protocol.md)**《受控写入协议》**:两层拦截、`mgs-gate` 工具、越界探针与凭据处理的唯一权威(必须先读)
- [writing-for-agents](../../internal/methods/writing-for-agents/SKILL.md):文档写入方法(写技术设计与结果记录前必读)
- [工作结果模板](../../templates/work/result.md)**《结果字段》**:结果记录字段的唯一权威
- 统一接口:`<插件根>/records/mgs_records.py`(config/list/show/deps/ready,读取任务与依赖,不硬编码目录)

若当前上下文没有给出技能安装位置,在 `$CODEX_HOME` 下定位 `skills/game-code/SKILL.md`,再取其包根(上级两级)。

## 步骤

1. **确认输入**:任务说明中给出的项目根、执行凭据(token)、任务目标与允许修改范围。没有明确任务引用时,经统一接口 `ready` 从当前可开工集合选取第一个待执行代码任务(在报告中说明选择依据)。缺凭据时报告无法写入并结束,不伪造。
2. **读取实际任务与基线**:经统一接口 `show/deps` 读取任务记录全文与依赖(不凭记忆或转述);读取任务「输入与基线」引用的**技术设计当前版本**、产品设计规格、现有工程目标文件现状。依赖未完成或记录与工程冲突时如实报告;冲突不阻塞的部分继续。
3. **核对范围**:按[受控写入协议](../../internal/protocols/gate-protocol.md)调用 `mgs_scope` 确认可写范围;任务文本声称的「允许修改范围」与 `mgs_scope` 不一致时,以 `mgs_scope` 为准并在报告中说明差异。**可开工或 ready-for-agent 不等于已获写入授权。**
4. **必要技术设计**:需要新结构、新参数或规格留白时,先形成或细化技术方案;技术设计由制作实现维护,更新经 `mgs_write` 携带 `expected_sha256` 并回读核对。规格中的留白参数集中为**可核对的命名参数**并如实记录采用值;固定的产品阈值不擅自改动。**发现产品要求冲突或目标变化时,记录影响并交回对应设计与统筹流程,不自行降低要求**;本任务可继续部分继续。
5. **实现方式来自项目实际配置**:引擎、运行与验证方式从项目 TECH_DESIGN 与 CONFIG 的实际约定读取;样例项目的具体技术选择只是该项目的事实,不因此成为本技能或框架的默认引擎或默认检查框架。
6. **实施代码变更**:在会话工作区草拟完整新内容并自检;`mgs_write` 提交(更新已有文件携带 `expected_sha256`),逐个回读核对。
7. **匹配风险的行为检查**:按步骤 5 的项目配置选择与**变更风险匹配**的检查,行为层优先——覆盖任务「完成标准」逐条边界;项目无既有检查体系时,把一次性检查脚本放在**会话工作区或系统临时目录**运行(不进项目、不引入第二套工具链),检查必须**实际运行**,把命令与真实输出记入结果记录;**未运行的检查(如需要浏览器或人工的)明确列出,不虚构通过**。
8. **结果记录**:把本次执行结果写入 `<项目根>/docs/mygamestudio/work/<任务身份>/results/<日期>.md`(经 `mgs_write` 受控写入,字段以[工作结果模板](../../templates/work/result.md)《结果字段》为准):**成果位置**、适用依据与**版本**、已执行检查及真实输出、未运行检查的明确列出、遗留事项与后续影响(接手条件、交回事项)。
9. **待验收**:按共同执行规则第 4-5 步——约定独立审查或人工验收未完成时,结果保留**待验收**,不宣称完成;任务记录的进度与分流由统筹维护,本入口不代改。
10. **边界核对**(任务说明要求时):按[受控写入协议](../../internal/protocols/gate-protocol.md)《越界探针》执行直接写探针与越界 `mgs_write` 探针,记录与未要求时的处理均按该节纪律。
11. 输出报告(见下)。

## 报告结构(固定)

```
## 专业执行报告
### 输入核对(任务/基线与版本/依赖/范围与 mgs_scope 差异)
### 技术设计(本轮技术方案要点与留白参数采用值;交回事项)
### 合法写入与回读(每次 mgs_write 的目标、decision、rule_stage、回读核对结果)
### 行为检查(实际运行的命令与真实输出摘录;未运行的检查及原因)
### 边界核对(每个探针的原始输出;未要求时写"本次未执行")
### 交接与遗留(成果位置/适用版本/证据位置/待验收/接手条件)
```

## 边界

- 只写执行凭据授权的技术文件、技术设计与结果记录;产品要求或设计文件需要变化时,在报告中提出并回到统筹/设计流程,不代为修改。
- 发现任务描述与实际工程冲突时记录冲突,继续可完成部分;失败或中断时保存**实际进度和缺口**,如实交接,不掩盖。
- 检查证据只记实际运行的结果;未运行、无法运行的检查明确列出,待验收不虚构通过。
- 凭据处理按[受控写入协议](../../internal/protocols/gate-protocol.md)《执行凭据》一节;需要人决定的事项原样保留。
- 普通实现完成不自动提交、推送、发布或修改远端工单,另行取得对应授权;**新增命令执行路径保持受控**:检查命令限于读取项目与写临时目录,对项目的写入一律经 mgs-gate 受控通道(共同边界见[共同合同](../../internal/contracts/common.md)《写入与保障》)。
