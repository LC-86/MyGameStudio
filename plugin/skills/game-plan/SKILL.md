# Game-Plan:把当前规格拆成可接手的本地原子任务

制作统筹的拆单入口:输入是**当前工作目标、已采纳规格(含版本)、适用技术约定和已有任务**,输出是逐项原子任务、交付与完成标准、执行和验收责任、依赖及基线引用。拆单方法是游戏侧协议(可独立核验的小成果、真实依赖、Agent/Human 分工),不照搬任何软件开发票模板;不重新裁决未决项,不代开发者作决定。

## 包内依据(开始任何工作前读取)

本技能位于 `<插件根>/skills/game-plan/`,包内材料在其上级目录:

- [管理技能合同](../../internal/contracts/management.md)中的 Game-Plan 一节:输入、输出、写入与完成条件
- [共同合同](../../internal/contracts/common.md):业务入口共同约定
- [工作记录合同](../../internal/contracts/records.md):任务最少信息、后端接口与版本引用
- [任务分流规则](../../internal/contracts/task-triage.md):五类状态与人机分工语义
- [受控写入协议](../../internal/protocols/gate-protocol.md):两层拦截、mgs-gate 工具与写入步骤(必须先读)
- [writing-for-agents](../../internal/methods/writing-for-agents/SKILL.md):文档写入方法(**所有任务记录写入步骤必读**)
- [工作请求模板](../../templates/work/task.md):任务记录字段与落点
- 统一接口:`<插件根>/records/mgs_records.py`(config/list/show/deps/ready/verify)

若当前上下文没有给出技能安装位置,在 `$CODEX_HOME` 下定位 `skills/game-plan/SKILL.md`,再取其包根(上级两级)。

## 步骤

1. **确认输入**:本轮拆单目标、已采纳规格及其**基线版本**、适用技术约定(引用 TECH_DESIGN,不代写)、已有任务与结果。已有任务经统一接口读取(`mgs_records.py config/list/show`,落点按 CONFIG 文档映射,不硬编码目录)。只拆**已采纳**内容;未决项不拆成可执行任务。
2. **只细化当前及近期**:本轮与近期可交付成果拆成原子任务;远期工作保持合适**粗粒度**(按 needs-triage 记录或在报告中说明"远期,本轮不拆解"),不把整册 GDD 展开成任务。
3. **拆解原则**:每项任务一个**可独立核验的小成果**,粒度适合一次执行;完整功能尽量形成可试玩的窄路径;单独的资源、调研、玩法试验也是合理任务,不强迫每项覆盖完整管线。按专业侧(代码/视觉音频资源/人工验收)分别考虑拆解建议并核对修改重叠。已有要求一律用**引用**(基线条目与版本、决定/研究/原型引用),不复制规格正文到任务里。
4. **任务字段**(按[工作请求模板](../../templates/work/task.md),另加拆单必需的「依赖」「所需能力」两项):**稳定身份**(排序变化不重命名)、标题、当前目标(引用项目目标)、输入与基线(版本)、本次交付、允许修改范围、所需能力(引用 CONFIG 执行条件,未就绪的如实标注)、完成标准、执行责任(Agent/Human 与专业角色)、验收方式(必要检查、独立审查及人工参与)、依赖、依赖与写入协调(共享资源、先后顺序与**集成责任**)、尚缺信息、结果索引(**结果入口**,执行结果按轮追加于此并可回读)。
5. **真实依赖与写入协调**:依赖只记录**真正影响开工**的任务,以任务身份表达(如 `04-gull-swoop`),经 `mgs_records.py deps` 核对**可解析且无循环**;同一可写成果同一时间**单一写入者**——重叠修改排先后(用依赖表达)或明确集成责任人与顺序,写入协调写在相关任务的对应字段。
6. **分流**(按[任务分流规则](../../internal/contracts/task-triage.md)):逐项给出五类分流之一,与进度、执行责任、验收方式分别记录;输入不足用 needs-info 并列具体缺失与谁补齐;需要人**执行**的工作用 ready-for-human;需要人**验收**(如试玩判断手感)记在该任务验收方式中,**不阻止前面的 Agent 制作**;暂缓、依赖未完成都不写成 wontfix;wontfix 只用于不再安排且保留原因与相关决定。
7. **重复拆解防护**:重新处理同一拆解时先读既有任务;同一目标与基线引用的既有任务**更新其安排**(分流、依赖、完成标准、状态变化),**不新建**重复任务;已由既有成果覆盖的请求也如此处理,不制造第二份。
8. **受控写入**(制作统筹角色,按[受控写入协议](../../internal/protocols/gate-protocol.md)):`mgs_scope` 确认可写范围;新建任务用 `mgs_write` 写完整新内容;更新既有任务携带 `expected_sha256`;每次写入后回读核对。拆单轮本身也是一个管理任务(工作请求=本轮拆单目标,结果索引记录拆解结果),便于安排的追加与回读。不写 GAME_DESIGN、TECH_DESIGN 与代码;越界被拒即停止该项并原样记录。
9. **开工集合与回读**:`mgs_records.py ready/deps/verify` 回读;报告当前**可开工**集合与不可开工原因(未完成依赖/输入不足/基线版本漂移/能力未就绪/待分流)。**可开工或 ready-for-agent 都不等于依赖已全部完成或已获全部授权**——开工前按任务「允许修改范围」与运行保障核对授权。

## 报告结构(固定)

```
## 拆单报告
### 输入核对(目标/规格与版本/技术约定/既有任务)
### 任务清单(逐项:身份/标题/交付/执行责任/验收方式/依赖/分流)
### 依赖与写入协调(依赖关系、单一写入者安排与集成责任)
### 当前可开工集合(可开工与不可开工及原因;授权核对提示)
### 分流说明(五类安排;未决、暂缓与不再安排事项的去向)
### 写入与回读(mgs_write 结果、统一接口回读结果)
### 遗留事项(缺信息/需人决定/未拆解的远期工作)
```

报告按「未参与讨论的执行者可独立读取」标准书写,引用实际身份与版本,不依赖对话记忆。

## 边界

- 只写任务记录与工作安排(work/ 及统筹管理资料);需求经引用保持设计维护者,技术约定经引用保持制作实现维护;发现规格缺口或目标范围问题时如实报告并交回,不自行改基线。
- 不代开发者决定未决项(如预警是否采纳);相关事项列 needs-info 并注明需要谁补齐。
- 不虚构完成或进度;已有任务的进度只按事实更新。
- 不把执行凭据写入任何文件或报告正文。
- 越界写入被拒即停止该项并原样记录,不换路径重试。
