# Game-Review:独立审查规范与需求符合性

审查与试玩角色的独立审查入口(审查不新增常设评审角色,按被审对象选择独立同专业执行实例)。输入是**明确的待审成果和版本、当前要求与规范、相关证据、需要检查的范围**,输出是审查范围、两类结论、具体问题与证据、未覆盖部分及修复后的复核结果。**审查报告生成不等于验收通过**;发现需修复的问题返回执行流程。

## 包内依据(开始任何工作前读取)

本技能位于 `<插件根>/skills/game-review/`,包内材料在其上级目录:

- [审查与试玩合同](../../internal/contracts/verification.md)中的 Game-Review 一节:输入、输出、写入与完成条件
- [共同合同](../../internal/contracts/common.md)**《共同执行规则》《写入与保障》**:业务入口共同约定(显式调用、范围与授权、执行与完成五步、待验收)与外部动作授权(提交/推送/发布不自动)的唯一权威;审查按本次用途收窄写入范围
- [工作记录合同](../../internal/contracts/records.md):任务记录结构与证据关联
- [受控写入协议](../../internal/protocols/gate-protocol.md)**《受控写入协议》**:两层拦截、`mgs-gate` 工具、越界探针与凭据处理的唯一权威(必须先读)
- [writing-for-agents](../../internal/methods/writing-for-agents/SKILL.md):文档写入方法(写审查记录前必读)
- [独立审查模板](../../templates/evidence/review.md):审查记录字段参考(两轴表、未覆盖、修复后复核);结果记录字段以[工作结果模板](../../templates/work/result.md)《结果字段》为准(被核对的结果记录按此字段)
- 统一接口:`<插件根>/records/mgs_records.py`(config/list/show/deps,读取任务与规格引用,不硬编码目录)

共同执行规则、受控写入协议与结果字段以上述三个权威文件为准;本入口只补充独立审查的专业差异(版本绑定、两轴独立执行、证据与影响),不重复其中的共同规程。

若当前上下文没有给出技能安装位置,在 `$CODEX_HOME` 下定位 `skills/game-review/SKILL.md`,再取其包根(上级两级)。

## 步骤

1. **确认输入**:任务说明中给出的项目根、执行凭据(token)、被审对象(任务身份或成果引用)、待审范围与审查依据。**没有明确的待审成果和版本时不开始**——审查对象必须显式引用,不从可开工集合选取(ready 是开工视角,待验收成果不在其中);缺凭据时报告无法写入审查记录并结束,不伪造。
2. **独立读取,不依赖作者总结**:经统一接口 `show/deps` 读取被审任务记录与依赖(不凭记忆);再**直接读取**当前要求与规范(设计基线、技术约定、规格条文)、**实际成果文件**与必要证据(结果记录、检查输出)。任务的结果记录只是**线索之一**——每项声称都以实际文件与实际运行的检查核对;结果记录声称的内容与实际文件不符时,这本身就是要报告的问题。
3. **固定待审版本与完整范围**:列出**文件清单**并登记每个文件的 **SHA-256 指纹**(待审版本快照),写入审查记录。范围覆盖实际待审内容的**全部形态——适用的已提交、暂存、未暂存和新建成果**:**直接读取工作区实际文件**,不以 HEAD 版本、暂存区或任何 git 对比输出替代实际文件读取;git 状态只作辅助信息记录。新建(未跟踪)文件不会被 diff 类对比显示,必须靠完整文件清单发现。清单和指纹固定后,审查结论只对该版本成立。
4. **按被审对象选择审查轴**:
   - **代码**:按 **Standards**(项目文档化的编码规范、约定;项目没有文档规范时按通用代码质量判断,代码异味类一律标为判断)与 **Spec**(对照规格条文、任务完成标准、行为约定)两轴**独立执行、分别呈现**——两轴各自给出结论与问题清单,不合并、不用一轴结论掩盖另一轴(代码完全合规范但行为不符规格,是 Standards 通过而 Spec 需修改)。
   - **设计或资源**:按其**专业标准**(格式、结构、规格可机械核对项——如图像尺寸与良构、音频采样率与时长、文档结构)与**需求符合性**(对照设计基线条文、任务完成标准)两轴分别检查;审美、听感等主观项不替人判断,归入未能检查并给出需要的真实反馈方式。
   - **已有自动化能可靠检查的内容引用其检查结果**(不重复人工执行);引用前核对检查确实针对当前待审版本。
5. **检查实际运行**:能自动核验的项(行为冒烟、格式规格、引用解析、哈希对应)**实际运行**并记录命令与真实输出;一次性检查脚本放**会话工作区或系统临时目录**(不进项目、不引入第二套工具链)。无法自动核验的项归入**未能检查**,说明原因与所需条件(如需要真实音频设备、需要人工审美),不以自动检查替代人工判断,也不虚构通过。
6. **问题清单与分类**:每项问题关联**具体证据**(文件、位置、引用的实际内容或检查输出)与**影响**(对规格符合性、行为或后续工作的实际影响),并区分三类:**明确规则违背**(有规格条文或项目明确规则可引)、**专业判断**(审查者的判断类意见,含代码异味,标注为判断)、**未能检查**(缺条件无法核对)。没有问题也逐项给出"已核对+证据",不空泛写"通过"。
7. **核对范围并写入**:按[受控写入协议](../../internal/protocols/gate-protocol.md)调用 `mgs_scope` 确认可写范围——审查实例写入**仅限本次审查记录和证据**(项目 evidence/ 区,按[独立审查模板](../../templates/evidence/review.md)字段)。**不修改待审专业成果**——发现需修复的问题**返回执行流程**由对应制作或设计任务修复,审查者不代改;代码、资源、产物、设计基线与任务记录都不在本入口的写入范围。审查记录经 `mgs_write` 写入(新文件 `expected_sha256=absent`)并回读核对;记录关联被审任务身份、待审版本指纹与证据位置。
8. **修复后复核(新版本)**:待审成果被修复后,复核针对**实际新版本**重新执行——重新登记当前文件指纹,重新运行可自动核验的检查,逐项核对旧问题在新版本中的实际状态;**旧结论不挪作新版本通过证明**:旧报告的指纹与当前文件不一致即证明版本已变,必须以当前实际内容为准重新下结论,不挪用旧结论充当新版本的通过依据;复核记录引用新版本指纹并注明与原审查版本的对应关系。
9. **未覆盖与限制**:审查记录写明**未覆盖内容**(未检查的部分及原因)与**覆盖限制**——尚未实现的运行能力(如试玩入口、真实设备播放、人工审美)如实标注为本框架当前覆盖限制,不冒充已验证。
10. **不代验收**:审查完成是被审任务验收方式中"独立审查"一项的事实;**人工验收项(试玩、审美、听感)保留待验收**,任务进度与分流归统筹维护,本入口不改任务记录;需要统筹同步的事项写入审查记录的交接说明。
11. **边界核对**(任务说明要求时):按[受控写入协议](../../internal/protocols/gate-protocol.md)《越界探针》执行直接写探针与越界 `mgs_write` 探针(如对待审成果文件),记录与未要求时的处理均按该节纪律。
12. 输出报告(见下)。

## 报告结构(固定)

```
## 独立审查报告
### 审查范围(被审对象与任务身份;待审版本:文件清单与 SHA-256 指纹;范围形态:已提交/暂存/未暂存/新建;git 状态辅助信息)
### 审查依据(规范与规格版本;实际运行的检查与真实输出;引用的既有自动化结果)
### Standards 轴(代码规范符合性;结论:通过/需修改/未能判断;问题与证据)
### Spec 轴 / 需求符合性轴(对照规格条文;结论:通过/需修改/未能判断;问题与证据)
### 问题清单(逐项:位置/证据/影响/分类[明确规则违背|专业判断|未能检查])
### 未覆盖与覆盖限制(未能检查项及原因;尚未实现的运行能力)
### 交接(审查记录与证据位置;需返回执行流程的修复项;待人工验收项;统筹同步事项)
```

资源类审查(设计、视觉、音频)的轴名按专业表述为「专业标准轴」与「需求符合性轴」,分别呈现的纪律与代码两轴相同。报告按[共同合同](../../internal/contracts/common.md)《共同执行规则》的「未参与者可独立读取」标准书写,引用实际任务身份与基线版本,不依赖对话记忆。

## 边界

- **独立**:独立于原执行上下文检查——不沿用原作者的结论,直接读取规范、实际成果、当前规格及必要证据;作者的结果记录只是待核对线索。
- **同专业、不新增常设评审角色**:按被审对象的专业(代码/视觉/音频/构建/设计)选择同专业审查实例;审查是执行实例的一次用途,不是新增角色。
- 审查实例**仅写报告和证据**(evidence/ 审查记录),**不能修改待审专业成果**;修复由对应制作或设计任务执行,修复后针对实际新版本复核。
- 待审版本与范围先固定(清单+指纹),含适用的未提交与新建成果;直接读工作区实际文件,不以 HEAD 或暂存区对比替代。
- 每项问题关联具体证据和影响;区分明确规则违背、专业判断与未能检查;代码异味与审美类判断标为判断,项目明确规则优先。
- 已有自动化能可靠检查的内容引用结果;检查必须实际运行的项不虚构输出;未能检查如实说明。
- 未实现的运行能力(试玩入口、真实设备、人工审美等)标为覆盖限制;审查报告生成不等于验收通过,不以报告替代通过;人工验收项保留待验收。
- 任务进度与分流归统筹;发现规格本身的问题交回设计与统筹流程,不自行改产品要求。
- 凭据处理按[受控写入协议](../../internal/protocols/gate-protocol.md)《执行凭据》一节;不执行任何外部动作(提交、推送、发布等),外部动作边界见[共同合同](../../internal/contracts/common.md)《写入与保障》。
- 失败或中断时保存已完成的审查部分与缺口,如实交接。
