# 项目协作配置合同

> 包内适配版(mygamestudio 0.4.0 建立,任务票 17 更新包内说明)。来源:插件设计仓库 `.scratch/mygamestudio-framework/contracts/project-configuration.md`。本版仅按包内现状补写说明,语义与设计一致;文件指纹与来源见包内 `provenance/manifest.md`。

Game-Init 负责本合同,相当于把原 setup 的项目协作配置能力整合进游戏接入流程。参考探查和确认方法,不直接运行原始 setup 的默认写入。

## 配置范围

| 项目配置 | 首版约定 |
| --- | --- |
| 任务后端 | 本地 Markdown 或 GitHub Issues;已有有效配置优先沿用,无既定方式时为个人项目建议本地 Markdown并由初始化清单确认 |
| 任务位置 | 本地任务根目录,或明确的 GitHub host、owner、repository;不扫描无关仓库 |
| 五类标签 | 沿用五类 canonical 语义,可映射到项目现有标签;映射完整且不冲突 |
| 核心文档 | 默认本地 Markdown,允许沿用已有路径;记录实际项目约定、游戏设计、技术设计位置 |
| 领域资料 | 记录术语与决定的实际位置,沿用已有单一或多上下文布局;新小项目保持简单 |
| 外部访问 | 记录可用连接的引用及已明确的操作范围,配置文件不存明文凭据 |

任务后端与核心文档位置分别配置。使用 GitHub Issues 管任务,不要求把整个游戏设计文档复制进每个 Issue。

## 配置过程

1. 读取项目已有约定、文档和任务线索。完成条件:能区分已经确定的配置与仍需选择的部分;原项目保持只读。
2. 沿用可用配置,针对缺失项提出简短建议。完成条件:任务源、标签映射与资料位置可确定,无互相冲突的当前来源。
3. 将配置和拟写内容加入初始化清单,确认后生效。完成条件:目标位置与外部动作明确,原有规则及周边内容保留。
4. 通过统一接口回读任务、标签与文档引用。完成条件:后续 Skill 能按配置找到资料;读可用与写已获授权分别记录。

若需要增加或修改项目 AGENTS.md 等入口指针,必须将确切文件和变更列入清单取得相应授权。保留现有文件与全局规则,不能沿原 setup 的默认选择自动修改其他客户端文件。

## 配置的保存与引用

新项目可使用 CONFIG.md 保存协作配置,由 INDEX.md 提供带条件的入口。已有 docs/agents/ 配置等可直接复用,通过入口或 CONFIG.md 引用其权威位置;每项配置选择一个维护位置。

CONFIG.md 是协作配置,不是运行时权限凭证。具体执行仍按任务允许修改范围及宿主/项目已有授权核对,不经 mgs-gate。

## 切换与离线

切换后端先读取现有任务与关联,提出迁移映射和保留方案,确认后切换当前来源。旧记录保留历史身份,不形成两套可独立修改的当前任务账本。

远端不可用时可展示注明时间与来源的缓存,或保存待发布草稿。不能将草稿报告为已发布任务,也不能静默改用本地后端。外部写入结果不确定时先回读再重试。

其他任务平台预留后端接口,未实现的后端不声称具有可执行支持。
