# 审查与试玩合同

运行任一入口前采用[共同合同](common.md)。本组是工作方式,按被审查对象选相应专业执行实例,不新增常设角色。

## Game-Review

- 输入：明确的待审成果和版本、当前要求与规范、相关证据、需要检查的范围。
- 工作：独立于原执行上下文检查。代码按 Standards 与 Spec 两轴分别审查；其他产物按适用专业标准及需求符合性检查。输入覆盖实际待审内容，包括适用的未提交和新建成果。
- 输出：审查范围、两类结论、具体问题与证据、未覆盖部分及修复后的复核结果。
- 写入：本次审查记录和证据；修复由对应制作或设计任务执行。
- 完成：所有要求的审查项有依据明确的结论；发现需修复的问题返回执行流程，不能以审查报告生成代替通过。

代码审查的两轴独立执行、分别呈现，避免规范符合性掩盖需求问题。已有自动化能可靠检查的内容引用检查结果；代码异味类判断标为判断，项目明确规则优先。

## Game-Playtest

- 输入：明确的版本与入口、要检查的场景或问题、适用要求、可用控制工具及人工参与约定。
- 工作：制定必要步骤并实际执行可用的检查，记录输入、观察与证据；需要人的体验判断时给出明确试玩任务并记录实际反馈。
- 输出：版本与场景、已执行步骤、观察和证据、缺陷或反馈、尚未执行的部分。
- 写入：本次试玩记录、证据及允许的测试运行状态；不改产品基线来迁就观察结果。
- 完成：所称已试玩部分有实际执行证据，人工结论来自实际反馈；仅制定计划的工作明确标为计划。

Game-Playtest 获取运行证据，Game-Review 对照约定审查，两者按任务需要组合。只有在本轮发生新改动、检查失败或出现具体疑点时，扩大或重复相关验证。

## 包内说明

Game-Review 与 Game-Playtest 不再作为公开技能入口。代码审查走 Matt `code-review` 与 `internal/review/pending_review.py` 的完整待审捕获；试玩判断记在对应任务上。上列合同保留审查与试玩语义，供任务字段引用，不恢复独立入口。普通工作使用宿主和项目已有工具，不经 mgs-gate。旧入口去向见[旧入口与 gate 去向](../game/retired-entries.md)。
