# 反馈循环与证据

## 什么算能抓住原问题

从用户现象和已确认的正常行为定义观察。真实触发路径与失败条件都必须在检查里：重开后重复结算，不能只测“奖励函数单次调用返回正确数字”；游戏卡顿，不能只测某段计算很快；无错误日志也不能证明玩家交互正常。

优先复用已有红灯、崩溃记录、测试资源或运行步骤。可选方式包括：正常接口测试、引擎内最小操作、可回放输入、构建命令、真实请求回放、同条件对照和必要的人工设备操作。不要为使用技能先创建一个新测试框架。

实际运行时，辨认“用户报告的故障”“无关环境失败”“本次没有捕获”。三者不能合并成通过或失败。创建命令不等于已经运行；终端退出成功也不一定覆盖需要观察的游戏行为。

只读诊断可检查现有日志和成果，不能因此植入探针或修改项目。用户只希望了解报错含义时，直接解释可支持的部分，不启动整套实验。

## 抓不到时如何推进

先评估现有真实材料能支持什么结论。来自同一版本的日志、调用栈和录屏可以缩小原因范围，但不自动证明拟议修复有效。可以提出带条件的候选和最小新增采集需求，不能把自己写的故障模型当成原项目复现。

缺少设备时只请用户完成无法代理的一段操作，提供场景、版本、输入、应观察的现象和必要输出。不要索取未脱敏的整个账号、全量私人存档或与故障无关资料。单次反馈不足时说明局限，不反复让用户试一堆没有区分力的改动。

## 最小化与间歇故障

最小化保留引发问题的真实条件，优先删除无关步骤，而不是切断必要的生命周期。达到足以高效区分原因的规模即可；无法减少的实际设备条件无需假造替代。

记录每组尝试的版本、条件与失败情况。固定种子、控制时间、隔离输入有助于重放，但不能承诺跨平台、引擎或执行顺序都完全确定。日志、调试器和人为延迟也可能改变被测时序，要把这类实验与原始条件分开报告。

修复前后使用可比较的环境与样本。零次失败只支持“本次这些条件和样本内未复现”，不自动升级成全局根除。是否已达到本任务的检查标准，依任务范围、风险及已约定标准判断，不设所有游戏通用的尝试次数或失败率阈值。

## 候选原因和实验

每个候选应能被证据排除：支持线索、可观察预测、区分它的操作。候选数量由问题决定，不凑列表。发现真实差异后及时更新判断，不同时修改五个因素再从绿色结果猜原因。

优先通过已有调试器、定向日志或性能采样获取必要信号。临时日志使用可识别标记并在修复后清理；默认不输出整个请求、整个存档或所有环境变量。

## 版本对比与二分

仅在版本、资源、配置和必要测试输入可对应时使用对比；旧代码配新资源导致的错误不能误判为当时就有的回归。先保护当前未提交工作，采用获准的隔离检查目录或项目已有安全方式；不默认 reset、stash、切换共享工作区或强制清理。

Git 的 `bisect run` 将退出码 0 视为正常、1 至 127（125 除外）视为异常；125 表示该版本不能测试。只有无关构建/环境错误才适用不可测处理；本次原问题若就是构建失败，不能把它跳过来掩盖。跳过关键相邻版本可能只能缩小范围，不能保证得出唯一引入提交。[Git 官方说明](https://git-scm.com/docs/git-bisect)。不要仅凭被定位的提交就断言具体根因，仍需检查行为变化和因果证据。

## 性能检查

围绕已报告的场景退化或明确目标测量，不从“帮我找全库所有性能问题”自动开展无限审计。保留设备、场景、构建类型、分辨率、质量设置、冷热启动和测量方式中影响结论的条件；按症状选择帧时间、加载时长、内存或其他已有指标。

不只比较两个不同时点的平均帧率；先确认变化真实，再定位关联路径，复验同一条件。降低质量、去掉功能或跳过数据可能是权衡或绕过，不应不经确认冒充满足原要求的优化。

目标设备问题优先取得目标设备数据，编辑器测量只说明编辑器环境下的事实。Unity 的目标平台性能指南可作为按需方法来源，不把其中版本相关操作硬编码进所有引擎：[官方指南](https://docs.unity.com/en-us/engine/6000.7/manual/analysis/profiler/profiling-applications/profiling-target-device)。

## 按事实交付

建议简述：原症状与适用版本；复现或测量入口及结果；原因结论的依据；实际修改或未修改；回归结果；仍缺的证据与人工行动。这是可裁剪的沟通要点，不是必填报告。

可以交付有价值的阶段调查而未修复；可以确认原因而未获修改许可；可以完成修复但尚未目标设备验证。分别说清楚，不把其中一个冒充另一个。
