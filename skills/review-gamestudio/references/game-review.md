# 游戏成果的按需评审视角

游戏专业知识帮助识别实际交付的断点，不成为增加机制的模板。先明确当前任务是功能、独立资源、内容、工程调整还是已有成果的检查，再选择相关视角。它们不是任务类型、第三评审轴或新技能注册表。

## 将专业问题放回两条评审线

Standards 问：这份代码、资源或内容是否遵守当前项目适用的制作约定？
Spec 问：当前任务承诺的游戏行为或其他成果是否完整、正确且没有越界？

例如，项目规定资源必须保留特定身份信息而本次丢失，属于规范问题；要求实际受击反馈但资源未接入，是需求问题。同一根因同时涉及两轴时相互引用，不虚增两个独立故障。

## 功能闭环

从已确认的起始状态、玩家操作、规则结果与反馈核对。相关代码存在但场景未引用、资源已导入但事件未触发、结算正确但重复操作会重复发奖，都可能成为当前任务的真实断点。

只检查任务声明或确实受本次变化影响的行为，不展开整款游戏。模块测试支持对应规则结论，不自动证明输入、碰撞、场景生命周期和实际资源链路。

## 资源与内容

核对真正交付的源版本、导出资源、依赖和工程引用是否对应。源文件在工程外不是缺陷；缺少获准且必要的版本与恢复依据才是应说明的缺口。按项目规则区分候选、有效测试资源、运行资源和生成缓存，不把所有临时字样文件视为垃圾。

独立美术任务按约定的源文件、格式、动画与交接标准评审，不强行要求整套玩法可用。功能任务已经承诺工程集成时，只有资源预览不能算完成。占位是否允许取决于本次规格，不因为是早期版本就擅自降级，也不因尚未最终美术就扩大任务。

## UI、视觉与声音

已确认的界面状态、输入方式、信息辨识和反馈目标是依据。截图支持静态呈现的判断；交互需要相应运行证据；动画和声音需要其时序、内容与实际触发的证据。无法查看或播放时说明限制，文件名正常不等于内容正确。

有参考图也需确认它是方向参考还是精确验收目标。未授权的新审美偏好只作建议，不判为硬性不合格。存在明确标准、足够证据和判断授权时 Agent 可以审视觉；用户保留的最终风格或真实体验仍待本人决定。

## 状态、平台与性能

按本次变更风险核对时间、暂停、重复输入、场景恢复、存档、随机或网络依赖。不存在的机制不添加；测试种子、配置和运行环境与目标是否一致需核对，不能把一个可控用例推为所有平台通过。

已有性能目标时引用其设备、场景与测量条件。编辑器结果、录屏和目标设备实测的证明范围不同。没有要求时可说明回归迹象和需要测量的风险，不凭行业印象发明性能门槛。

## 体验与责任

按共享任务责任说明区分已检查结果和待人工接受项。体验尚未发生是验证缺口，不等于已证明不好玩；玩家要求的反馈确实缺失则是可报告的需求问题。

技术检查通过、代码评审通过、人工接受、任务完成与发版是不同结论。复核能否直接满足其中某项，而不是让一个总分替代全部。

## 示例：首次开启宝箱（虚构）

假设已确认“首次发奖、不能重复发奖、播放指定开启动画”，当前任务还要求开发者体验反馈。已取得同版本的余额测试，但动画只有独立预览、没有场景接入。

Standards：若实际资源命名与版本关联符合规范，可报告已检查范围内未发现违规；看不到的源依赖另列缺口。
Spec：余额测试支持首发与防重发行为；若确认场景没有动画连接，则指出“要求的动画尚未接入”，不能只写视觉建议。
人工条件：尚未获得开发者对该版本的体验确认。修复必要缺失并准备可玩版本后，才由实现入口交接。

评审提出有依据的发现与未验证事项，不自行生成动画、修改设计或关闭任务。
