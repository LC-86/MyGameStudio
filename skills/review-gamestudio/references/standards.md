# Standards：规范与代码风险

项目适用规范是主要依据。读取与本次交付有关的约定，不加载整套无关手册。当前授权或项目规范若要求不可绕过的安全和权限边界，不会因某段代码的局部偏好而消失。

项目采用一种做法时，不仅凭个人偏好或常见模式判它违规。代码有可见的正确性问题或外部风险仍应依据实际影响说明；不是因为写进规范就不再核对。

Matt 固定版本内置以下十二项 Fowler code smell。这里保留相同观察主题，采用简短中文解释；它们均是启发式提示，不是确定错误或自动要求重构。只有与本次变化有关且有实质影响时才报告。

| 名称 | 要观察的现象与改进方向 |
| --- | --- |
| Mysterious Name | 名称掩盖用途或混淆概念；考虑采用项目明确词义，而不是任意美化。 |
| Duplicated Code | 同一规则在多处重复实现并可能不同步；判断是否确实应当集中。 |
| Feature Envy | 逻辑主要依赖另一个对象的数据；考虑将知识归属放回合适位置。 |
| Data Clumps | 相同参数组合频繁同行；有真实共同概念时再组合成对象。 |
| Primitive Obsession | 简单字符串或数字掩盖重要领域语义；仅在确有约束时建议表达类型。 |
| Repeated Switches | 多处重复按同一类别分支；检查新增变化是否需要到处同步修改。 |
| Shotgun Surgery | 一项概念变化散落到很多无关位置；考虑集中相关知识。 |
| Divergent Change | 同一模块被多个互不相关原因驱动；讨论职责分离的真实收益。 |
| Speculative Generality | 为尚不存在的需求添加通用层或参数；回到当前已确认用途。 |
| Message Chains | 调用者必须沿多层内部结构导航；考虑提供更直接的行为入口。 |
| Middle Man | 模块只搬运调用而没有隐藏知识；评估去除后是否减少复杂度。 |
| Refused Bequest | 继承关系要求实现者放弃大部分接口；核对组合是否更适合真实用途。 |

报告时先给定位与具体影响，再标“可能的……”及改进建议。不是看到 switch、原始类型或一次转发就自动违规；同一代码形态在不同背景中可能合理。

自动工具已经检查的格式与类型规则，复用本次有效结果，不再人工逐项重复。实际失败必须在报告中可见；工具未运行也不能假装通过。对工具不能覆盖的语义和约定继续评审。

纯资源任务不运行代码 smell 清单。资源格式、命名、依赖、导入或性能要求按项目标准和当前任务处理；缺少阈值时说明测量与风险，不捏造统一的面数、贴图尺寸、帧率、音量或包体限制。
