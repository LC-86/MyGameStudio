# 游戏行为的测试参考

这是一组按需选择的检查视角，不是每个任务都要覆盖的题库。游戏规则仍以项目已采纳的 GDD/spec/任务为准。

## 能通过重复观察验证的内容

条件触发、数值结算、次数上限、状态转换、进度保存与恢复等，通常可以寻找相应行为入口。具体测试应包含已确定的前提和结果，不能从通用知识推导出新机制。不存在冷却、存档或失败惩罚时，不因为参考里提及就增加这些系统。

## 选择足以覆盖风险的层次

纯规则可从稳定模块入口测试；输入、场景引用、动画事件、资源生命周期等问题，可能需要引擎内或集成测试。不要把所有功能从 UI 测一遍，也不要只测方便的底层函数而遗漏实际出错的连接。

Unity 官方区分 Edit Mode 与 Play Mode 测试：前者涉及编辑器环境，后者允许在运行时执行，具体支持和使用方式随所装版本与项目配置核实。本参考不固定某个引擎版本或强制工具。

## 时间、循环与并发来源

测试冷却、持续效果和节奏相关规则时，明确观测的是模拟时间、帧推进还是现实时间。优先受控时间推进；测试结束恢复暂停、时间倍率和其他被修改状态。

纯逻辑测试通过，不自动代表不同帧率、物理设置和设备都通过。哪些环境属于本次覆盖，由任务约定；只对实际运行过的环境给结论。浮点误差容许范围须有依据，不能为了绿灯随意放宽。

## 随机与关卡输入

使用可回放的种子或输入序列定位行为错误，并检查真正的规则约束。一次随机结果符合预期，不足以证明总体概率正确；需要统计检查时先约定样本与容许范围，并说明随机失败风险与环境。

## 重复触发与状态恢复

奖励重复发放、暂停期间状态推进、死亡或场景重载后的残留，都可以是实际需求相关时的测试目标。测试之间独立准备和清理场景、全局状态、监听器与临时存档，不把先前测试的成功当成本次初始条件。

## 必要测试资源不是候选垃圾

可复现测试所需的最小场景、图片、模型、音频或固定存档属于有效输入。按 setup 的资源约定保存可用版本及必要导入元数据；外部资源要能取得指定版本。大型批量候选不混进测试仓库，但不能用“测试资源全部忽略”破坏测试恢复。

## 自动检查的结论边界

可以检查提示是否触发、材质是否缺失、文字是否遮挡等明确条件；视觉基线比较只证明相应差异，不能证明主观美术方向正确。真正的手感、可理解性或由用户保留的审美选择，不能用一个常量或主观自评代替。

性能检查需匹配约定设备、工作负载和测量方式，不把模拟规则测试当作真实性能通过。体验与设备检查并不因本轮不采用 TDD 就可以省略，交回实现任务选择恰当验证方法。
