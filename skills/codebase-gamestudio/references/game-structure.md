# 游戏代码结构：按当前问题取用

本参考提出观察问题，不规定固定引擎、层数、目录数量或通用架构。

## 状态归属与生命周期

区分本帧、本次动作、本局和跨局状态，明确真实拥有者、可写入口及重置时机。场景重载、暂停、对象池复用、异步加载或事件订阅涉及当前行为时，检查谁负责创建、取消和清理。没有涉及的系统不提前建设。

示例：角色显示的血量、规则计算中的血量和存档中的血量是否是相同状态的不同用途？不能仅为“统一”把设计上不同的数值合并；也不能无理由维护互不一致的重复真值。

## 规则与表现

需要独立验证的规则，不应只能通过读取 HUD 文本或检查动画内部变量才能得到。表现层消费已经明确的行为结果；如果动画时序本身参与判定，明确该交互而不是为了纯函数形式把它删掉。

回调、节点、组件、系统、脚本都可以承载职责。遵循项目与引擎已有机制，不把 Matt 的 module、interface、seam 等概念变成对词语或类型名的强制替换。

## 引擎与外部能力

场景、物理、资源生命周期等真实集成行为，仍需要覆盖该环节的检查；纯规则测试不替代它们。时钟、随机来源或存储可以在必要时控制，优先使用已有能力，不把每个引擎 API 包成自己的框架。

## 内容、资源与运行代价

按现有项目约定区分源资产、导出资源、运行实例与缓存。内容身份和资源引用不应因为仅整理代码就被随意改变。存档结构或资源身份迁移属于另一个有实际影响的决定，不藏在接口清理里。

高频调用、分配、资源释放和同步等待有明确风险时再测量；“更深”“更少方法”不证明更快。数据局部性和项目性能证据可以改变结构取舍。

## 示例：宝箱奖励

假定奖励规则已经确定。结构设计应明确开启资格和已领取状态由谁维护，如何产生一次奖励结果，界面与音效如何得到结果，跨场景持久化如有要求由谁处理。

它不应擅自增加掉落稀有度、通用事件总线、背包经济或存档系统；也不应为了“分层”先建一套尚无调用方的接口。

## 来源与适用限制

方法适配自 Matt 的 `codebase-design` 及其 `DEEPENING.md`、`DESIGN-IT-TWICE.md`；上游出处见本目录内的许可通知。这里的游戏情境是 MyGameStudio 的设计建议，不是一套经过实测的通用引擎标准。
