# 责任、分流与交接

本文件是 MyGameStudio 任务协作方法的共享参考，不是新的状态机或任务后端。拆票、实现、评审和导航使用同一含义。项目只需记录实际映射与不同的既有约定，无需复制全文。

## 三个信息各守一件事

标签说明下一执行段由谁推进；验收条目说明谁确认哪个结果；现有任务状态说明工作是否结束。标签不代表永久归属，不是最终签字人，也不是权限凭证。

- `ready-for-agent`：下一执行段已经明确，可以由 Agent 承担。进入实际可领取集合还须确认真实依赖已满足、未被其他执行者占用，以及工具和授权允许。以后需要人的验收，不妨碍现在由 Agent 实现。
- `ready-for-human`：当前确有一项可以由人接手的具体行动，必要输入已经准备好。可能是体验、方案选择、明确的人工操作，不一律等于“人工写代码”或“等待试玩”。

同一开放任务使用一个当前分流标签或项目已有的等价字段。交接时按映射替换对应旧分流，不累积互相矛盾的角色；保留无关标签。已关闭任务的标签按项目已有习惯处理，不靠 ready 标签表示结项。

`needs-info` 仍表达缺少实际需要的信息；`needs-triage` 仍用于需要评估的来件；`wontfix` 表示明确不做。已有票由本技能清楚拆出，不因此再走一轮外部来件分流。任务依赖单独记录，不能因为依赖未完成就说需要用户验收。

这些是项目对 Matt 分流含义的细化，不宣称 Matt 原版自动支持同票 Agent→人工的交接。若原有自动化把 ready-for-agent 视为整票全自动处理，须在使用新约定前修改领取与关闭条件；未改造的执行器不应用于含人工验收的任务。没有增加新标签，但执行规则仍需要一致。

## 怎样分配每项判断

优先沿用项目、spec 和用户已确认的责任。每项要求先判断标准、证据和授权：

标准足够明确，当前执行者可以获得足以支撑结论的真实证据，并获准作出该结论时，由 Agent 自主完成。这里包括被明确授权的视觉检查，不按学科一刀切。

用户明确保留的体验感受、重要设计取舍和最终风格选择交给指定的人。实际玩家体验不可用模型模拟代替。Agent 先完成可独立验证的准备、分析和检查，不把所有工作推给用户。

标准不明先查现有资料；仍有会改变结果的选择才问。工具不可用先处理已授权范围内可解决的问题；确实需要人提供访问或在其设备操作时，说明具体步骤，不假装原检查已通过。

没有人工要求、依据与证据充分的任务，不另造人工验收。没有任何明确依据时，也不能将“未写验收人”理解为无限自我授权。

## 同一张票的正常交接

先由 Agent 完成实现与自己的检查。交给人之前，提供实际可识别的版本、可用的启动或预览方式、必要操作场景、需要回答的具体问题、已经执行的检查和遗留限制。

准备工作真实完成、只剩人的那项行动时，按已有记录授权切换为 ready-for-human，保持任务开放，人工项保持未完成。常规检查失败就继续修复或如实阻塞；不能拿打不开的成果让用户完成体验验收。其他独立、已授权工作可以继续，不必把整个项目都暂停。

接到反馈后，仅对本次反馈明确覆盖的版本与条目记录结论。截图只支持静态布局时，不由此确认交互与手感；“看起来不错”是否属于最终批准需结合明确上下文判断，不能默认为对未展示内容的全面接受。

反馈要求修改时，将具体差异和必要的复查范围交还 Agent。涉及新的设计决定时回到当前讨论，不能把用户的试玩反馈自动变成 GDD 规则。修改影响原验收依据时，受影响项需重新核对，未受影响且仍适用的证据可保留。

若本轮无标签或关闭的写入权限，只报告建议动作和已完成事实，不宣称已修改远端，不重复完成已有工作以回避交接。

## 什么时候可以结束

没有人工环节：Agent 的约定成果和所有必要检查都有足够证据，无阻塞问题时，可以在已有授权内标为完成；无关闭权限则报告满足条件，不能声称已经关闭。

有人工环节：除上述条件外，指定人的适用确认已经取得，才可以宣称整体已验收。无人回复不等于通过；完成实现不等于体验已经接受。关闭或推送不会扩大原任务授权。

独立探索任务获得否定结果，若已完成约定调查并提供有效证据和局限，可以完成其研究工作，但不能说候选玩法通过。独立验收票也可以以“不通过”完成检查报告；被验收的功能仍不满足条件，不能因其检查票关闭而被下游当成通过。

任务的前置条件若是“验收通过”，必须读取结论而非只看依赖票 closed。任务被取消或放弃也不等于依赖所需成果已交付。这是在已有依赖说明中写清条件，不新增一套通过标签。
