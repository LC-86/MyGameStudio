# 游戏成果与验证

按当前任务需要使用这些视角，不作为工种分类或必填清单。

## 功能成果

从实际游戏场景说明起始条件、玩家操作、规则结果与可识别反馈。完成所需的代码、内容、资源、场景接入和自检尽量由同一成果覆盖。正式工程已有条件可验证时直接复用，不默认另建演示游戏。

## 基础工程与独立资产

底层逻辑只有在具备真实使用方、独立目标和可验证接口时才单列，不为未来猜测先造框架。与某个功能绑定的小实现步骤留在功能内。

独立美术、音频或关卡工作确有专业交接或规模需要时，可以单列。写明输入、参考、版本、源文件和导出要求、当前是否允许占位，以及接入工程与游戏内检查由谁承担。资产文件验收完成不等于对应功能完成。

沿用 setup 确定的资源区、版本与备份规则。只记录本次必要的源版本和工程对应关系，候选与缓存不混进工程交付。不在拆票时备份或删除资源，不把“规定要备份”写成“已经可恢复”。

## 玩法探索

明确本次要减少的不确定、已有版本和可观察证据；确需制作验证内容时限定范围。否定原假设可以是研究成果，未采纳试验值不自动进入正式规则。实际试玩、测量或访问未执行时，报告未完成，不能以一份意见代替。

## UI、美术和体验检查

客观状态、引用、尺寸或约定的画面偏差，在实际能力及授权足够时可由 Agent 检查；图片能说明什么就只说明什么，不能由一张截图证明操作响应、动态效果或玩家感受。

最终风格取舍、手感或指定人的接受结论，由相关验收条目所指定的人判断。人员、检查场景与实际成果就绪条件写清，不把“人工试玩一下”当成充分验收标准。

## 环境与证据

涉及目标设备的操作、画面或性能时，写明需要的环境，不把编辑器检查等同于目标设备结果。来源可查的规则和已执行的证据分开。必要测量的阈值应来自已确认要求或明确试验假设，不能拆票时虚构。

一般自检跟随交付，不机械另建验收票。只有跨多个成果、独立检查者、时间或访问条件确有需要时再单列检查，并写明不通过后如何交接；不要求下游把“检查已完成”当成“对象已通过”。
