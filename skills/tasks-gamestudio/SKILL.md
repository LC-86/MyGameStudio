# Tasks GameStudio

沿用完整小成果的拆分方法。让一个新会话能够看懂任务、找到依据、知道怎样验证，以及自己的完成范围在哪里。

任务票是交给另一个上下文执行的正式内容，接收方没有当前对话。按技能名称取得 `writing-for-agents` 的写作方法组织每张票；需要派发子代理时另读取 [docs-gamestudio 的委派参考](../docs-gamestudio/references/delegation.md)。同一上下文已经取得方法就直接沿用，不为每张票重复取得；无法取得时说明具体缺口和受影响的工作，只继续不依赖它的部分，不模仿缺失的方法。

不建立新的必填任务类型。底层逻辑、玩法、UI、美术和音频描述工作涉及的方面，不决定任务必须怎样拆，也不直接决定由谁验收。

## 1. 读取当前范围与项目约定

从用户指定的 GDD、spec、计划、任务或当前对话中获取已经明确的工作范围。必要时读取相关正文、已采纳修改与讨论，沿用项目术语和实际工程。已有信息足够时不重复调查，也不强制先生成 GDD 或 spec。

按项目入口定位任务来源、实际标签映射、验收约定与资源管理说明。缺失项只补影响当前工作的部分。只读查看相关现有任务，避免重复建票；对已有票提出范围明确的更新，不覆盖无关内容。

先读取[责任、分流与交接](references/task-responsibility.md)。若项目采用不同的既有语义，先显式说明差异并沿用有效约定，不静默改变标签含义。

关键设计缺失或相互矛盾时列出缺口，不在拆票时发明规则。独立且已经明确的部分可以继续整理，未明确部分不标为可直接执行。

## 2. 拆成最小完整成果

功能任务穿过达成当前行为真正需要的层次，能够独立展示或验证，适合一个新的 Agent 会话连续推进。相关代码、必要资源、集成和自检属于同一个成果时，优先放在一起；不按文件、工种或技术层机械拆票。

技术基础、资源、内容或检查本身具有独立目标、输入与交接需要时，可以单独成票，并明确自身成果和后续集成责任。不要为了未来的人类验收，把整项可由 Agent 实现的工作从开始就交给人。

整体工作很小就建议直接处理，不为使用技能制造多张票。发现确有必要的前置重构时，先安排最小使能改动，不先搭建推测性的框架。大范围机械迁移可以先兼容、分批迁移、最后移除旧形式；只有整合后才能通过检查的，明确整合责任及这一限制。

涉及游戏行为、资源交付、玩法探索、UI 或美术检查时，按需读取[游戏成果与验证](references/game-delivery.md)，不用其中的视角制造未采纳系统或必填流程。

## 3. 明确依赖与验收责任

每张票引用必要输入及真实阻塞任务，并说明可观察的完成标准。新增行为的检查应能识别目标问题或缺失，保留既有行为的回归检查则验证约定未变；不把已经存在的空泛条件作为新增成果的证明。

验收项按实际需要注明 Agent 或具体的人负责。通常由 Agent 完成的明确检查可以合并说明；仅对需要保留人工判断的条目明确标记。若项目已经有等价字段，直接使用，不另建平行的“验收人”表格或类型系统。

判断依据是标准是否明确、执行者能否取得所需证据、判断是否在已有授权内，而不是是否涉及 UI 或美术。用户保留的体验、选型与重要取舍不能被自动验收。能够自主验证且获准的工作，也不无故增加人工审批。

需要人接手时，写明具体判断、预期输入和交接条件。实施过程中才知道的构建版本、链接和测试结果由实施者填写，不在拆票阶段编造。没有必要时，不为每张交付票另配一张验收票。

按项目实际映射采用 ready-for-agent 或 ready-for-human，表示下一执行段的推进方；说明下一执行段仍受依赖、领取状态、实际工具与授权约束。两种标签不同时作为当前分流，不用它们代替进度或最终验收结果。缺资料、依赖未完成、尚不能试玩各自如实表达，不伪装成人工验收已就绪。

## 4. 核对方案并确认保存范围

向用户展示每张票的标题、成果、真实依赖，以及确实需要人的判断和交接。说明特殊拆分的原因；普通内部步骤由 Agent 组织，不让用户逐项安排实现。

检查本次要求是否都有承担者、资源是否有人接入、验收是否依赖无人负责的工作。相同文件的修改冲突与业务依赖分开说明，不把“无依赖”当成可以无条件并行。

未获批准的拆分先提供草稿。已有授权明确覆盖拆分与发布决定时不重复索取同一确认；新增范围、重要取舍和未覆盖的远端写入重新确认。任务标签若会触发现有自动执行，发布前核对该效果是否已获授权，不能以“只是贴标签”为由启动未获准工作。

## 5. 保存任务并回读

采用项目已有工具和记录位置。本地一票一文件；远端一票一记录，在可用且获准时建立原生父子与阻塞关系，不支持时按项目约定使用明确引用。父子不等于阻塞；必要的关联写入之外，不关闭父项或改变其范围与状态。

任务保留当前交付所需的明确条件及来源引用，不复制整本 GDD，也不只写“见规格”。真实输入路径、资源标识和运行依据可以引用；避免编造未来的文件清单、行号和具体实现。原型最小片段确实承载已确认决定时，可注明来源引用。

外部写入结果未知先回读，不盲目重复创建；发现部分成功则报告已保存与未完成部分。无写入能力时交付明确标识的草稿，不换到未批准的数据源。

回读任务内容、分流、关键依赖与引用，报告真实结果。本技能到任务交付为止，不认领执行、不制作资源、不运行游戏、不提交推送。后续执行者遵循项目责任约定完成自检、交接和结项，而不是由拆票技能常驻管理。

## 任务正文参考

结构按项目调整；模板不是必须填满的表单。

```markdown
# 任务标题

依据与范围：本次要求、必要来源及明确不做的内容。
本次成果：可以独立使用、演示或验证的结果。
依赖：真正需要先完成的任务或输入。

## 验收
- [ ] Agent：明确行为或检查，以及需要的证据。
- [ ] 开发者／指定验收人：仅列确实要求人作出的判断。

## 交接（需要时）
接手前应准备什么，接手者需要决定或操作什么。
实际版本、启动入口、证据和反馈在执行后补齐。
```
