# 游戏资源与文档冲突

## 先判断冲突的实质

普通文本合并只处理部分问题。对象关系、资源身份、源文件与导出版本也可能冲突，即使文本能够自动合并，组合行为仍需要检查。查看共同基线和双方实际内容；删除/修改、重命名/修改、路径与大小写差异也需要核对。

## 场景与序列化资源

不要仅因文件可读或没有冲突符号，就认为对象关系正确。使用当前引擎已有且可用的专用合并工具或编辑器能力，不自建通用场景合并器，也不默认修改用户工具配置。

例如 Unity 提供 UnityYAMLMerge 处理场景与 prefab 合并。工具成功后仍核对当前任务相关对象、引用和运行结果。工具不支持当前文件或环境不可用时说明未验证部分。

## 资源身份与依赖

Unity 的 .meta 等引擎身份与导入资料，不按普通缓存删除。核对资源文件与其身份、材料、动画、骨架和场景引用是否对应；同时保留两个文件也可能造成重复身份，不能用任意改 GUID 解决后续引用。

这些原则按实际引擎使用，不要求非 Unity 项目增加 .meta 文件。

## 二进制和 LFS

PSD、模型工程、音频工程等不具有通用逐行合并语义。能用已有专业工具合并时按语义处理；不能时比较实际版本、预览、来源和目标，依据已确认选择保留，必要时将双方另存到获准位置待人工决定。

LFS 指针正确不等于实际对象已经取得或正确。没有下载或读取到实际文件时，不宣称已经检查其内容。不要为了看内容自动上传全部外部素材、突破配额或安装付费工具。

## 源文件与生成内容

当前任务涉及导出资源时，确认双方来源。只有明确可重建且获准时，才从正确源版本重新生成；重建后的引用、设置和其他有效变化仍需保留。不是看到生成文件就删掉一边。

## GDD 与 spec 冲突

Markdown 能拼接不代表相互矛盾的游戏规则能同时成立。以已采纳决定和任务边界判断，必要时把产品取舍交回当前讨论。不因“处理文本冲突”获得重新设计规则的授权。

## 操作与证据

Git 的 rebase 场景中，ours/theirs 对应关系可能不同于用户对本地/远端的直觉。直接核对提交，不靠名称猜。

检查至少区分：冲突是否解决；当前成果哪些方面已验证；merge/rebase 是否结束；是否仍需人体验或作选择。缺少运行环境时，Git 操作即使按授权结束，也明确标为尚未完成相关运行验证；项目若要求先验证才能继续，保留该前提。
