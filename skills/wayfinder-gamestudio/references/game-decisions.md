# 游戏决策：先消除会推翻后续工作的未知

以下是问题发现视角，不是所有游戏必须执行的阶段或问卷。已确定内容直接沿用。知识库辅助识别冲突和取舍，不为题材补齐所谓标准系统。

## 选择当下最值得解决的问题

优先考虑：这个假设若错误，会使哪些后续制作无效？哪一个答案能解锁当前最重要的选择？现有条件是否允许取得有效证据？

常见相关视角包括：目标体验与核心行为能否相互支持；是否有足以观察目标的反馈；长期结构是否依赖尚未成立的短循环；资源制作或平台条件是否会影响验证真实性。无需为这些视角打分，也不固定顺序。

“工作量大”与“设计不确定”不同。已明确的一百个关卡可以拆内容制作批次；一个只有三条规则但无法决定关键取舍的问题，可能更需要讨论和验证。只有多个关键未知相互依赖且需要跨会话续接时，地图才有明显价值。

## 贯穿例子（虚构，不是研究结论或用户已选玩法）

用户提出一个结合采集、经营和解谜的休闲游戏，尚不清楚主循环。目的先限定为“确定首个可玩版本的核心体验与主要关系”，不是列出整款游戏的一切任务。

最初可以分别识别：玩家主要享受自主探索还是连续操作？经营部分在当前体验中承担什么作用？两者是否需要在首版相互依赖？先澄清会改变其余问题的上层选择。

在上层关系未定前，商店商品数和升级曲线通常不是当前问题；不自动创造商城。若“需要多少初期升级项”已经是一个明确但依赖上层决定的问题，可以记录为被阻塞的问题，而不是提前填答案。

缺资料时，由 research-gamestudio 按需要选择深度并使用现有工具。需要亲自体验才能判断时，先明确最小验证问题；已有原型就复用，获准制作时才使用 prototype-gamestudio。

玩法原型默认是可玩的浏览器小游戏：有必要场景、SVG或合适的轻量美术、真实输入、规则变化与反馈，不是按按钮模拟完成动作的报表。只实现这次验证需要的内容；必要的三维、引擎或设备条件不能被不相关的二维演示替代。

若原型已能运行但用户尚未作指定体验选择，制作可报告完成，设计问题仍未解决。用户否定当前玩法后，可以根据证据修改方向；不隐藏反例，也不为宣布地图进度而自行替用户选中方案。

采纳后由 GDD 记录本项目现行关系，由 spec 记录当前具体交付或后续验证范围；地图保留简短答案与出处。随后重新判断哪些问题仍有必要，不继续执行已被新选择淘汰的旧列表。

## 原型和研究的证据边界

研究中的开发者意图、玩家效果和本项目适用性是不同结论。可玩原型、完成观察、方案采纳、正式交付同样不同。临时数值可作为获准实验输入，但不能成为未经选择的最终规则。

不把查看截图当作实际试玩，不把浏览器检查当作目标设备已通过，不以自动模拟代替被保留给用户的体验决定。需要访问、素材或工具时先明确具体缺口；纯计划权限不授权安装、上传或制作。

## 什么时候结束

本次目的明确到足以继续相关工作，关键取舍有答案，必要验证已有证据或其尚缺状态被准确保留。若目的包括选择一个真正合适的操作方式，就必须完成该选择需要的体验，不能仅写“待体验”后结案。

如果只需准备一个可执行的实验，完整游戏平衡无需先定；如果只需交付首版依据，未来扩展可以明确排除。主动延期必须确实不阻碍当前目的，不能通过延期逃避关键选择。
