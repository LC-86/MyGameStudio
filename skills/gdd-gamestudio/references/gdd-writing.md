# GDD 编写与维护

## 文档目标

GDD 说明这整款游戏是什么、希望产生什么体验、玩家做什么，以及相关系统和表现如何配合。完整程度以当前确认范围为界：有实际内容与关联说明，而不是标题齐全、所有章节写“待补充”。必要决定不足时交付部分设计或候选，不宣称已可全面制作。

“详细”并非 spec 独占。一个系统的完整规则可以留在 GDD 的相关章节。spec 的区别是本次交付范围、变化与验证，不是简单的详细/概括二分。

## 按当前目标取用的写作视角

| 视角 | 有用的表达 |
| --- | --- |
| 游戏定位与体验 | 当前范围、目标玩家或使用情境、希望产生的感受，以及明确不追求什么 |
| 核心游玩 | 起始状态、主要行动、结果、反馈和重复游玩的动机；没有胜负也不强加失败机制 |
| 操作与信息 | 输入、镜头、状态可读性、关键反馈和必要辅助 |
| 规则与系统 | 条件、状态、例外、资源与其他机制的相互作用 |
| 内容与进程 | 当前范围的关卡、角色、谜题、叙事或其他内容怎样组织和变化 |
| 数值与平衡 | 参数含义、单位、适用对象、关系与依据；暂定数值和正式规则清楚区分 |
| 视听与界面 | 与体验相关的美术、动画、音效和 UI 要求，引用现有资源规范与样例 |
| 约束与验证 | 已确认的平台、输入方式、性能等约束；设计假设、观察方法与未解决缺口 |

各项是观察角度，不是必填章节。联网、商业化、运营等只在本项目相关且已有要求时进入，不为了类型完整新增系统。知识的选用原则与访谈方法一致：领域知识用来发现矛盾、遗漏和待验证假设，不替用户决定，也不因为某个类型常见就把系统补成默认要求。

## 组织方式

小项目先用已有的一份设计文档；没有约定时可参考 docs/GAME_DESIGN.md。内容过长且形成独立主题后，再拆成总览与详细页面，不预建空目录。总览解释整体关系和范围，详细页面维护具体规则。

可用场景、规则表、已有草图、必要公式或原型片段准确表达，不强制长用户故事。引用实际存在的内容，不虚构图片、原型或用户测试；不为了生成 GDD 自动制作素材。

新建、整体整理和局部修订都是本技能范围。局部修订只更新受影响内容及真实关联；保留未受影响结构、用户措辞和已有资料入口，不借重写风格引入设计变化。

## 资源和专业性

指出本项目行为需要哪些表现及其作用，不只写“音效适当”。若某反馈尚未决定，就保留缺口或交回讨论，不自行补成定稿。

源资产、工程资源、测试样本、候选素材、缓存和大型交付物，沿用 setup 建立的管理约定。GDD 记录表现意图、来源版本或必要规范引用，不成为素材备份目录。未验证的图形、音频或手感要求仍需实际检查。

## 检查一致性

对照目标、现行规则、相关内容与最新已采纳决定。关注单位和术语差异、保留/清空矛盾、互相依赖的系统，以及候选混入正式规则。不强制扫描整个项目。

用户只要求整理已有设计时，准确呈现已有内容；明确允许构思候选方案时，标明用户约束、建议和假设。形式完整的候选不是最终采纳。没有试玩就不写“已经证明有趣”。

完成后明确本次文档覆盖什么、哪些还需决定或验证；对应的关联 spec 是否已修订，只报告实际做过的部分。
