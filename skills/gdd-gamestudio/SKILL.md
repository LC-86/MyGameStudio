# GDD GameStudio

生成并维护当前游戏设计，使读者理解目标体验、实际玩法及相关系统如何一起成立。可以整理全局，也可以只修订一个章节；不因使用本方法而重新设计整款游戏。

先读取 [文档分流与增量协作](../docs-gamestudio/references/document-routing.md)，它决定一段内容归 GDD、spec 还是术语表，以及何时落盘、何时停止。编写或实质修订正文时，按技能名称取得 `writing-for-agents` 的共同写作方法并读取 [GDD 写法](references/gdd-writing.md)与 [docs-gamestudio 的语义保真要求](../docs-gamestudio/references/semantic-fidelity.md)；同一上下文已经取得写作方法就直接沿用，不为每个章节重复取得。

## 1. 确定本次输入与范围

沿用当前讨论、用户明确引用的资料、项目约定和已有 GDD。明确本次是在整理已采纳内容、增量修订，还是用户要求先提出候选方案；已有信息足够就不再访谈。

区分用户要求、已采纳决定、实际实现、候选与试验假设。知识帮助识别缺口，不把常见系统补成默认要求。没有策划入口且本次已允许创建文档时，提出或采用与项目一致的最小位置，并说明位置；不会为此强制完整 setup。

讨论中的局部调用只处理本轮已经明确的设计及受影响章节，不等待全部问答完成。没有内容变化时不写。

## 2. 写清设计及其关系

按照项目的实际范围，说明目标体验、核心行为、相关规则与系统关系、内容组织、操作信息、视听表现和必要约束。保留决定中的条件、例外和排除项；详细程度服务当前阶段，不靠填满模板判断完整。

组织已知内容，按需引用现有数值、内容表、素材规范或技术说明，不复制其全部正文。已有参数的角色、单位和依据保持明确；试验值不是已证明的平衡结论。资源只引用版本与位置，不把大量候选、源文件或构建产物嵌入文档。

用户明确要求候选策划时，可以在范围内提出设计并标明建议与假设。默认整理模式不自行补定重要选择。关键矛盾或设计缺口带回正在进行的问答；无活动问答时只澄清影响本次整理的问题，必要时使用 [grilling-gamestudio](../grilling-gamestudio/SKILL.md)，不重问已确认内容。

## 3. 按需衔接规格

本轮也明确了具体交付范围、验收或制作约束时，可使用 [spec-gamestudio](../spec-gamestudio/SKILL.md) 处理本次工作规格。只需引用已有 spec 就直接读取，不启动维护它的技能；没有具体交付需求时不批量生成 spec。

传递本轮决定、依据、修改范围、已有目标文件和剩余缺口，不让对方从头复原会话。被 spec-gamestudio 请求更新设计时，只完成该差异并返回，不立即把相同内容再次交回规格技能。发现对方文档还有关联缺口，返回给当前 Agent 接续处理，不形成相互反调的循环。没有新差异、对方已经覆盖或缺口已经解决时停止调用。

## 4. 局部保存并回到讨论

在已授权位置做最小更新，保留无关内容及现有结构。修改前核对目标是否出现冲突编辑；明确采纳的变更优先于旧设计，但新时间戳、建议或代码现状不构成采纳。

回读本次实际变化，说明更新位置和未决项。资料只部分完成时准确说明范围；设计已写入不等于实现或试玩通过。作为讨论的一部分时，完成这一轮更新便回到原问题集；单独调用则到本次文档成果为止。不自动制作资源、拆实现工单、改工程、提交或推送。
