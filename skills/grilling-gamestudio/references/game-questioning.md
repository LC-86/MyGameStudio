# 游戏专业提问参考

这份资料帮助发现当前游戏问题中的歧义、取舍、相互影响与验证需求。它是观察视角，不是设计标准、流程门槛或必答题库。用户当前目标和项目实际情况决定哪些内容有用；相关材料已回答的问题不再询问，读完后不产生新问题也可以是正确结果。

本页的角度与例子来自 MyGameStudio 的设计讨论，用于说明如何生成问题；不将其表述为经过实证验证的行业定律。访谈的分轮、前置依赖、确认与调用边界由 SKILL.md 负责，本页不另建一套流程。

## 正确方向来自当前目标

从用户要获得的体验或解决的工作问题出发，不从“这种类型通常有什么系统”出发。资料可以帮助检验目标是否一致、代价是否被理解，但不能替用户决定作品应当是什么样。

例如，用户已明确“没有时间压力、希望玩家慢慢发现规律”，就应围绕自主探索、信息理解和卡住后的帮助方式考虑问题，而不是因解谜资料提及倒计时就询问限时多少。

游戏不必全部包含竞争、失败惩罚、复杂经济或高频决策。欣赏、创作、叙事、放松等目标也可以成立。混合类型按本轮讨论的行为和机制选视角，不要求先给整个游戏贴准一个类型标签。

已有决定优先复用，但不压制有证据的质疑。发现与目标或其他规则冲突时，说明具体情境和影响；用户了解后坚持的取舍仍是项目选择，不用同一套惯例反复要求其改口。

## 先判断未知的性质

以下区分用来避免把所有困难都变成用户问卷，不是要求每次输出分类表。

| 遇到的未知 | 合适的处理 |
| --- | --- |
| 可以查到的事实，例如是否已有存档模块 | 通过获准的资料和工具调查，不让用户代查 |
| 会改变体验的重要决定，例如失败后保留什么 | 展示具体选择与代价，交给用户决定 |
| 用户已授权的局部实现细节 | 在授权内选择并说明必要理由，不要求用户逐项批准 |
| 依赖体验或测量的效果，例如节奏是否合适 | 提出假设和观察方法，保留待验证身份，不逼用户报出确定答案 |

若两种合理理解会带来不同结果，而已有决定没有解决这种差异，就找到了一个值得讨论的分歧。若差异不会影响当前目标或下一步，或已明确留到以后，可以先不展开。

## 可选的专业观察视角

只选当前相关的视角，也允许使用表外的合适视角。每一行都不是必备系统或必须询问的题目。答案会改变后续的相关范围，而不是解锁一套固定题库。

| 视角 | 可以寻找的遗漏或取舍 | 情境化问题示例 |
| --- | --- | --- |
| 目标体验 | “爽快”“休闲”“紧张”等表达对应什么行为和感受 | “这里的休闲，主要是不需要快速操作，还是失败后不损失进度？” |
| 核心行为与选择 | 玩家在做什么，何时有理由改变做法 | “在什么情况下，玩家值得尝试另一种操作，而不是始终重复同一种？” |
| 规则与状态 | 条件、结果、同时发生的事件怎样解释 | “最后一次攻击同时击败双方时，本局结果按什么判定？” |
| 信息与反馈 | 玩家怎样理解状态、成功或失败的原因 | “操作没有生效时，玩家怎样区分输入未接收与条件未满足？” |
| 挑战、节奏与随机 | 难度来源是否符合目标，随机怎样影响可应对性 | “后期的变化主要要求更快反应，还是判断更多信息？” |
| 成长与经济 | 收益是否鼓励目标行为，是否存在反向激励 | “反复完成最简单任务收益最高时，是否仍符合你希望的游玩方式？” |
| 关卡与叙事 | 信息顺序、空间安排与理解机会是否匹配 | “玩家错过这条线索后，仍有什么机会理解下一步为什么成立？” |
| 美术、声音与界面 | 表现是否支持识别、操作和目标感受 | “不用阅读说明时，玩家能凭什么区分背景物件与可交互物件？” |
| 辅助与访问需求 | 已知使用条件下，帮助是否足以理解和操作 | “关闭声音后，关键反馈还有哪种方式能够被注意到？” |
| 制作、资源与验证 | 方案有哪些实际条件和可观察结果 | “这个效果需要放进实际镜头里看什么，才能判断可以继续制作？” |

把“希望的体验、玩家可能的行为、规则及表现、验证依据”来回对照即可，不要求按固定顺序讲完。单纯讨论资源备份或代码接口时，使用其实际恢复或调用情境，不绕回整款游戏的玩法设计。

## 把知识转成问题的几种方式

### 把形容词转成可观察的差异

“战斗要有打击感”不必直接转成“震动幅度要多少”。先定位用户在意的差异，例如：“现在更需要解决的是命中不易确认，还是敌人受到攻击后缺少明显反应？”

这两个答案会指向不同的后续问题。列出的选择只是帮助说明分歧，允许用户提出另一种理解；不把选项变成封闭答案范围。

### 用当前项目的具体情境代替抽象偏好

“失败惩罚不要重”可以问成：“玩家已完成这一段的大部分内容，最后一步失败后，你希望他重新做哪一部分？”优先使用已有场景，而不是随意引入项目没有的检查点、生命或货币。

### 显示真实取舍，而不是收集“都想要”

先说明两个方案在当前目标下的差别，再请用户选择。例如：“保留本局进度能减少重复操作，但会改变这次失败的后果；本轮更希望保留哪一种体验？”只有确实存在的影响才拿来比较，不夸大冲突。

推荐从用户目标和已有事实推导。关键依据不足时，说明推荐的条件、缺少的事实或需要验证的假设，不把主观偏好包装成行业共识。

### 用反例检查玩家行为与设计目标

针对当前方案选择有解释力的反例：玩家是否会用更省力、更安全或回报更高的方式，使预期行为失去意义？例如闪避也能取消攻击后摇时，先说明它可能改变攻击策略，再确认这种变化是否被接受。

反例不是自动判错。用户可以有意保留这种用法；不把所有偏离预期的玩法都认定为必须修复的问题，也不穷举与当前目标无关的极端情况。

### 追问变化的后果，而不是重新访谈

“提高移动速度”已经是一个明确要求。只有它影响相关关卡、躲避机会或表现时，才追问：“这会改变原来需要绕开的危险区域，你希望保留原来的应对要求，还是接受通过方式的变化？”未受影响的规则不重问。

### 把无法通过讨论决定的效果转成验证问题

免伤时长、掉落速度或提示强度，可以先提出有理由的初始方案，但保持试验值身份。说清之后需要观察什么，例如玩家是否理解失败原因、是否只重复一种操作、提示后能否自己解释下一步。

本方法只明确验证问题，不自行开展原型、试玩、招募玩家、生成素材或运行测试。需要这些工作时交回原任务，由相应技能在已有授权内处理。

## 一个按回答变化的示例：无时间压力的解谜提示

以下是示意，不是针对真实项目的已采纳设计，也不是让每个解谜项目照问。

已知目标：没有时间压力，希望保留玩家自主发现规律的体验；本轮只讨论提示系统。

值得问的问题：“玩家长时间没有进展时，游戏应该主动给出一点线索，还是等待玩家自己请求帮助？”这来自自主探索与卡住后支持之间的取舍，不来自题库中的必填栏目。

如果项目已经确认“只在请求时提示”，直接沿用这一决定。此时可能还有价值的问题是：“第一次提示以后，玩家仍需要自己推理出什么？”如果这也已经明确，就不再询问，继续寻找当前真正的缺口，或结束讨论。

回答为“指出值得观察的信息，保留下一步推理”时，后续检查可以是：仍然卡住后，增加同一条线索的信息，还是换一种表达？只有已经确定需要升级提示时，才继续展开升级方式。

不要因为资料存在相关案例，就增加倒计时、广告换提示、出售提示道具等讨论。效果是否真的保留推理乐趣需要实际观察，本轮只能确认方案和待验证问题。

## 领域知识与项目决定分开

技能库参考保存适用条件、关系、取舍、提问示例和验证方法。具体游戏的规则、选择、数值与观察结果，属于该项目自己的设计资料。

单次对话里的偏好不自动升级成知识库规则。值得复用的发现，可以在另行授权的维护任务中整理成带适用范围和来源的条目；当前访谈不自动修改知识库或建立学习状态系统。

当需要专业资料但现有参考未覆盖时，可以使用可说明依据的推理或在授权范围内调查相关来源，并标明局限。不要把某份参考未安装当成访谈无法继续的理由，也不要捏造“行业标准”补空白。
