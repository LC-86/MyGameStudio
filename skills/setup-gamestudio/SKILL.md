# Setup GameStudio

让后续 Agent 知道：任务在哪里、资料在哪里、资源怎样流转和保存、该沿用哪些项目约定。

这是一份供 Agent 阅读的普通项目配置，由本技能库的方法驱动，不是插件安装、游戏初始化或工作流运行时，也不需要专用程序解析。通过现有工具探查、提出建议、确认、写入和回读。

写入的每份约定都是正式工作资料：指针带用途、引用与访问状态真实、用户尚未确认的内容保持未确认身份。按 [docs-gamestudio](../docs-gamestudio/SKILL.md) 的写作方法表达；同一上下文已经取得方法就直接沿用。

## 1. 先看已有约定

根据用户给定的目录和当前工作区确定项目范围。存在多个合理目标时，只澄清目标；不要扫描其他个人项目。

只读查看足以确定配置的资料：适用的 AGENTS.md / CLAUDE.md、README、现有任务约定、领域文档，以及必要的工程元数据。识别已有游戏设计、技术说明、资源规范和运行检查说明的位置。涉及资源管理时，查看已有 .gitignore / .gitattributes、资源与制作区入口、源资产版本和备份约定；工程外目录仅在明确允许的范围内查看。Git 远端只提供仓库线索，不自动决定任务来源。

优先沿用仍有效的约定。已有 Matt 配置、MyGameStudio 配置或其他布局，都可以直接使用；不要因为名称不同就另建副本。发现相互矛盾的现行来源时，展示冲突并确认，不按文件名或更新时间猜选权威来源。

项目入口规则仍指向旧版 MyGameStudio 的运行层、记录程序或已退役入口（`game-producer`、`game-init`、`game-design`）时，指出这些引用已经失效并建议删除或改写，说明当前由哪些技能承担对应工作。只改约定文档；不迁移旧记录数据，不改动这个游戏项目的任务、资产、存档或外部存储，也不批量切换其他项目。

探查针对配置与入口，不开展完整代码审查、玩法访谈、全量资产盘点或环境安装。只读请求只返回建议，不写入。

完成条件：能区分已有约定、真正缺失的选择和尚未确认的事实。

## 2. 只补会影响工作的配置

### 任务与功能规格

确认任务实际存放在哪里，以及后续技能如何读取、创建和更新它们。已有来源优先；没有约定时，根据已识别的仓库推荐对应平台，否则建议本地 Markdown。用户已经明确的选择不再询问。

记录明确的项目范围或仓库、任务位置、功能规格位置、必要的身份和关系约定，以及当前可用的操作工具。任务与完整游戏设计可以放在不同位置，用引用连接；同一份现行内容只在一个位置维护。

使用项目已有 CLI、连接器或文件操作。按当前工具的实际能力选择操作方式，不复制一整份 API 手册。其他平台也可以用自然语言说明流程，但配置意向不等于已具备访问能力。缺少访问时如实说明，不静默换成本地任务源，也不为验证写权限创建测试工单。

新建约定可参考 [任务配置模板](templates/issue-tracker.md)，默认写入 docs/agents/issue-tracker.md。路径仅是默认值；已有等价文档直接复用。

### 分流约定（按需）

只有项目采用分流、已安装的相关技能需要角色映射，或用户明确要求时才补齐；已有约定可用则不改。

默认沿用 needs-triage、needs-info、ready-for-agent、ready-for-human、wontfix 五个含义。实际标签或字段沿用项目习惯。分流只表达信息是否齐备和适合由谁处理，不代替任务进度、依赖判断或验收结果。

参考 [分流模板](templates/triage-labels.md)，默认写入 docs/agents/triage-labels.md。配置映射不等于创建远端标签；远端修改另按具体授权执行。

### 术语与决策资料

确认术语表和重要决策记录的位置，以及相关工作开始时如何按需读取。复用现有布局；没有约定时，默认一个项目术语表与一个决策目录，不为普通项目提前设计多上下文结构。

术语表只解释概念，不充当游戏设计或任务清单。配置可以约定将来使用 CONTEXT.md 和 docs/adr/，但这些文件尚不存在并不阻碍 setup，也不创建空术语表或空决策记录。

参考 [领域资料模板](templates/domain.md)，默认写入 docs/agents/domain.md。

### 游戏资料与资源管理

只补其他配置未覆盖、后续工作确实需要的入口：已确认的引擎与版本来源、目标平台的已有约定、游戏设计、技术说明、资源规范、运行与检查说明的位置。

记录出处和必要的简短说明，不复制上述文档正文。可从工程元数据直接读取且容易变化的值，优先指向来源。未确定的引擎、平台或玩法保持未确定，不替用户做选型，不生成完整游戏设计，不把未知项全部变成接入障碍。

已有 README 或文档索引足够时，直接引用。确需补充时，参考 [游戏资料入口模板](templates/game.md)，默认写入 docs/agents/game.md。它只导航，不保存另一份资源管理规则。

游戏会生成或使用素材时，按需读取 [资源管理与制作流程模板](templates/assets.md)，补齐以下实际约定；已有规范足够就复用，不另造资产系统：

- **位置和用途**：区分试验候选、可编辑源文件、工程当前依赖的资源、必要测试资源、可重建缓存和大型交付物。缺少约定时，建议“游戏工程 + 工程外制作区 + 独立备份”；制作区的 working / candidates / versions 仅为示例，沿用项目布局。
- **版本与存储**：明确哪些使用普通 Git、哪些按需使用现有 Git LFS、哪些使用外部版本存储或备份。源文件少且适合跟工程回退时，可以直接采用项目内 LFS；不强制源资产全部外置，也不把所有图片或测试资源一律忽略。工程必需的资源身份、导入设置及源文件外部依赖要一起保留。
- **制作到工程的流程**：候选先在制作区筛选，源文件在其实际编辑位置修改，按引擎要求导出和接入当前需要的资源，再验证、保留重要源版本，并在已有任务或简短资源说明中记录对应关系。以后返修沿同一路线；需要改变资源身份或路径时按引擎约定处理。阶段性资源不必完美才入库，缺少就无法开发或测试的输入仍须可恢复。
- **提交与清理**：提交前检查本次文件、依赖和异常体积，只纳入当前任务成果；候选和临时文件不自动进入历史。定义清理的责任、保留依据及确认方式，不按 test / temp 名称或单次文本搜索直接删除。被忽略不等于被备份或受保护；修改忽略或 LFS 规则也不等于清理旧历史、减少游戏构建包体。
- **恢复与访问**：明确工作文件和重要源版本的备份位置、时机、责任以及恢复验证方式。工程版本与源版本分别可恢复，外部必要资源引用确定版本而非 latest。只写本机绝对路径、只留提示词或只设置同步，不作为恢复已验证的依据；远程 Agent 不默认能访问本机制作区。备份未落实时标明缺口，不以配置完成为由删除源文件。

规则优先写入已有资源规范；缺少合适位置才建议 docs/agents/assets.md，并加入带用途的入口指针。不要求资产数据库、自动同步、固定编号或每次保存归档。只记录会影响当前项目的约定，不盘点每一件素材。具体制作、备份执行和清理由后续任务按授权完成，setup 不代做。

完成条件：每项必要配置都有明确来源或待确认选择；后续资源任务能按约定从制作走到工程，并找到对应源版本与恢复方式。不要求所有项目复制整套模板。

## 3. 提出最小修改并取得确认

一次说明建议沿用什么、补充什么、修改哪些具体文件。只询问无法从现有资料确定且影响本次配置的选择，给出推荐答案；已知信息不重复问，独立选择可以一起确认。

展示拟写内容或清晰差异。仅在相应授权范围内写入。用户已明确批准同一范围及处理方式时，不重复索取相同确认；新增范围、冲突或外部操作需重新说明并确认。

项目入口优先使用当前宿主实际读取、且项目已有的 AGENTS.md 或 CLAUDE.md。两者指向同一文件时只维护一次；两者独立存在时保留各自规则，必要时让它们指向同一份配置，而不是复制正文。没有入口文件时，建议当前宿主适用的一个文件，并纳入修改清单。

入口只写带用途的短指针，例如“拆分或维护任务前，读取任务约定”；涉及素材生成、导入、替换、提交或清理时，指向已确认的资源管理约定。不粘贴全部配置，不注册自动执行链。已有 Agent skills 或等价配置段落就原位补齐，保留无关内容和其他技能库的约定。

完成条件：目标、拟写内容和授权范围足够明确，可执行部分与未决定部分分开。

## 4. 写入并回读

默认仅实施已确认的最小文档变更。必要目录只在获准位置创建；工程外制作区未获授权时只记录建议位置，不扫描、创建或写入。用户明确将 .gitignore / .gitattributes 纳入本次范围时，先核对引擎必需文件、既有规则、跟踪状态及现有 LFS 可用性，再进行针对性的配置修改与只读核对；条件未满足则只提供建议，不写入未就绪规则。

不以试运行配置为由导入素材、构建游戏、提交大文件或进行远端写入。安装工具、素材生成与导出、备份执行、删除或搬迁文件、取消跟踪、历史重写、LFS 历史迁移、强制推送及更换现行数据来源，均另作明确任务，不由本次 setup 顺手完成。

选择新任务来源涉及既有资料时，先提出迁移需要，本次不直接切换有效指针；仅改变文档约定不等于已经完成迁移。

重复执行时只补缺项。配置未变化就保持文件不变，不刷新日期、不追加重复段落。写入前后保留用户已有修改；出现重叠编辑时停止覆盖并重新核对。

完成后回读实际文件，核对路径、引用、来源及本次差异。将实际存在、尚未创建和未能访问的目标区分说明。资料路径已知不等于运行检查已通过，工具已安装不等于远端写权限已验证。

完成条件：已写内容与确认一致，后续 Agent 能从项目入口找到相应约定，或缺失访问已被明确披露。资源规则须能回答“生成放哪里、采用后怎样进工程、源版本在哪里、如何恢复、何时允许清理”；本次没有实际验证的访问或恢复能力保持未验证。

## 5. 交付并停止

简要报告复用了哪些约定、实际修改了哪些文件，以及仍影响后续工作的缺项。没有修改时直接说明“现有约定可复用，本次未修改文件”。

配置完成只表示协作约定和资料入口就绪，不表示游戏可运行、设计完成或所有工具已经可用。区分资源规则已约定、忽略或跟踪配置已修改、LFS 上传已验证、备份已完成、恢复已验证和旧历史已清理；只报告实际做到的部分，不用一项替代另一项。说明用户可以直接修改这些普通文档，不必每个任务或每件素材都重新 setup。

本技能不自动调用 ask-gamestudio 或其他用户入口。后续使用哪项技能，由用户选择。

## 权限与范围

本技能只使用本次明确允许的项目范围与已有访问。任务平台选择、文档里的授权描述和 Skill 名称都不是新增权限；保留宿主权限要求。常规写入仅限已确认的项目协作文档与另经确认的项目级忽略／跟踪配置，不自动提交、推送、修改远端、修改用户全局配置或安装其他技能库。令牌、密码及其他秘密不写入配置或报告。
