# 资源管理与制作流程

> 编写说明：本文件是 setup 的按需编写参考，也是后续资源任务的项目约定模板，不是独立技能、强制流水线或机器格式。优先补充已有资源规范；只有缺少合适位置时才建议生成 docs/agents/assets.md。将示例替换为已确认位置，删除无关分支和本说明。未确认或不可访问的内容如实标注；不要复制所有表格制造填表负担。游戏资料索引和项目入口只引用本约定，不重复规则。

## 资源存放与版本方式

根据实际用途分类，不仅按后缀或文件名分类。已有资源库、LFS 或其他版本工具能够满足要求时继续使用，不为了目录样式搬迁资料。

| 资源 | 实际位置与管理方式 | 保留原则 |
| --- | --- | --- |
| 工程代码、场景、工程配置与必要元数据 | <当前工程仓库；普通 Git 或适合的版本方式> | 能恢复对应工程状态；场景等若是大型二进制，按实际性质处理 |
| 当前开发、运行和验证依赖的资源 | <引擎实际资源目录；按需使用现有 Git LFS> | 含采用中的阶段资源、占位资源；不要求达到最终美术品质才保存 |
| 回归测试所需素材 | <项目已有测试目录或可获取的固定版本> | 测试依赖不是可随意丢弃的候选，不按 test 名称排除 |
| 可编辑源资产及其依赖 | <项目内 LFS、外部源资产库或制作区及版本备份> | 源工程、外部纹理、所需链接文件一起保存；既能定位版本，也能重新编辑 |
| 试验与候选素材 | <本次项目允许的制作区／素材库> | 默认不全部提交工程仓库；当前候选和有价值方案按需要保留 |
| 可重建缓存和中间产物 | <引擎或工具的现有位置> | 核实能由保留输入重建后，按引擎规则忽略；不把身份和导入设置当缓存 |
| 构建包、录屏、渲染序列等 | <现有交付或证据存储> | 必要的小型测试证据可以进仓库，大型交付物记录可达位置与对应版本 |

没有既定管理方式时，可以建议以下逻辑结构；目录名、编号和是否单独设交付区都不是强制要求：

```text
工作空间/
├── Game/                    # Git 根在这里，沿用实际引擎目录结构
│   ├── 代码、工程设置、必要元数据
│   ├── 当前工程资源与必要测试输入
│   └── 已有任务或资源来源说明
├── Game-Art/                # Game 仓库之外；仅在授权范围内访问
│   └── chest/
│       ├── candidates/      # 试验候选
│       ├── working/         # 正在编辑的源文件及依赖
│       └── versions/        # 重要节点源版本，如 r001、r002
└── Deliveries/              # 按需要使用的大型交付区
```

这套外置建议适用于较多的候选和大体积源资产。源文件少、适合与工程一起回退时，直接放项目内 LFS 往往更简单，不要求另建源仓库。也可以沿用有明确保护和备份的本地工作区，但被 Git 忽略的文件不因此获得保护。

## 一次资源任务如何执行

这是后续制作／实现任务要遵循的路线，setup 只确定约定，不在配置期间代做制作、提交、备份或清理。已有明确设计、可复用资源或可恢复版本时直接沿用，不强迫每次从生成候选开始。

### 1. 准备候选

把生成、下载或试验文件保存到本任务的候选位置；不把整批结果直接写进引擎资源目录。按已有任务标准由 Agent 筛选；核心风格或设计取舍按授权交由用户判断，不为每个文件新增人工关卡。

### 2. 编辑源文件

在确定的源文件工作位置修改。正常保存并按项目备份约定保护工作进度；重要编辑检查点由实际风险决定。源文件与其外部依赖一起保持可恢复，不仅保存预览图、提示词或生成参数。只有预览、提示词并不代表已经保存了实际源资产。

### 3. 导出和接入工程

按实际引擎要求导出本次需要的模型、贴图、动画、音频等，并带齐依赖。只接入当前工作需要的一套资源；不把整个制作区复制进工程。使用引擎适用的导入／替换方式，保留资源身份和必要导入设置；同一逻辑资源优先使用稳定路径，新变体或引擎要求则采用有理由的不同身份。

### 4. 验证并保留节点

在实际工程验证当前任务要求，如显示、尺寸、材质、声音、动画或交互。记录检查范围、结果和未验证项，文件存在或能导出不等于游戏内验证通过。

采用某个源版本、完成重要修改或形成阶段交付时，保留对应源资产节点；不要求每次保存都新建版本目录。采用现有版本工具的不可变标识，或不覆盖的命名节点都可以。验证未通过的工作仍按需要保存为在制版本，不把“未通过”当成不保存或可以丢失的理由，也不报告为验收完成。

### 5. 记录源资产对应关系

在已有任务或简短资源说明里记录：资源身份、工程中的实际位置、对应源版本及必要依赖、源资产与备份的可取得位置、来源及适用的使用条件、实际验证状态。已有记录足够时只引用，不再创建平行清单或给每个文件填完整表单。

对应关系必须能随工程版本回退。写进工程版本的简短说明，或者引用有固定版本的任务／资产记录均可；仅有不断被覆盖的“当前最新版”说明不够。外部存储不能只写 latest 或某台电脑上的绝对路径，要能找到确定版本。

示例（示意记录，非实际完成情况）：

```text
宝箱：工程资源 <实际位置>
来源版本：chest/r001（含模型源文件和依赖纹理）
源版本和备份：<能取得这个版本的确定位置>
来源／使用条件：<已知来源及适用说明>
验证：<执行过的检查>；未验证：<尚未完成的部分>
```

### 6. 整理提交和推送范围

按既有授权检查本次新增、修改和拟提交内容、文件体积及必要依赖。候选、重复导出、大型录屏或未知大文件混入时先说明并处理范围，不能为了凑提交自动删除它们。工程资源、接入修改、必要元数据和对应源版本说明作为同一交付保留。

筛选发生在提交前，而不只是推送前。普通 Git 与 LFS 分别采用项目已确认的跟踪规则；LFS 是版本存储，不是压缩或无限容量承诺。跟踪配置存在、实际文件按 LFS 管理、文件已上传是不同事实；未经确认不宣称已完成后两项。

### 7. 返修与回退

形状、源纹理或源动画的问题回源文件修改，再导出、接入和检查；工程摆放、引擎材质或导入参数按实际归属在工程里修改。新的阶段成果保存对应源版本，更新已有来源说明，不靠堆叠“最终版2”“最终版3”记录全部历史。

工程回退时恢复相关资源与接入修改，并核对当时对应的源版本；要继续编辑旧方案时，从该源版本恢复工作副本。已经归档或被发布版本引用的源节点不随手覆盖。

## 备份、恢复和访问

采用 <实际备份方式与位置>，由 <当前任务 Agent／用户／既有备份系统> 在 <已约定的时机> 执行；尚未落实的项目写明缺口，不虚构计划任务已经运行。工作文件按实际风险备份，重要源节点保留可恢复副本。版本控制存储与独立备份的责任分别说明，不把同一硬盘中的另一个目录视为已落实独立备份。

定义两条恢复检查：获取对应工程版本及所需大文件后，能够按说明开发／运行；取得该版本的源资产及依赖后，能够继续编辑。实际恢复检查另在获得访问与执行授权的任务中完成；setup 只核对说明和已有证据，不自动下载全部资产或启动引擎。

外部资源的访问方式面向实际执行环境说明。远程 Agent 不默认能访问本机制作区；未获得访问时报告受阻范围，不猜路径、不安装同步工具、不扩大个人目录访问。必要工程资源外置时，明确固定版本和获取步骤，否则不能宣称工程可复现。

仅配置同步、备份路径或上传计划，不代表备份和恢复已经完成。没有恢复保障时，保留唯一源文件，不以“已进工程”或“setup 完成”为由删除它。

## 清理约定

由 <责任方> 在 <任务结束或其他已确认时机> 提出清理范围，保留当前工程依赖、必要测试输入、仍有价值的候选、重要源节点及必须保留的证据。没有既定保留期就建议一个合适方式并确认，不擅自设定自动删除周期。

删除前核对明确路径、当前和需保留版本的依赖、备份与恢复情况以及授权。单凭文件名包含 test / temp、文件较旧或一次文本搜索未命中，不能证明资源已无用。动态引用和引擎资源身份要按项目实际方式检查。

清理结果分为已确认可删、继续保留、依赖或备份待核对。没有足够依据时只列出疑问，不执行删除。被 Git 忽略不是备份，不让无差别清理覆盖有价值的制作文件。

修改 .gitignore 不等于移除已跟踪文件或历史；增加 LFS 模式不等于迁移旧对象；二者都不代替最终游戏构建的资源排除和压缩规则。已有大文件历史、远端存储回收或构建包体优化各自安排明确任务，不由日常整理顺手完成。

## 资源任务的交付说明

用实际结果简要说明采用的资源和源版本、工程位置、本次检查、拟提交或已提交范围、备份状态及未完成事项。文案按实际情况写，不强制固定报告结构。

示例：宝箱源版本为 <r002>，工程资源已更新；实际检查为 <范围与结果>。本次待提交 <内容>，未包含候选。源版本备份 <完成／未完成／未验证>，清理 <未执行／已确认的实际结果>。
