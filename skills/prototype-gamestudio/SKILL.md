# Prototype GameStudio

用最小而足够真实的游戏体验回答当前设计问题。玩法原型默认是可玩的浏览器小游戏，不是关于游戏的表单、控制台或交互说明书；它可以很小，但玩家的操作必须实际影响游戏结果。原型服务决策，不等于正式交付，保留有用发现和必要依据。

## 1. 对准要回答的问题

利用当前对话、相关 GDD/spec 和已有成果，明确待决定的事、哪些内容已确定、怎样观察差异以及结论由谁判断。只澄清会改变原型方向的缺口，不重开完整访谈，不为使用本技能而创建规格或任务。

用户要求原型或已有任务明确包含实验制作时，在相应权限内执行。只要求讨论、阅读资料或自动维护 GDD/spec，不构成制作原型的授权；需要时说明一个具体的验证建议。方案已明确、目标是正式集成时，返回该区分，不把交付降成演示。

已有成果能回答问题，就复用并观察，不另建同义原型。一个主要问题可含必要的关联检查，不顺带实现整款游戏。完成条件：能说清原型要支持哪个决定、什么结果有用、当前允许制作什么。

## 2. 默认交付浏览器小游戏

验证玩法时，优先制作一个可直接操作的浏览器小游戏。让玩家在游戏情境中行动，由实际输入和规则产生结果，再通过必要反馈影响下一次行动；不能用“点击接住即加分”之类状态按钮替代需要时机、位置或其他真实选择的玩法。

二维美术优先使用 SVG 或合适的轻量程序化图形，按当前情境制作可识别对象、状态与动作，保持视觉一致。允许简洁，但不能仅放无语义方块并让用户靠长说明想象体验。卡牌、文字、经营等以界面为核心的玩法，可以通过真实规则与选择构成游戏，不强制角色移动、实时碰撞或空间场景。

按[形态与保真度](references/prototype-shapes.md)保留会影响答案的条件。浏览器优先不是所有问题的绝对要求：已有成果能回答时直接使用；仅研究数据关系可用针对性模拟；关键三维、引擎或设备问题保留相应实际环境，并说明浏览器原型能证明和不能证明什么。不为原型擅自改选正式工程技术栈。

原型中的计时、失败、奖励、连击和其他系统来自已确认设计或明确标记的试验设定，不为“像小游戏”擅自增加。只在比较确有价值时提供多个方案，不凑固定数量；保留共同条件并明确真正变化的部分。

完成条件：能说明用户实际玩什么、当前需要哪些交互和表现，以及选定载体的结论边界。

## 3. 制作并确认原型可用

制作本次验证所需的输入、规则、可识别对象和有意义的反馈。游戏画面与玩家行为是主体，说明简短，调试参数和状态面板默认收起；不能交付通用网站仪表盘、着陆页或静态截图来代替小游戏。特效只服务识别和操作反馈，不靠无关粒子、震屏或动画掩盖规则缺失。

优先交付可靠的自包含 HTML；确需库、模块或外部资源时，提供完整小包和当前环境中经过检查的运行入口，不把单文件或某种框架设为硬要求。不能假称多文件内容可以直接双击运行；在线部署、外部托管另按授权处理。只有源码、截图或录屏，不等于用户已经得到可玩入口。

按当前需要提供键盘、点击、拖动或触控，以及方便重复体验的重开或重置。不为原型增加无关输入方式。可选声音在允许的用户交互后启用并可静音，不能让音频不可用阻塞核心玩法。开发控件不遮挡关键区域或抢占实际输入。

不为临时外壳追求生产级架构、全量测试覆盖和无关打磨；仍要做足以确认原型能运行、对照条件有效、关键计算没有误导结论的检查。关键指标可采用已有测试或独立算例核对，不能用“不写测试”免除实验有效性。需要制作代码、图像或音频时按现有专业工具完成实际成果，不以说明或占位承诺替代。

状态默认使用内存或可重置的测试数据。必须验证持久化、网络或设备时，使用获准的隔离条件，保护真实存档、账户和外部服务。候选、源资产、必要测试资源和工程导出依 setup 约定保存；不把全部候选和大录屏加入工程历史。

完成条件：本次承诺的小游戏或获准的必要例外成果实际存在；已检查真实启动、主要输入、规则结果、反馈和必要重置。SVG 语法正确或程序构建成功不能替代运行检查。实际设备与输入覆盖如实报告；无法运行则说明缺口，不宣称可玩。

## 4. 观察、交接和适度迭代

按[证据与交接](references/evidence-and-handoff.md)回答原问题。Agent 能取得证据且获准判断的部分自主完成；需要人的真实体验或选择时，准备可识别版本、入口、操作和具体问题，沿用[任务责任](../tasks-gamestudio/references/task-responsibility.md)，不替人回答。

将观察、推断、建议和用户采纳分开。一次体验、受控模拟或缩小负载只支持相应范围；没有观察就不能声称假设成立。结果否定假设或仍不确定都可以如实报告，不能靠修改目标把原型变成成功。

按反馈修正妨碍判断的问题；比较结论需要复用适用条件。修改范围明显扩大或出现新的重要决定时返回当前讨论。只剩未授权或必须由人的行动时，保留该缺口，不循环打磨。用户只要求制作可体验原型时可以交付原型；其构建完成不等于设计问题已得到答案。

## 5. 保存发现，返回原任务

在获准位置记录问题、实际版本或源材料、适用条件、已观察结果、局限及决定；没有文档权限时在对话中交付并说明未保存。这份记录会被后续设计讨论读取，按技能名称取得 `writing-for-agents` 的写作方法，并按 [docs-gamestudio 的语义保真要求](../docs-gamestudio/references/semantic-fidelity.md)表达：可运行、体验已发生、方案被采纳和正式实现已完成是四种不同状态，分别记录；无法取得时说明具体缺口和受影响的工作，只继续不依赖它的部分，不模仿缺失的方法。重要原型版本及其所需资源按项目约定留存，文件不一定要进入 Git；使用分支归档、提交、推送、上传或删除仍需相应授权。

当前任务已包括文档维护且内容已经采纳时，按 [文档分流与增量协作](../docs-gamestudio/references/document-routing.md) 使用 [gdd-gamestudio](../gdd-gamestudio/SKILL.md) 或 [spec-gamestudio](../spec-gamestudio/SKILL.md) 更新相关部分；探索观察可保留为证据，候选和试验值不冒充正式规则。完成后返回，不让原型、讨论和文档方法相互循环。

正式复用另按实现范围和验证标准评估：可以复用合适的代码和资源，也可以重做，但不自动把原型升格、覆盖正式成果或调用用户专用实现入口。被其他技能使用时返回发现和剩余事项；单独使用时到本次原型交付或验证结论为止，不自动拆票、领取新任务、改标签或关单。
