# Spec GameStudio

把本次工作写到后续执行者无需暗中猜测关键决定即可推进。继承 to-spec 的整理职责，不重新展开需求访谈，不默认扩写整份游戏策划。

先读取 [文档分流与增量协作](../docs-gamestudio/references/document-routing.md)，它决定一段内容归 spec、GDD 还是术语表，以及何时落盘、何时停止。编写或实质修订正文时，按技能名称取得 `writing-for-agents` 的共同写作方法并读取 [规格写法](references/spec-writing.md)与 [docs-gamestudio 的语义保真要求](../docs-gamestudio/references/semantic-fidelity.md)；同一上下文已经取得写作方法就直接沿用。

## 1. 使用已知依据

从当前问答、已有规格、相关 GDD、项目术语和必要工程现状中获取本次要求。沿用项目或 setup 约定的规格位置与工具；只读取相关内容，已有事实不重复调查。

本次目标明确后可以先写规格草稿，之后同一任务的答案继续补入该草稿，不每答一题生成一份文件。已有相关规格优先修订；不同交付确有独立边界时再分开。没有具体工作需求时，不为了保存零散想法造 spec。

从对话整理而来的决定、实现事实与建议分别表达。缺少关键决定时保留未决，不为完整而补写。局部缺口交回当前问答，不重开整轮访谈；无活动问答时仅问妨碍准确整理的事项。

## 2. 明确怎样检查

整理已有的验证要求，优先选择能够观察目标行为的现有接口或检查方式，不机械要求只能有一个入口，也不为测试发明多余结构。确需新的验证取舍时简短确认，已有安排不重复问。

按任务需要区分逻辑检查、工程内表现检查和人工体验判断。明确所需输入、观察结果及必要的检查环境；没有运行的检查只写成计划，试验数值保留试验身份。

## 3. 忠实编写本次规格

写清目标、方案、具体行为与交付要求、已有实现决定、验证方式、本次不做和必要依据。按工作类型使用短文、表格、公式或场景，不强制长用户故事和全部章节。

保留已确认的数值、单位、条件、顺序、例外和否定要求，不把精确规则压缩成模糊摘要。模块或接口决定按已有讨论记录，不自行发明文件级实现方案；必要的实际资料路径可以引用。

资源、内容和工程任务同样适用：写清本次源资产、工程资源、版本对应及游戏内检查需要，沿用项目资源管理约定，不复制素材库规范，也不生成大文件。为测试授权的占位内容不是最终表现方向。

GDD 中的必要规则以简短上下文加准确引用进入规格；不能只写“详见 GDD”而让执行者自己猜测本次适用内容。

## 4. 按需更新设计并保存

本轮已确认要求包含新的游戏设计决定、且当前文档维护范围允许时，使用 [gdd-gamestudio](../gdd-gamestudio/SKILL.md) 只更新相关设计。没有设计变化的错误修复、测试或阶段实现要求，不强行改 GDD；没有 GDD 也不妨碍已有依据充分的规格。

被 gdd-gamestudio 请求处理规格差异时，完成后返回，不将相同内容立即反向交回。对方缺口与处理结果返回给当前 Agent 协调；没有新差异、对方已经覆盖或缺口已经解决时停止调用和写入，按协作约定终止重复操作。

保存前对照依据检查遗漏、弱化、矛盾和越界新增。使用已有授权与项目约定位置保存或发布，并回读实际结果；写入结果未知先核对，不直接重复创建。GDD 与 spec 的更新不是原子事务：一份成功另一份失败时分别报告各自状态与剩余差异，先回读再补缺，不宣称两者已一致。

说明本次完成、草稿和阻塞的范围。“已保存”不等于“可直接实施”，“可实施”不等于“已授权实施”。不默认添加会触发自动执行的标签，不批量发布实现工单，不修改工程或自行进入下一阶段。作为讨论的一部分时，完成当前更新即返回原问答。
