# 工作规格写法

## 目标与输入

spec 是本次功能、系统、资源、测试或工程变更的可执行依据，不是整款游戏的总策划，也不是任务列表。其读者可能没有参与讨论，应能理解本次要做什么、不能偏离什么、怎样验证。

原始材料包括已确认对话、相关 GDD、现有实现与必要决定。阅读相关章节与具体引用，不全量抄录项目。授权内的实现建议可以明确写成建议或委派决定，不冒充用户原话。

## 可裁剪的结构

```markdown
# <本次工作的规格>

<适用目标、范围、依据版本；草稿或部分未决时在这里说清楚。>

## 目标与方案
<要解决的问题、已经确定的方向。>

## 行为与交付要求
<实际条件、操作、结果、反馈、例外；资源或工程任务使用对应成果要求。>

## 已确认实现约束
<已有模块关系、接口兼容、平台与资源约定等；不是假造的文件清单。>

## 验证方式
<检查入口、观察结果、必要环境与责任。哪些待试玩、哪些可自动核验。>

## 本次不做
<已经明确排除的工作。>

## 未决项与依据
<重要问题、暂定试验值、相关资料位置及其可核对版本。>
```

章节可合并，不适用就省略。忠实覆盖当前范围，不靠长篇和大量用户故事证明完整。基本输入已知而细节待答时可以先建同一份草稿，但阻塞执行的决定不能靠“待补充”隐藏。

## 游戏任务的具体表达

写清规则产生的实际行为，而不是只有功能名。比如“死亡结束本局，重开保留永久解锁、清空局内临时能力”，不能弱化为“失败后继续并保留部分进度”。

数值保留单位、适用条件和身份；例如“先用 2 秒验证”不变成“2 秒已验证最优”。保留必要的先后关系、例外、同时事件处理和明确不做。

作品表现不是可随便省略的装饰。必要的界面、反馈、动画、声音和内容随本次交付约定表达。资源成果可包含源版本、工程文件、接入责任、备份安排及必要证据的位置，但这些说明不等于备份已执行。占位资源可以是本次有效输入，不能被误当垃圾或自动升级为最终美术。

工程重构可以以行为不变、接口兼容和回归检查表达；素材任务可以以可编辑源、导出规格与实际镜头下检查表达。没有设计变更的工程修复不要求生成完整 GDD。

## 验证与就绪

优先使用已有且能观察目标行为的检查入口；按需组合自动检查、工程内检查、人工体验判断，不要求一个入口包办一切，也不强制所有类型检查都出现。

写出来的检查是要求，不是结果。自动测试通过不等于手感好；用户确认设计不等于运行过工程。没有相关检查工具时说明缺口，不能悄悄降低标准。

重要未决会影响当前交付时，明确该部分还不能完整执行；可以指出不受影响的已明确范围。草稿、保存、可用于实施和实施授权是不同概念，不通过标签自动合并这些含义。

## 与 GDD 的引用

spec 可以摘录实现不可缺少的规则，并指向 GDD 的对应章节及版本。不要整本复制，也不要只留“看 GDD”三个字。无现成版本标识时引用已读取片段或既有记录，不为标识创建提交。

同一份系统设计已经完全满足本次需求时可直接引用，不重复造一份相同文档。存在独立的本次范围、变更或验收时才建立对应规格。已经结束的旧规格保留当时依据；新采纳变化更新当前相关规格和 GDD，不改写历史得像新规则一直存在。
