# Domain GameStudio

校准本项目的共同语言，用具体情境澄清概念，再保存后续工作确实需要的定义与理由。不是聊天记录器，也不负责完整玩法规格或通用行业知识库。

## 读取与澄清

沿用项目入口和 setup 已建立的术语、设计与决策资料位置。只读相关主题；已有等价文件就直接使用，没有约定时可在获准范围内采用 CONTEXT.md 和 docs/adr/，按需创建。

发现同名异义、异名同义或与既有定义冲突时，先判断是换一种说法、另一个概念，还是用户改变了定义。用实际情境说明会带来什么不同结果；能查的事实自己查，重要取舍由用户决定。表达已清楚就继续，不纠正每一句日常用语。

对照已有要求、当前实现和用户新目标，分别说明不一致，不因代码现状而改写目标。行业知识辅助发现问题，不强制项目采用通用叫法，也不借命名增加机制。与 [grilling-gamestudio](../grilling-gamestudio/SKILL.md) 同时使用时，沿用原问答，不另起重复访谈。

## 选择值得留下的概念

添加前判断：脱离当前对话，后续参与者是否可能合理地误解该概念，并因此产生不同的设计、实现或验证？一条简短定义是否能消除这种差异？

关注本项目特有含义和重要的概念区分，不以词语是否生僻、出现次数或是否首次出现决定收录。普通词也可能值得定义。已有准确定义就复用；模糊含义先澄清，不把猜测写成现行定义。

通用常识、临时称呼、具体数值、完整规则和实现细节不进入术语表。它们需要保存时交给对应资料，而非直接丢弃。只处理本次相关概念，不全库抽取名词或凑齐词典。

## 在授权范围内及时保存

概念已确认且文档维护已获授权时，及时更新相关条目，不逐个询问是否保存，也不等会话末尾才回忆。术语与决策记录是供后续工作复用的正式资料，按技能名称取得 `writing-for-agents` 的写作方法，并按 [docs-gamestudio 的语义保真要求](../docs-gamestudio/references/semantic-fidelity.md)表达：定义足够区分概念，规则和数值不塞进词表，已确认决定与已实现、已验证分开。无法取得时说明具体缺口和受影响的工作，只继续不依赖它的部分，不模仿缺失的方法。参考 [术语写法](references/CONTEXT-FORMAT.md)，保持短定义，必要时说明关系与易混淆说法。

只有决定难以逆转、缺背景时容易被误解、且存在真实取舍时，才建议独立留档；已有可靠记录就引用。参考 [决策写法](references/ADR-FORMAT.md)。已确认决定不等于已经实现或验证；修订时保留必要历史和替代关系。

只讨论或无写入权限时提供未保存草稿。定义变化不自动授权重命名代码、迁移数据、改玩法或外部发布。

## 与文档协作配合

在“讨论并维护文档”任务中，对不适合词表的已确认规则或本次交付要求，按 [文档分流与增量协作](../docs-gamestudio/references/document-routing.md) 交回当前 Agent，按需使用 [gdd-gamestudio](../gdd-gamestudio/SKILL.md) 或 [spec-gamestudio](../spec-gamestudio/SKILL.md)，不把词表变成设计收件箱。

概念或记录没有变化时不写文件。回读实际修改，简短交代已保存位置及未决项，完成当前部分后回到原讨论。
